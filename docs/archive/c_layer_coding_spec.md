C 语言工程标准规范

---

## 1. 引言

本规范旨在为 C 语言软件项目提供一套全面、严格、可实施的工程标准。它整合了业界最佳实践、安全编码指南（如 CERT C、MISRA C:2012）、现代软件工程方法，并强调代码的正确性、安全性、可维护性、可移植性和可测试性。

---

## 2. 适用范围

- 所有新编写的 C 代码（推荐使用 C11 标准，最低 C99）。
- 现有代码的维护、重构和审查。
- 第三方库的集成评估（需符合本规范或提供等效保证）。

---

## 3. 核心原则

1. **正确性优先**  
   严格遵循需求规格，处理所有边界条件、错误路径和异常输入。

2. **安全第一**  
   杜绝内存破坏、未定义行为、注入攻击、侧信道泄露等安全缺陷。

3. **防御性编程**  
   对外部输入、资源状态、函数返回值进行严格校验，不信任任何隐式契约。

4. **可维护性**  
   代码应清晰、模块化、低耦合、文档完整，降低长期维护成本。

5. **可移植性**  
   尽量遵循 ISO C 标准，平台相关代码必须隔离并在文档中说明。

6. **性能合理**  
   在保证正确性和安全性的前提下优化关键路径，避免过度优化和过早优化。

7. **可测试性**  
   设计应便于单元测试、集成测试、故障注入和自动化验证。

---

## 4. 代码风格与格式化

### 4.1 基本格式

- **缩进**：4 个空格，禁止使用 Tab 字符。
- **行宽**：建议不超过 80 字符，最多 120 字符（需团队一致同意）。
- **大括号风格**：推荐 Allman 或 K&R，但项目内必须统一。
- **空格规则**：
  - 二元运算符两侧加空格；
  - 逗号、分号后加空格；
  - 关键字后加空格（如 `if (`）；
  - 函数名与括号间不加空格；
  - 一元运算符与操作数之间不加空格（如 `!flag`、`*ptr`）。
- **指针声明**：`*` 紧贴变量名（`int *ptr;`），项目内统一即可。
- 每条语句独占一行，禁止多语句同行。
- 空行用于分隔逻辑块，增强可读性。

### 4.2 命名约定

- **类型名**：`PascalCase`（如 `VerthysSuperBlock`）。
- **函数名**：`snake_case`（如 `verthys_superblock_init`）。
- **变量名**：`snake_case`，局部变量可适当简短，全局变量必须具有描述性。
- **宏和枚举常量**：全大写加下划线（`MAX_BUFFER_SIZE`）。
- 避免使用下划线开头的标识符（保留给编译器和标准库）。
- 避免使用单字母变量（循环索引 `i`、`j` 允许，但复杂逻辑应使用有意义名称）。

### 4.3 注释与文档

- 每个源文件和头文件应有文件头注释，描述模块用途、设计约束、依赖关系。
- 所有公共函数（非 `static`）必须使用文档注释（推荐 Doxygen 风格），说明：
  - 参数含义及方向（`[in]`、`[out]`、`[in,out]`）；
  - 返回值及错误码；
  - 前置条件、后置条件；
  - 线程安全性；
  - 内存所有权（是否由调用者释放）。
- 复杂算法、非显而易见的逻辑、性能敏感代码必须添加行内注释。
- 注释应解释“为什么”，而不是重复代码做什么。
- 禁止保留已注释掉的代码，应及时删除。

## 5. 语言使用规范

### 5.1 标准遵循

- 使用 C99 或 C11（推荐 C11 以利用 `_Static_assert`、`_Atomic`、`_Generic` 等特性）。
- 禁用编译器特定扩展（除非通过宏封装并明确文档化）。
- 避免使用已废弃或危险的标准库函数，改用安全替代（见附录 B）。

### 5.2 类型安全

- 使用 `<stdint.h>` 定义固定宽度整数类型（`uint32_t`、`int64_t` 等），确保跨平台一致性。
- 使用 `size_t` 表示对象大小、数组索引、内存长度。
- 使用 `ptrdiff_t` 表示指针差值。
- 禁止隐式类型转换导致精度丢失或符号改变；必要时显式转换并检查范围。
- 避免混合有符号和无符号运算，必须混合时需显式转换并注释理由。
- 枚举类型用于表示一组离散值，不用魔法数字。

### 5.3 内存管理

- 所有动态内存分配（`malloc`、`calloc`、`realloc`）必须与对应的释放（`free`）成对出现。
- 使用 `calloc` 或分配后 `memset` 初始化内存。
- 检查所有分配函数的返回值，处理 `NULL`。
- 使用 `realloc` 时，应先将结果赋给临时指针，成功后再替换原指针，避免泄漏。
- 敏感数据（密钥、密码）在使用后必须立即清零，使用 `explicit_bzero`、`SecureZeroMemory` 或平台安全清零函数，并通过 `volatile` 指针防止编译器优化。
- 推荐使用 RAII 模式（通过 `goto cleanup` 实现）确保所有错误路径释放资源。

### 5.4 错误处理

- 定义统一的错误码枚举（如 `Result`），避免魔法数字。
- 所有可能失败的函数返回错误码，调用者必须检查并处理。
- 禁止忽略错误返回值，除非明确注释说明理由。
- 错误路径必须释放已分配资源，保持状态一致。
- 使用 `goto` 跳转到公共清理代码，减少重复和遗漏。
- 错误码必须设计成项目专用，禁止使用统一模板

### 5.5 字符串和缓冲区

- 固定大小缓冲区操作必须使用带长度限制的函数，确保不会越界且结果正确终止。
- **推荐做法**：
  - 使用 `snprintf` 进行格式化输出；
  - 使用 `memcpy` 配合显式长度复制已知长度数据；
  - 使用 `strnlen` 检查字符串长度；
  - 若必须复制 C 字符串，使用 `strlcpy`（若平台支持）或自定义安全拷贝函数，**避免使用 `strncpy`**（因其可能不添加空终止符）。
- 禁止使用用户输入作为格式字符串（`printf(user_input)`）。
- 使用 `const` 限定不修改的指针参数。

## 6. 安全规范

### 6.1 输入验证

- 所有外部输入（文件、网络、用户输入）视为不可信，执行严格验证。
- 验证长度、范围、格式，不依赖调用者保证。
- 解析二进制数据时使用安全读取函数，检查偏移和长度，防止越界读取。

### 6.2 整数安全

- 整数运算前检查溢出（使用 `__builtin_add_overflow` 或手动检查）。
- 数组索引使用 `size_t` 并确保非负。
- 避免有符号溢出、移位超过位宽等未定义行为。
- 混合有符号/无符号运算时显式转换并验证。

### 6.3 指针安全

- 解引用前检查指针非 `NULL`（公共 API 必须检查）。
- 指针算术不得越过数组边界。
- 使用 `restrict` 时确保实际不重叠。
- 函数返回指针时，明确所有权语义（是否需释放、是否可为 NULL）。

### 6.4 敏感数据保护

- 敏感数据（密钥、密码、哈希）使用后立即清零，使用 `volatile` 指针或专用安全清零函数。
- 防止编译器优化掉清零操作（如使用 `explicit_bzero`、`SecureZeroMemory` 或平台 API）。
- 敏感数据避免打印到日志、写入核心转储。

### 6.5 并发与线程安全

- 明确函数是否线程安全，在文档中标注。
- 共享数据必须使用锁、原子操作或不可变设计保护。
- 使用 C11 `_Atomic` 或平台原子库实现无锁结构。
- 锁的粒度适中，避免死锁，遵循一致的获取顺序。

## 7. 模块化与设计

### 7.1 头文件组织

- 头文件应自包含，包含所需的其他头文件或前置声明。
- 使用包含保护（`#ifndef HEADER_H` 或 `#pragma once`）。
- 头文件只声明公共接口，不暴露内部实现。
- 使用 `extern "C"` 包裹以支持 C++ 调用（若需）。
- 避免在头文件中定义变量，可使用 `static inline` 函数或 `enum` / `#define` 定义常量。

### 7.2 接口设计

- 函数参数尽量少（≤ 5 个），复杂结构使用结构体传递。
- 输出参数使用指针，并标注方向（`[out]`、`[in,out]`）。
- 返回错误码，而非通过输出参数传递错误。
- 提供 `init`/`deinit` 对称函数管理生命周期。
- 模块间依赖单向，避免循环依赖。

### 7.3 抽象与可移植性

- 平台相关代码隔离到单独文件（如 `os_posix.c`、`os_win.c`）。
- 条件编译宏最小化，集中管理。
- 抽象常用功能（内存分配、随机数、时间、文件 I/O）为内部接口。
- 遵循 POSIX 或 ISO C 标准，减少平台差异。

## 8. 测试与验证

### 8.1 单元测试

- 每个模块必须有单元测试，覆盖正常路径、边界条件、错误路径。
- 使用成熟测试框架（Unity、CppUTest、CMocka、Google Test 的 C 接口）。
- 测试用例应独立、可重复、快速执行。
- 对安全敏感代码进行专门测试（模糊测试、故障注入、压力测试）。

### 8.2 集成与系统测试

- 定义模块间接口契约，进行集成测试。
- 模拟外部依赖故障（文件系统、网络、内存分配失败），验证恢复逻辑。
- 进行性能测试，确保满足指标。

### 8.3 静态分析

- 强制启用编译器警告：`-Wall -Wextra -Werror`，可加 `-Wconversion`、`-Wshadow`。
- 集成静态分析工具（Clang Static Analyzer、Cppcheck、Coverity、PVS-Studio）。
- 遵循 CERT C 或 MISRA C 子集（根据领域选择）。
- 定期运行并清零告警。

### 8.4 动态分析

- 使用 Valgrind（Memcheck、Helgrind）检查内存错误和线程竞争。
- 在 CI 中使用 AddressSanitizer、UndefinedBehaviorSanitizer、LeakSanitizer。
- 使用覆盖率工具（gcov、LCOV）确保关键路径覆盖。

---

## 9. 构建与工具链

- 使用 CMake 或 Make 管理构建，支持多平台。
- 编译选项严格：`-std=c11 -Wall -Wextra -Wpedantic -Werror`，可加 `-Wconversion` 等。
- 依赖管理使用版本控制，避免系统环境差异。
- 提供 CI 流水线（GitHub Actions、GitLab CI），自动运行构建、测试、静态分析。

---

## 10. 文档

- 每个模块提供设计文档或 README，说明功能、接口、使用示例、限制。
- API 文档使用 Doxygen 自动生成。
- 架构决策记录（ADR）保存设计变更历史。
- 维护编码规范、安全指南，定期更新。

## 附录 B：禁用函数与安全替代

| 禁用函数 | 风险 | 安全替代 |
|----------|------|----------|
| `gets` | 缓冲区溢出 | `fgets` |
| `strcpy` | 无长度检查，可能溢出 | `snprintf`、`strlcpy`（平台支持）或自定义安全拷贝 |
| `strcat` | 无长度检查，可能溢出 | `snprintf`、`strlcat` |
| `sprintf` | 无长度检查，可能溢出 | `snprintf` |
| `scanf` 系列（不安全的 `%s`） | 可能溢出 | `fgets` + `sscanf` 或安全解析函数 |
| `strncpy` | 不保证空终止，易误用 | 避免使用；使用 `snprintf` 或 `memcpy` 显式长度 |
| `memcpy`（用于重叠区域） | 未定义行为 | `memmove` |
