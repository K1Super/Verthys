# 全库密钥轮换内容一致性修复 Spec

## 1. 结论（已验证）

2026-11-11 02:09（本地时间）执行的“恢复码解锁 → 重绑设备 → 全库密钥轮换”
把模块 MDEK 轮换成了新随机密钥，但轮换只重写了记录外层与仓库分片外层，
没有把**内容层分片信封**（照片索引/数据块/缩略图/块集、文件保险箱内容）
从旧 MDEK/旧 epoch 换封到新 MDEK/新 epoch。轮换后这些内容全部认证失败，
表现为拾光照片无法查看原图、文件保险箱内容不可读。

| 证据 | 来源 | 结论 |
| --- | --- | --- |
| `DeviceRebind success` → `VerthysRotate begin/commit`（18:08:46–18:09:32Z） | `audit.log` | 轮换确实在重绑后执行并提交 |
| 轮换进度 `records=204 files=0 chunks=0 bytes=28924532` | `main_ui.log` | 照片内容以“记录”形式存在，不走文件仓库；轮换未对内容层做任何换封 |
| `rot_copy_records` 仅调用 `vty_repo_add_ex` | `core/src/crypto/vty_rotate.c` | 内层信封原样复制，外层用新 MDEK 重封 |
| `vty_module_enable` 无条件 `vty_random(new_mdek)` | `core/src/container/vty_module.c` | 模块密钥在轮换中必然变化 |
| `vty_chunk_seal/open` 以 `MDEK + file_uuid + seq + epoch` 派生内容密钥 | `core/src/container/vty_chunk.c` | 旧内容无法用新 MDEK/新 epoch 解封 |
| `rewrap_content_envelope` 已存在但只被 `vty_repo_module_rekey` 使用 | `core/src/index/vty_repo.c` | 模块启用路径有换封，轮换复制路径漏接 |
| 轮换 `keep_old=false`，`.old-*` 备份被删除 | `vty_rotate_commit` + 审计 | 旧库唯一可回退副本已不存在 |

受影响范围：

- photo 模块（0）：照片索引 `0x01`、数据块 `0x05`、缩略图 `0x07`、块集 `0x09`；
- fileverthys 模块（2）：文件元数据 `0x08`、文件数据块 `0x04`、旧元数据 `0x05`；
- accounts 模块（1）：记录为明文载荷，不经过内容层封装，轮换本身不受影响。

## 2. 目标

1. 全库轮换必须同时完成“容器 DEK 轮换 + 模块 MDEK 轮换 + 内容信封换封”，
   轮换后所有模块内容可正常解密。
2. 轮换提交前必须逐条证明：旧库中能按旧 MDEK/旧 epoch 解封的内容信封，
   在新库中能按新 MDEK/新 epoch 解封；否则整个作业失败、旧库保持不变。
3. 默认保留旧库备份（`.old-*`），作为轮换后的兜底副本；用户显式取消才删除。
4. 内容换封失败/完整性复核失败时，错误码明确（`ERR_00000009`），
   前端提示“轮换已中止、旧库未替换”。

## 3. 非目标

- 不改变容器格式、记录类型分配或模块口令语义。
- 不自动修复已损坏的历史轮换结果（旧 MDEK 已随旧库删除，无法反推）。
- 不替代用户自行导出备份（`.venc`）的职责。

## 4. 设计

### 4.1 轮换内容换封（C 核心）

- `vty_repo_rewrap_content(type, module_index, old_mdek, old_epoch,
  new_mdek, new_epoch, ...)`：
  - 仅处理非系统记录、模块 0/2；
  - 先按旧 MDEK/旧 epoch 尝试解封顶层内容信封；认证成功才重封；
  - 照片索引 `0x01` 与文件元数据 `0x08/0x05` 额外递归换封
    `chunkDataB64` 内联分片（旧版布局）；
  - 明文记录（账户等）认证失败后原样返回 `rewrapped=0`，不误判为损坏。
- `vty_chunk_rewrap_embedded` 增加 `old_epoch/new_epoch` 双参数，
  轮换跨代时分别用于解封与重封。
- `rot_copy_records`：
  - 按叶的 `module_uuid` 定位模块索引；
  - 取旧库/新库该模块 MDEK（启用模块用会话密钥，未启用模块用 Keyring）；
  - 换封后写入新库；回读后调用 `vty_repo_content_envelope_check`
    证明新库可解封，失败返回 `VTY_E_VERIFY`。
- `rot_copy_file`：对文件仓库分片做同样的“可选换封 + 回读校验”，
  覆盖历史双重封装布局。

### 4.2 提交前验证

- 每条换封记录：旧库可解封 → 新库必须可解封（逐条验证）。
- 记录字节回读比对保持既有逻辑；换封只改变内层密文，不影响记录名/类型/ID/时间。
- 任一验证失败 → `VTY_E_VERIFY`，作业失败，源库不替换。

### 4.3 兜底备份

- 后端 `verthys_rotate_commit` 的 `keep_old` 默认值改为 `true`；
- 前端轮换向导“保留旧库备份”默认勾选，并标注推荐；
- 备份命名沿用 `<库路径>.old-<pid>-<tick>`，可用恢复码独立打开；
- 用户显式取消勾选才删除备份。

### 4.4 错误契约

- 轮换完整性复核失败返回 `ERR_00000009`（`VERTHYS_ERR_CORRUPT` 域）；
- 前端轮换向导映射为“数据完整性校验失败：轮换已中止，旧库未被替换；
  请保留现场并联系技术支持”。

## 5. 备选方案与否决理由

| 备选 | 结论 | 理由 |
| --- | --- | --- |
| 轮换不改变 MDEK，只轮换 K_c | 否决 | 改变既有“全库密钥轮换”语义；模块槽仍需按新 K_c/恢复码重封，且无法满足用户对模块密钥轮换的预期 |
| 前端在轮换后逐张重加密照片 | 否决 | 需要全量解密再加密，内存/时间不可控；轮换期间源库只读，前端无法安全重写 |
| 只保留旧库备份、不修换封 | 否决 | 用户每次轮换后仍需从旧库手工恢复，不是根治 |
| 轮换失败时自动回滚到旧库 | 已具备 | 提交前失败不会替换源库；本次补充的是“提交前必须证明新库内容可解” |

## 6. 风险与回滚

- 换封只对旧 MDEK 认证成功的内容生效；明文内容不受影响。
- 逐条回读验证增加轮换耗时（线性于内容条数），但不改变数据量级。
- 保留旧库增加一份库文件占用；用户可显式取消或手动删除 `.old-*`。
- 代码回滚点：`vty_chunk.*`、`vty_repo.*`、`vty_rotate.c`、
  `vault_rotate_controller.rs`、`verthys.ts`、`VaultRotateDialog.vue`。

## 8. 已损坏数据的恢复边界

旧 MDEK 是随机密钥，仅存在于被删除的旧库文件/旧模块描述符中；当前新库
只保留了用旧 MDEK 封装的内容密文，**无法在不恢复旧库文件的前提下解密**。
可选恢复路径：

1. 使用此前导出的 `.venc` 备份重新导入（推荐，用户持有导出密码）；
2. 对磁盘做旧库文件取证恢复（需管理员权限，成功率取决于簇是否被复用）；
3. 若曾保留 `.old-*` 备份（本次轮换未保留），用恢复码打开旧备份导出内容。

本轮修复保证后续轮换不再产生同类损坏，并提供默认旧库备份；不承诺恢复
已被本次缺陷破坏且无备份的密文。
