## 一、审查结论摘要

链路的分层设计本身是清晰的：前端两阶段加载（占位骨架 → 可视区按需解密）、扫描游标三命令状态机、
共享内存带 HMAC 认证与 VirtualLock、读取后随机覆写擦除、锁定时统一清缓存 —— 这些都是高水准的工程化处理。

但**照片业务负载的体量与传输通道的容量假设之间存在系统性错配**，导致这条链路在本项目的真实数据
（几 MB 级照片，元数据内联加密块）上无法可靠工作：

- 「记录」不再是 KB 级小对象，而是 **1.78 × 照片原始体积** 的大对象（内联块 + 两层 base64 膨胀）；
- 而扫描通道被写死为 **8 MiB 固定共享内存窗口**、IPC 响应单行被写死为 **16 MiB**、
  导入侧却允许单条记录 **12 MiB**。

四个阈值互不约束，链路在超过约 4.5 MiB 照片负载时必然断链。此外存在占位项缓存回灌
导致缩略图永久空白、模块密钥在闲置销毁后仍可用、解密全部在主线程等问题。

缺陷统计：**P0 致命 2 项，P1 高 5 项，P2 中 8 项，P3 低 5 项**，共 20 项。

另做**加载速度专项审查**（见第四节）：单列 10 项（含 1 项 P0 级速度缺陷），
并给出精确字节账本、耗时构成与首屏时延预算。速度问题的性质与容量问题同源——
**用最重的通道（全量数据扫描 + 单条 IPC）去完成最轻的任务（渲染列表与缩略图）**，
且项目内已具备的轻量快路径（摘要扫描，仅索引不解密数据）未被采用。

## 二、链路全貌（审查基线）

```
PhotoAlbum.vue onMounted
 └─ isModuleReady("photo") + ensurePhotoKey()          ← 会话缓存取模块密钥
     └─ loadPhotos()
         ├─ getModuleCache("photos") 命中 → 直接回灌（强制 loaded=true）
         ├─ ensureRecordScanSafe()                      ← 永不抛出
         │   └─ ensureRecordScan() → scan_open(200)/scan_next/scan_close
         │       Rust scan_controller → worker scan_open/scan_fetch
         │       → C Verthys_ScanOpen/ScanFetch（LSM 快照迭代 + extent 解密）
         │       → 8 MiB 命名共享内存（HMAC + VirtualLock）→ 读回 → base64
         │       → recordScanCache（LRU-5000，>64 KB 的 dataB64 置空）
         │   失败回退：clearRecordScanCache → 逐条 get_record
         ├─ getRecordIdsByType(TYPE_PHOTO_META) → maxMetaId 增量过滤 → 占位项 push
         └─ setModuleCache("photos", photos.value)
     └─ watch(visiblePhotos) → ensureVisiblePhotosDecrypted()
         ├─ getRecordsDataB64Batch(可视区)              ← 缓存命中 0 IPC；>64 KB 走 getFullRecord IPC（LRU-50）
         ├─ 并发 4 × decryptPhotoMeta → decryptMeta（PBKDF2 150k + XChaCha20 + JSON.parse，主线程）
         └─ updateShallowItem(photos[i])                ← meta 含完整 chunkDataB64，常驻内存
点击照片 → onView → decryptChunk × N（每块一次 PBKDF2）→ 拼接 Blob → viewer
```

## 三、缺陷清单

### P0-1 扫描通道 8 MiB 固定窗口装不下照片记录 → 进入拾光必然扫描失败【P0 · 致命】

- 位置：[shm_schema.rs](file:///c:/Users/Administrator/Desktop/Verthys/verthys-tauri/shm_schema.rs#L74-L76)（`SHM_DEFAULT_SIZE = SHM_MAX_SIZE = 8 * 1024 * 1024`，固定不可增长）、
  [scan_shm.rs](file:///c:/Users/Administrator/Desktop/Verthys/verthys-tauri/verthys-worker/src/runtime/scan_shm.rs#L182-L190)（`needed > self.size` → `Err("data exceeds shared memory size")`）、
  [worker.rs](file:///c:/Users/Administrator/Desktop/Verthys/verthys-tauri/verthys-worker/src/runtime/worker.rs#L584-L629)（一次性取满 200 条再写 SHM，失败即整批失败）、
  [crypto_const.ts](file:///c:/Users/Administrator/Desktop/Verthys/verthys-tauri/src/constants/crypto_const.ts#L41-L56)（`CHUNK_SIZE = 1 MiB`、`MAX_INLINE_META_BYTES = 6 MiB` 判定内联）

- 事实（体积算式）：内联路径下 meta 记录体积 ≈ **1.78 × 照片原始体积**
  （chunk 密文 ≈ P → 内层 base64 ≈ 1.33P → JSON → `encryptMeta` 密文 ≈ 1.33P → 外层 base64 ≈ 1.78P）。
  即一张 5 MiB 照片产生约 8.9 MiB 的单条记录；而扫描窗口总量只有 8 MiB（还要减去 64B 头 + 每条 40B 索引 + 名称区）。
- 为什么是缺陷：扫描取的是**全类型、全明文数据**的记录窗口（C 层对每条记录做 extent 解密并输出完整 data），
  批大小由前端固定 200 条（[verthys-cache-domain.ts](file:///c:/Users/Administrator/Desktop/Verthys/verthys-tauri/src/cache/domain/verthys-cache-domain.ts#L177-L177)），
  通道容量与记录体量之间没有任何按大小自适应的退让逻辑（无"装不下就减少本条批"的收敛）。
- 影响：相册中**只要内联负载合计超过约 4.5 MiB（一张 5 MB 照片或十余张小图）**，`scan_open`/`scan_fetch`
  即返回失败 → `ensureRecordScan` 抛错 → 回退逐条 IPC → 进入 P1-1 的次生灾害。
  用户侧表现为：进入拾光后**照片列表为空（"暂无照片"）或长时间停在"正在解密加载照片…"**。
  该失败是**确定性**的（同一窗口每次必然超限），不重试、不自愈。
- 修复方向（择一或组合）：
  1. 照片模块改走**摘要扫描**（`ensureSummaryScanSafe`，4 MiB、只传元数据）拿 ID，再按需取单条 —— 同时需解决 P1-3 的"缩略图要搬整条密文"问题；
  2. 或让扫描**按字节预算自适应批大小**（先取 1 条试算体积，累计不超过窗口的 60%），并让 C 层支持"跳过数据、只回索引"的元数据模式；
  3. 根治方案：把缩略图从 meta 中拆成独立小记录（见 P1-3），让扫描窗口只承载 KB 级对象。

### P0-2 占位项被以 `loaded=true` 回灌模块缓存 → 重进拾光缩略图永久空白【P0 · 致命】

- 位置：[usePhotoData.ts](file:///c:/Users/Administrator/Desktop/Verthys/verthys-tauri/src/composables/photo-album/usePhotoData.ts#L302-L308)（缓存回灌 `{ ...p, loaded: true }`）、
  同文件 [L344-L356](file:///c:/Users/Administrator/Desktop/Verthys/verthys-tauri/src/composables/photo-album/usePhotoData.ts#L344-L356)（finally 把含占位项的数组写入模块缓存）、
  [L237-L245](file:///c:/Users/Administrator/Desktop/Verthys/verthys-tauri/src/composables/photo-album/usePhotoData.ts#L237-L245)（`if (vph.loaded || !vph.metaId) continue;`）、
  [verthys-cache-domain.ts](file:///c:/Users/Administrator/Desktop/Verthys/verthys-tauri/src/cache/domain/verthys-cache-domain.ts#L292-L300)（模块缓存持有数组**引用**，非快照）

- 事实：`loadPhotos` 的 finally 把 `photos.value`（含 `loaded:false`、`thumb:""` 的占位项）写入模块缓存；
  由于模块缓存存的是同一数组引用，未解密项在缓存中**保持占位态**。第二次进入模块时，
  回灌逻辑对**所有**缓存项强制 `loaded: true`，`ensureVisiblePhotosDecrypted` 因此对所有项 `continue`，
  自动解密被永久跳过（`clearModuleCache` 只在 `lockAll` 清，见 [security-session.ts](file:///c:/Users/Administrator/Desktop/Verthys/verthys-tauri/src/session/security-session.ts#L427-L428)）。
- 影响：切走再切回拾光后，**此前未滚动到的照片全部显示为空板**（无缩略图、无名称、无大小），
  必须逐张点击才能恢复（`onView` 的按需解密回退）。这是高频操作路径上的必然缺陷，非偶发。
- 修复方向：回灌时保留真实 `loaded` 语义（`loaded: !!p.meta`），或对 `thumb === ""` 的项强制视为未加载；
  更彻底的做法是占位项不写缓存、缓存只存已解密项（回灌后余额由扫描 ID 补齐）。

### P1-1 回退枚举路径撞上 16 MiB 单行上限 → 协议断链并杀死 worker【P1 · 高】

- 位置：[actor.rs](file:///c:/Users/Administrator/Desktop/Verthys/verthys-tauri/src-tauri/src/worker/actor.rs#L251-L261)（超长行 → `mark_child_dead_if_needed` + "协议断开"）、
  [protocol.rs](file:///c:/Users/Administrator/Desktop/Verthys/verthys-tauri/src-tauri/src/worker/protocol.rs#L45-L45)（`MAX_LINE_BYTES = 16 MiB`）、
  [verthys-cache-domain.ts](file:///c:/Users/Administrator/Desktop/Verthys/verthys-tauri/src/cache/domain/verthys-cache-domain.ts#L540-L561)（回退 `enumerateRecords` → `enumerateRecordsStream`）、
  [constants.rs](file:///c:/Users/Administrator/Desktop/Verthys/verthys-tauri/src-tauri/src/constants.rs#L167-L167)（导入侧允许单条 `data_b64 ≤ 12 MiB`）、
  [dispatch.rs](file:///c:/Users/Administrator/Desktop/Verthys/verthys-tauri/verthys-worker/src/runtime/dispatch.rs#L260-L270)（`get_record` 响应对已是 base64 的记录数据**再做一次 base64**）

- 事实：P0-1 失败后回退到 `verthysEnumerateRecords`（一次性返回 `startId` 起**全部**记录的单行 JSON）。
  容器内照片负载 > 约 12 MiB 时（两张 6 MB 照片即足够），该行超过 16 MiB →
  actor 判定"输出单行超过上限"→ **标记子进程死亡 + 协议断开**；随后所有 IPC（含后续 `get_record`）全部失败。
  同样地，导入守卫允许 12 MiB 的 `data_b64`，而其读取响应行 = 12 MiB × 4/3 = **16 MiB + JSON 头**，
  本身就越过了单行上限（跨层阈值矛盾）。
- 影响：最坏情况下"部分照片读取失败"升级为**整个加密库会话不可用**（worker 死亡，需解锁流程重建），
  用户看到的是照片列表空白 + 后续任何操作报管道错误。
- 修复方向：① 让回退路径也走**分页/游标**（`enumerate_records` 带 `max_count`），禁止一次性全量；
  ② 建立跨层不变式：`导入单条上限 × 4/3 < 单行上限` 且 `导入单条上限 < 扫描窗口`，用编译期常量断言或 CI 测试锁定；
  ③ 超大响应改为走共享内存/二进制通道，而不是 JSON 单行。

- 位置：[verthys.ts](file:///c:/Users/Administrator/Desktop/Verthys/verthys-tauri/src/lib/verthys.ts#L791-L803)（`if (!r.ok) return { records: [], exhausted: true }`）、
  [verthys-cache-domain.ts](file:///c:/Users/Administrator/Desktop/Verthys/verthys-tauri/src/cache/domain/verthys-cache-domain.ts#L499-L508)（`while (!exhausted)` 依赖该标记）、
  同文件 [L584-L594](file:///c:/Users/Administrator/Desktop/Verthys/verthys-tauri/src/cache/domain/verthys-cache-domain.ts#L584-L594)（`mergeScanEntry` 内存优先、不覆盖）

- 事实：`scan_next` 返回 `ok=false`（熔断/状态机拒绝/共享内存校验失败）时，前端把它当成"遍历结束"，
  循环正常退出、`ensureRecordScan` 视为成功、`maxScannedId` 停在断点。错误既不抛也不上报。
- 影响：**照片列表静默缺失断点之后的全部照片**，UI 无任何异常提示；因 `maxScannedId` 已推进，
  同一会话内不会重扫，只有下次重新进入模块（增量扫描从断点继续）才可能补齐。
- 修复方向：`scan_next` 失败应抛错（与 `scan_open` 的语义对齐），由 `runRecordScan` 的 catch 走回退枚举或整段重扫；
  至少也应把失败上报到 UI（"照片列表加载不完整，可重试"）。

### P1-3 缩略图解密要搬整条内联密文，且反复经 IPC 重取【P1 · 高】

- 位置：[verthys-cache-domain.ts](file:///c:/Users/Administrator/Desktop/Verthys/verthys-tauri/src/cache/domain/verthys-cache-domain.ts#L173-L173)（`DATAB64_CACHE_MAX_BYTES = 64 KB` 管控置空）、
  同文件 [L600-L613](file:///c:/Users/Administrator/Desktop/Verthys/verthys-tauri/src/cache/domain/verthys-cache-domain.ts#L600-L613)（超限只留 id/type/name）、
  同文件 [L710-L731](file:///c:/Users/Administrator/Desktop/Verthys/verthys-tauri/src/cache/domain/verthys-cache-domain.ts#L710-L731)（`getRecordsDataB64Batch` → `getFullRecord` IPC 回退，LRU-50）、
  [usePhotoData.ts](file:///c:/Users/Administrator/Desktop/Verthys/verthys-tauri/src/composables/photo-album/usePhotoData.ts#L248-L281)（可视区批量预取）

- 事实：照片 meta 记录因内联块普遍为 MB 级（P0-1 算式），远超 64 KB 管控阈值 →
  扫描缓存**必然把它置空**，于是每张缩略图都要走 `get_record` IPC 重新搬运整条密文（数 MB base64），
  且只进 LRU-50 的全量缓存，滚动来回即反复重取。扫描阶段已经把同一份数据搬过一次（共享内存），等于**双倍搬运**。
- 影响：滚动浏览相册时持续产生 MB 级 IPC 与内存分配；机械盘/低配机上表现为"缩略图一张张慢慢刷出来"，
  并与 P2-5（主线程解密）叠加成明显卡顿。
- 修复方向：缩略图应可独立读取 —— 把 `thumbB64` 拆为独立小记录（或把 meta 拆成"轻量头 + 负载块"），
  使扫描窗口与 64 KB 管控都能命中它；读取链路按"轻量头"渲染，只有查看原图时才取负载。

- 事实：渲染缩略图只需要 `thumbB64`，但当前实现把整条 meta（含全部 chunk 密文 base64）挂在列表项上，

  用后即弃（或写入 LRU 而不是常驻）；模块缓存对照片列表设容量/裁剪策略。

- 位置：[verthys-cache-domain.ts](file:///c:/Users/Administrator/Desktop/Verthys/verthys-tauri/src/cache/domain/verthys-cache-domain.ts#L313-L322)（闲置 15 min → `removeModuleKey`）、

## 四、加载速度专项审查（性能）

### 4.1 精确字节账本（以单张 5 MiB 内联照片为例）

体积由常量与编码层数推导，非估算；每一层的放大都发生在"渲染一张缩略图"这条路径上：

| 层 | 内容 | 体积 | 依据 |
| --- | --- | --- | --- |
| L0 | 照片原始字节 | 5.00 MiB | 输入 |
| L1 | 分块密文（5 × 1 MiB + tag） | 5.00 MiB | [crypto_const.ts](file:///c:/Users/Administrator/Desktop/Verthys/verthys-tauri/src/constants/crypto_const.ts#L41-L56) `CHUNK_SIZE = 1 MiB` |
| L2 | 内层 base64（`chunkDataB64`） | 6.67 MiB | 内联路径写入 meta |
| L3 | meta JSON（含缩略图/哈希） | ≈ 6.72 MiB | [photo-crypto.worker.ts](file:///c:/Users/Administrator/Desktop/Verthys/verthys-tauri/src/workers/photo-crypto.worker.ts#L205-L235) |
| L4 | `encryptMeta` 后密文 | ≈ 6.72 MiB | XChaCha20 流加密不膨胀 |
| **L5** | **存库记录数据（外层 base64）** | **8.96 MiB** | 该值 = 扫描共享内存需承载的单条体积 |
| **L6** | **`get_record` 响应行（再 base64 一次）** | **11.95 MiB** | [dispatch.rs](file:///c:/Users/Administrator/Desktop/Verthys/verthys-tauri/verthys-worker/src/runtime/dispatch.rs#L260-L270)（单行上限 16 MiB 的 75%） |
| L7 | 前端解码后驻留（`meta.chunkDataB64`） | 6.67 MiB | [usePhotoData.ts](file:///c:/Users/Administrator/Desktop/Verthys/verthys-tauri/src/composables/photo-album/usePhotoData.ts#L221-L228) |

结论：**渲染一张缩略图，要搬运 12 MiB、经历 4 层 MB 级字符串处理，而缩略图本身只有几十 KB。**
30 张 5 MiB 照片的相册：列表首屏要搬运约 269 MiB（且因 P0-1 必然失败）。
