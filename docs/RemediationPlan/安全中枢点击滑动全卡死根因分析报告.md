# 安全中枢点击 / 滑动全卡死根因分析报告

> 产出背景：用户反馈"背景动效还在，但应用无法点击任何功能（包括关闭），全部卡死"，
> 并询问是否与既往底层 C 升级修复有关。应要求：**先找原因，未修改任何代码**。
> 本报告以静态证据链 + 现场取证判定法给出根因定位与根治方向。

---

## 一、结论摘要

| 编号 | 根因 | 性质 | 与本次卡死的因果 |
| --- | --- | --- | --- |
| A | **渲染主线程同帧自旋死循环**（`MasterFrameLoop` 同帧排空语义 × `tiltLoop` 拖拽态无条件自重排） | 前端确定性逻辑缺陷 | **主根因：100% 必现的全卡死来源** |
| B | `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` 环境变量二次注入三项 GPU 强制参数 | 后端启动配置缺陷 | 次根因：另一形态卡死（整画面定格）的潜在来源 |
| — | 既往底层 C 核心升级 | — | **无关**（证据见第四节） |

**一句话回答用户之问**：本次"点击/滑动即全卡死"不是 C 层、也不是 GPU 参数引起的，
而是前端渲染主循环的一个同帧自旋死循环 —— 它在轨道按下的那一刻被必然触发，
且循环永不结束，因此指针抬起事件永远无法被处理，拖拽标志永远为真，卡死永不恢复。
此缺陷结构早于最近一批修复，近批修复未触及它，所以"修复后依然卡死"。

## 二、主根因 A：渲染主线程同帧自旋死循环（完整证据链）

### 2.1 触发路径：轨道按下即入局

[SecurityDashboard.vue](file:///c:/Users/Administrator/Desktop/Verthys/verthys-tauri/src/components/management/SecurityDashboard.vue#L611-L634)
的 `onTrackPointerDown` 在 `pointerdown` 时立即执行：

```ts
dragging.value = true;          // 拖拽标志置真
...
tiltActive = true;
masterFrameLoop.once(tiltLoop); // 排入下一渲染帧
```

关键点：**只按了 `pointerdown`、指针尚未移动就已进入该路径**。
"点击"三档锚点同样落在这里 —— 锚点元素是纯视觉件
（[dashboard.css](file:///c:/Users/Administrator/Desktop/Verthys/verthys-tauri/src/styles/security/dashboard.css#L308-L320)
中 `.bs-anchor { pointer-events: none }`），点击实际落在测线宿主 `.bs-track` 上。
所以**"点击切换"与"滑动"走的是同一条致命路径**，两个症状同源。

### 2.2 死循环结构：tiltLoop 拖拽态无条件自重排

[tiltLoop](file:///c:/Users/Administrator/Desktop/Verthys/verthys-tauri/src/components/management/SecurityDashboard.vue#L565-L582)
每次执行的收尾：

```ts
if (dragging.value || Math.abs(tilt) > 0.02 || Math.abs(tiltVel) > 0.02) {
  masterFrameLoop.once(tiltLoop);   // 重新排入 once 队列
} else {
  ... // 收敛后停止
}
```

- 非拖拽态：摆锤物理按阻尼收敛，几十次迭代后停排 —— 有界。
- **拖拽态：`dragging.value === true` 使条件恒真，每次执行都重新排入自身 —— 无界。**

### 2.3 放大器：主循环的"同帧排空"语义

[master-frame-loop.ts](file:///c:/Users/Administrator/Desktop/Verthys/verthys-tauri/src/core/master-frame-loop.ts#L274-L277)
的每帧调度：

```ts
while (this.onceQueue.length > 0) {
  const task = this.onceQueue.shift();
  if (task) this.runTask({ task, label: "once", errors: 0 }, ctx);
}
```

`once` 队列的契约是"单帧一次性写入"，而排空方式是 **`while` 同帧循环**：
本帧内新排入的任务会被同一帧继续取出执行。

两者组合后的事实链：

1. `pointerdown` → `dragging = true`、`once(tiltLoop)`；
2. 下一个 rAF 帧进入 `loop()` → `while` 取出 `tiltLoop`；
3. `tiltLoop` 执行完 → `dragging` 仍真 → 又把自身 push 回 `onceQueue`；
4. `while` 判断队列非空 → 同帧再次执行 → 回到第 2 步，**永不结束**；
5. 当前 rAF 回调永远无法返回 → 渲染主线程被永久占据。

另有两点放大因素：

- `once` 任务执行入口 [runTask 包裹](file:///c:/Users/Administrator/Desktop/Verthys/verthys-tauri/src/core/master-frame-loop.ts#L274-L277)
  为每次执行新建 `errors: 0` 的任务记录 —— **错误熔断对 once 任务不生效**，
  即使任务抛错也会被捕获后继续自旋，无任何自动断路器；
- 自旋期间 `writeTilt()`（[L557-559](file:///c:/Users/Administrator/Desktop/Verthys/verthys-tauri/src/components/management/SecurityDashboard.vue#L557-L559)）
  每次迭代都执行 `style.setProperty`，虽被浏览器合并，但循环本身无任何让出点。

### 2.4 现象解释矩阵（与用户描述逐一对应）

| 用户观察 | 机制解释 |
| --- | --- |
| 背景动效还在动 | CSS 合成器类动画（氛围弧旋转、端点呼吸、数据包流）由**合成器线程**驱动，与渲染主线程无关，主线程自旋期间照常播放 |
| rAF/WebGL 类动画停（若用户未注意到，因主背景属前者） | 渲染主线程被占，`MasterFrameLoop` 不再产帧 |
| 点击任何功能全部无效 | 主线程事件队列永远饥饿，任何点击（含自定义关闭按钮）都不会被处理 |
| 关闭按钮无效且 45s 硬退出兜底不触发 | 兜底依赖 `CloseRequested` 事件，而自定义关闭按钮的点击根本到不了后端，`CloseRequested` 从未发生 |
| 永不自行恢复 | `pointerup` 无法被处理 → `dragging` 恒真 → 恒自重排 → 恒自旋，闭环自锁 |

### 2.5 与既往批次的关系（为什么"修复后仍卡死"）

- `master-frame-loop.ts` 的 `while` 同帧排空语义：属更早批次的空闲治理基础设施，历次修复未改动；
- `tiltLoop` 的重自排结构：属双星仪表盘设计批次，早于最近一批；
- 最近一批（γ 方案）仅在 tiltLoop 内部**新增了量化写入调用**，未改变"拖拽态恒自重排"的结构，
  也未改变主循环的同帧排空语义 —— **死循环结构原样保留**。

因此该缺陷不是最近改动引入，而是**长期未被识别**；修复后仍卡死是因为此前各轮
（GPU 参数摘除、唤醒分级、氛围迟滞、γ 量化）针对的都是其他问题，从未触及这条自旋链。

## 三、次根因 B：GPU 强制参数的环境变量二次注入

[lib.rs](file:///c:/Users/Administrator/Desktop/Verthys/verthys-tauri/src-tauri/src/lib.rs#L312-L318)
在 WebView2 启动前执行：

```rust
std::env::set_var(
    "WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS",
    "--enable-gpu-rasterization --enable-zero-copy --ignore-gpu-blocklist",
);
```

- 此代码路径**早于** tauri.conf.json 的 `additionalBrowserArgs`（最近批次已摘除），
  摘除动作被这第二注入点完全绕过 —— **最近批次移除 GPU 强制参数的根因修复实际未生效**；
- 本机双显卡环境下，这三个参数与透明分层窗口组合曾诱发 WebView2 GPU 进程 stall；
- 该隐患的卡死**形态不同**：整画面定格（连 CSS 动画也停）而非"动效仍在、交互失效"，
  可据此与根因 A 现场区分。它属于需要根治的第二问题，但不是本次现象的直接来源。

## 四、排除项：底层 C 升级与本次卡死无关的证据

1. **主进程不加载 verthys.dll**：
   [util/ffi.rs](file:///c:/Users/Administrator/Desktop/Verthys/verthys-tauri/src-tauri/src/util/ffi.rs#L71-L89)
   的 `extern "C"` 块全部处于注释状态（仅模板）；主进程内其他 `LoadLibraryW`
   仅加载系统库（`wtsapi32.dll`、`shell32` 等），无 verthys 核心的直连调用。
2. **C 核心仅存在于 worker 子进程**，主进程通过 stdin/stdout 行协议交互；
   全链路为 Actor 模型 + 超时覆盖
   （[session.rs](file:///c:/Users/Administrator/Desktop/Verthys/verthys-tauri/src-tauri/src/worker/session.rs#L229-L256)
   默认 15s `send_json_with_timeout`、`tokio::time::timeout` 包裹读行、
   `block_in_place + block_on` 桥接），C 层即便卡死，最坏后果是命令超时返回错误，
   不会同步阻塞渲染主线程。
3. **渲染主线程自旋是纯前端确定性缺陷**，触发条件与后端状态完全无关
   （`globalKeyReady` / `presetApplying` 两个前置守卫通过与否都会进入同一按下路径，
   仅影响是否提前 return，不影响"按下即自旋"的事实——守卫仅为 false 时直接返回，
   为 true 时必然自旋；两种情况下后端都不参与该帧循环）。

结论：C 升级（无论当时做了什么）不在本次卡死的因果链上，可放心排除。

## 五、复现与现场判定清单（供实测确认）

**必现路径**：
1. 打开安全中枢（安全防护面板）；
2. 在引力测线（轨道）任意位置按下鼠标（不必移动）或点击任一档位锚点；
3. 立即全局卡死。

**现场特征核对**：
- Windows 任务管理器：`msedgewebview2.exe` 渲染进程 CPU 被单线程打满（约 1 核 100%）；
- CSS 氛围动画仍在动、点击全失效、任意时长不恢复；
- 关闭按钮无效，进程不会在 45s 后自行退出（`CloseRequested` 未发生）；
- 若现场是"整画面连动画一起定格"则不是根因 A，改按根因 B（GPU stall）排查。

## 六、根治方向

修复必须同时覆盖"循环结构"与"契约语义"两层，缺一不可：

1. **契约层（根治核心）**：`MasterFrameLoop` 的 once 队列排空改为**帧快照**
   （进入排空前截断队列长度，本帧新排入者留待下一帧），从语义上禁止
   "单帧一次性任务"在同帧内自我延续；或为 once 任务补错误熔断。
2. **调用层**：`tiltLoop` 改为 `register` 常驻 throttled 任务（每帧至多执行一次，
   收敛后注销）或独立的拖拽期驱动，废除"拖拽态无条件自重排"。
3. **同类排查**：`useCosmicBackground` 的 `tickParallax`、`useCardTilt` 等
   存在同模式"once 自重排"的调用点一并审计（它们有收敛界，但同帧过量执行
   会放大单帧耗时，属同类契约违例）。
4. **次根因 B**：删除 lib.rs 中的环境变量注入，并同步校准
   `docs/CONFIGURATION.md` 中对运行期写出点的描述。
5. **修复后门禁**：点击锚点 / 拖拽 / 松手吸附 / 键盘路径 / 连续快速点击回归，
   并辅以渲染线程 CPU 曲线验证自旋消除。

0.08 / 0.12，收敛尾迹约 0.5~1.4s）；节奏如需调整可在泵常量的单点处
调参，不影响结构安全。
