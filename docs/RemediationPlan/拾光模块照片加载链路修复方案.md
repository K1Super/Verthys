## 3. 批次一：前端读取链路（本轮执行）

### 3.1 首屏改走摘要缓存（修 S1 / 规避 P0-1 的用户可见面）

- 新增"带状态"扫描包装（不破坏既有签名）：
  `ensureSummaryScanWithStatus()` / `ensureRecordScanWithStatus()` → `{ ok: boolean; error?: string }`，
  既有 `ensureRecordScanSafe()` / `ensureSummaryScanSafe()` 保持原签名委托到它们（其它模块零改动）。
- `loadPhotos` 改为三阶段：
  1. **阶段 A**：`ensureSummaryScanWithStatus()` → `getSummaryIdsByType(TYPE_PHOTO_META)` → 立即渲染
     （名称取摘要 `name` 并剥离 `meta_` 前缀；尺寸留空，待解密回填）；
  2. **阶段 B**：不再在进入模块时触发全量数据扫描（避免 8 MiB 窗口/16 MiB 单行的失败面）；
  3. **阶段 C**：可视区按需解密（沿用现有 `ensureVisiblePhotosDecrypted`），回填缩略图与真实尺寸。
- 摘要缓存不可用（旧格式容器/扫描失败）时：回退既有全量扫描路径，并在模块顶部显示
  "列表可能不完整，点击重试"的显式提示（不再静默空列表）。
- 摘要 `name` 为记录名（含 `meta_` 前缀），解密成功后以 `meta.name` 覆盖。

### 3.2 缓存回灌与增量过滤（修 P0-2 / P2-4）

纯函数下沉到 [utils.ts](file:///c:/Users/Administrator/Desktop/Verthys/verthys-tauri/src/composables/photo-album/utils.ts)（可单测）：

- `rehydrateEntries(cached)`：**保留真实 `loaded` 语义**——只有已解密（`meta` 存在）的项才置 `loaded: true`；
  未解密项保持待解密状态，回灌后仍会被阶段 C 自动补齐。
- `diffNewIds(allIds, loadedIds)`：增量过滤改为**集合差集**，不再用 `maxMetaId` 单调假设
  （删除中间 ID 后复用的新记录必须能出现）。

### 3.3 状态语义与错误可见（修 P1-2 / P2-2）

- `verthysScanNext` 失败由"静默返回 `exhausted: true`"改为**抛错**
  （与 `verthysScanOpen` 的语义对齐，避免把失败当扫完）。
- `usePhotoData` 维护 `loadError: Ref<string>`：扫描失败、批量预取失败、解密失败计数聚合后
  在模块顶部一次性提示（n 张加载失败 + 重试入口），禁止静默。
- 解密失败仍保留占位项（不删除照片），但标记 `failed: true` 供 UI 呈现；
  `decryptingMetaIds` 用 `try/finally` 保证任何异常路径都能释放去重标记。

### 3.4 密钥驻留（修 P1-5）

- 监听 `moduleKeyReadyRef.photo === false` → 清空 `photoKey`、清空已解密内容、提示"模块密钥已失效，
  请重新进入模块验证"；不再依赖组件卸载时清零。

### 3.5 查看器一致性（修 P2-7 / P2-8）

- `onView` 引入请求序号：过期请求的结果丢弃；覆盖 `viewerBlobUrl` 前先 `revokeObjectURL`。
- 渲染前校验：块数 == `payloadRef`/`chunkHashes` 长度，且逐块 BLAKE3 与 `chunkHashes` 一致；
  不满足 → 提示"照片损坏"而非渲染残缺图。

### 3.6 滚动与定位开销（修 S6 / P3-1 / S10）

- 维护 `metaId → index` 的 `Map`，替代 `photos.value.findIndex`。
- 滚动方向感知预取：前向多取、后向少取；滚动批次 80 ms 去抖合并。

### 3.20 记录模型演进：索引瘦身布局（§5.2 / §5.3 实施规格）

本节是布局二（索引瘦身）的实施依据；布局一为既有落盘形态，二者由读取侧并存解析。

**类型与归属**

| 记录 | 类型 | 载荷 |
|---|---|---|
| 索引（照片元数据） | 0x01（沿用） | 加密 JSON：展示字段 + 缩略图引用 + 负载引用 + 包裹态文件密钥；**不含缩略图数据、不含内联块密文** |
| 缩略图 | 0x07（业务域空闲值） | 单个 AEAD 记录：`nonce(24) ‖ 密文+tag`，AD 绑定文件哈希 |
| 负载块 | 0x05（沿用） | `nonce(24) ‖ 密文+tag`，AD 绑定 `seq‖total‖fileHash`（与布局一同一 AD 构造） |

**密钥层级（§5.3）**

- 每个照片文件一个随机盐 `fileSalt(16)`；包裹密钥 `wrapKey = PBKDF2-150k(fileSalt) → HKDF`（与既有派生链同构，按盐缓存命中）；
- 随机文件密钥 `fileKey(32)`：`wrappedFileKey = fileSalt(16) ‖ nonce(24) ‖ AEAD(wrapKey, fileKey)`（base64 存入索引 JSON）；
- 索引密文头部复用同一 `fileSalt`；缩略图与全部块用 `fileKey` 加密（缩略图用 `wrapKey`，避免为缩略图单独解封文件密钥）；
- 派生次数（每文件）：写 2 次（块任务 1 + 索引任务 1，与布局一相同）；读 1 次（索引解密即派生 `wrapKey`，缩略图与块解封复用缓存）。

**索引 JSON 字段（布局二）**：`fmt=2`、`name`、`mime`、`size`、`thumbId`、`chunkSetId`、`chunkCount`、`fileHash`、`createdAt`、`wrappedFileKey`；`thumbB64` 为空串（缩略图数据在独立记录）；逐块引用与逐块哈希在块集记录内（§3.21.1；读取侧保留对"索引内联 `chunkIds`/`chunkHashes`"早期形态的回退分支）。

**读取分流**：`fmt` 缺省或 1 → 既有路径（缩略图在索引内、块自包含）；`fmt=2` → 先解密索引（得 `thumbId`/`wrappedFileKey`），再取缩略图记录解密；查看原图/导出用 `wrappedFileKey` 解封 `fileKey` 后逐块解密。分流判定为纯函数，任一侧缺失即回落既有路径（不产生不可读窗口）。

**写入与迁移（§5.5 惰性演进）**

- 写入开关 `PHOTO_WRITE_FMT`（编译期常量，**默认既有布局**）：开关决定"从磁盘新导入"采用哪种布局；
- 容器（.venc）导入按**来源布局保留**：块密文无法在缺少来源密钥时重写，保留布局是数据保真的唯一正确做法；容器轻量头相应携带布局标记与包裹态密钥，供接收端预检与分流；
- 存量数据零改动（读取走既有路径），不做一次性全库重写；后台重打包为可选项，已在 §3.21.2 落地（默认关 → 入口不出现）。

**共享内存/缓存预算**：块集记录承载逐块项后（§3.21.1），索引明文上界 2656 字节（密文 base64 ≤ 3616 字节），块集记录明文上界 7964 字节（密文 base64 ≤ 10696 字节，最大照片 100 块场景），缩略图记录密文 ≤ 45076 字节——均在扫描缓存管控阈值（65536 字节）内 → 列表渲染与刷新零 IPC；预算由常量生成器断言把守，索引加密处对超预算输入前置拒绝。

**删除级联**：索引删除时同步删除 `chunkIds` 与 `thumbId`，并失效两层缓存与扫描缓存；块/缩略图记录经同一写者 FIFO 与台账（孤儿候选转正）保证不残留。

### 3.21 块集记录（索引瘦身至目标量级）与后台重打包（§5.2 收口 + §5.5 可选项落地）

#### 3.21.1 块集记录：把逐块引用与哈希移出索引

**动机**：布局二的索引此前仍携带 `chunkIds` 与 `chunkHashes`，二者随分块数线性增长（最大照片 100 块时 ≈ 7.7 KB 明文），是索引体积的主体；而列表路径（最高频）根本不需要逐块引用。

**落地方案**：新增**块集记录**承载逐块引用与哈希，索引只保留聚合引用（§5.2 的"块集标识 + 块数"）。

| 记录 | 类型 | 载荷（解密后） |
|---|---|---|
| 块集 | 0x09（扩展域空闲值） | `{ ids: number[], hashes: string[] }`（按序一一对应；密文与缩略图同规格：`nonce‖AEAD(wrapKey)`，AD 绑定文件哈希） |
| 索引（布局二，字段收口） | 0x01 | `fmt / name / mime / size / thumbId / chunkSetId / chunkCount / fileHash / createdAt / wrappedFileKey`，`thumbB64` 为空串 |

- **校验不变式**：取块集后须校验 `ids.length === hashes.length === 索引 chunkCount`，且块序号由数组位置给出（与 AD 绑定的 seq 一致）。
- **兼容**：仍保留对"早期布局二"（索引内联 `chunkIds`/`chunkHashes`、无 `chunkSetId`）的读取分支——存在 `chunkSetId` 时走块集，否则回落索引内联引用；既有布局一完全不受影响。
- **读放大变化**：列表路径少解密 ~6.7 KB/张（索引变小）；查看器/导出/删除多一次块集记录取用与解密（扫描缓存命中则零 IPC）。
- **预算（派生实测值）**：索引明文上界由"最大分块数 × 每块引用与哈希"改为"名称 + 固定字段 + 包裹密钥 + 聚合引用"——由 10460 字节降到 **2656 字节**（密文 base64 ≤ 3616 字节；典型照片 ≈ 数百字节，达成 §5.2 的"≈1 KiB"目标量级）；块集记录明文上界 **7964 字节**（密文 base64 ≤ 10696 字节，最大照片 100 块场景）；两者均 ≤ 扫描缓存管控阈值（65536 字节），由常量生成器两条不变式断言把守。

#### 3.21.2 后台重打包（存量布局 → 布局二）

**语义**：把**布局一**照片就地改写为**布局二**（重新加密为瘦身布局并删除旧记录集），低优先级、可取消、可续跑、不阻塞前台。

- **触发与门禁**：仅在写入布局开关为布局二时可用（默认关 → 入口不出现），入口为拾光模块顶栏的迁移按钮（图标按钮，悬浮提示"迁移旧布局照片（后台任务，可取消）"），运行中显示进度横幅（已处理/总数、成功/跳过/失败）与"取消迁移"。
- **单张流程（幂等单元）**：读索引 → 解密（已是布局二则跳过）→ 取块密文并解密 → **整图 BLAKE3 校验**（不通过即记失败、绝不影响源记录）→ 按布局二重新加密（新盐/新随机文件密钥/新索引 + 缩略图记录 + 块集记录 + 块记录）→ 新索引落库成功后再删除旧记录集（索引 + 旧块）→ 更新前端三层缓存与列表项引用（原位替换为新记录 ID，缩略图与解密状态复位）。
- **断点续传**：进度由"摘要索引中的布局一照片"驱动；已迁移的条目不再出现在待迁移集合，重启后自然续跑；崩溃窗口内新写入的块/缩略图/块集记录为孤儿候选，由既有块台账 GC 回收（与导入同一机制）。
- **失败处理**：任一步失败按张记账（读取/解密/校验/写入/删除），源记录保持不变；单项失败不中止整体，结束时汇总展示；后端按内容哈希去重跳过（`DUPLICATE_SKIPPED`）计"跳过"而非失败（源记录保留，下一轮再试）。
- **不变量**：任何时刻"旧索引仍在则新记录为孤儿"或"新索引已在则旧记录待删"——两者都可被读取侧正确处理（前者读旧、后者读新），不存在不可读窗口。

### 3.22 导出路径解密下沉 Worker 池（§3.19 剩余项 2 收口）

**动机**：导出链路的解密此前在主线程执行——占位项（重启后未解密）的索引解密、索引瘦身布局的缩略图记录解密、明文导出的整图逐块解密（PBKDF2-150k + AEAD）；整图导出会在解密期间持续占用渲染主线程。

**落地方案**

- 三个解密点全部改走 `workers/photo-decrypt-bridge`（Worker 池优先 + 主线程兜底）：
  占位项索引解密 → `decryptMetaPreferWorker`；瘦身缩略图 → `decryptThumbPreferWorker`；
  整图逐块 → `decryptChunksPreferWorker`（瘦身布局携带包裹密钥与块总数，块密文无自描述序号）。
- **顺序校验统一下沉**：既有布局"块自描述位置（seq/total）与列表位置一致"的判定由共享
  解密路径（Worker 与主线程回退）统一执行，导出/查看器/重打包口径一致；截断或乱序的
  块列表在拼接前即拒绝（此前仅明文导出侧单独校验）。
- **进度与取消语义不变**：解密为单张一次任务，逐张状态与百分比照旧；导出期间对话框
  不可关闭、无取消入口的既有语义未改变。
- **失败归因修正**：明文导出（PNG）此前将解密/完整性校验失败与画布转换失败混记为同一类；
  现以专用错误类型区分，解密失败归因 `decrypt-failed`（文案"照片解密或完整性校验失败"）。

## 5. 批次三：记录模型演进

### 5.1 类型分配（遵守既有值域）

| 类型 | 值 | 说明 |
|---|---|---|
| `TYPE_PHOTO_META` | 0x01（沿用） | 照片**索引**记录；新增格式在解密后的 JSON 中以 `fmt` 标记区分，扫描与类型索引零改动 |
| `TYPE_PHOTO_THUMB` | 0x07（业务域空闲值） | 独立缩略图记录，≤64 KiB（命中扫描缓存管控阈值） |
| `TYPE_PHOTO_CHUNK` | 0x05（沿用） | 负载块记录；新格式块在载荷头部携带 `fmt` 标记 |

禁止使用 `0x0301+` 之类跨越值域的编号（历史类型冲突事故的根因即值域失守）。

### 5.2 索引瘦身

- 索引记录只保留：名称、尺寸、MIME、缩略图引用、负载引用（块集标识 + 块数 + 块大小 + 整图 BLAKE3）；
  不再内联块密文。
- 缩略图独立后，索引 JSON ≈ 1 KiB 量级 → 扫描缓存可直接承载（≤64 KiB 管控不再置空），
  列表渲染与刷新零 IPC。

### 5.3 键派生收敛

- 每文件一次 `PBKDF2(150k)` 派生 wrap 密钥并包裹随机 `fileKey`；块级仅随机 nonce，
  `fileKey` 随索引记录一并保存（包裹态）。
- 该变更改变既有密文格式 → 必须与**存量兼容读取**并存：按索引 JSON 中的 `fmt` 标记分流，
  旧格式沿用旧路径（每块派生），新格式走新路径；不做一次性全库重写。

### 5.4 解密下沉与缩略图 URL

- 扩展既有 `photo-crypto.worker` 协议（新增 `decrypt_meta` / `decrypt_chunks` 操作），
  解密在主线程之外执行；主线程只接收展示字段与明文块（已落地，见 §3.13）。
- 缩略图与查看器统一 Blob URL，显式 `revokeObjectURL`（覆盖前、条目淘汰、组件卸载）。
  查看器路径已具备覆盖前释放；缩略图 Blob URL 仍待实施（S9）。

### 5.5 兼容与迁移

- 存量照片：**惰性演进**——读取走旧路径，用户重新导入/编辑时按新格式写入；
  可选"后台重打包"任务（低优先级、可取消、断点续传），不强制、不阻塞。
- 任何时刻不允许出现"只写新格式、读不了旧格式"的窗口。

## 6. 常量与跨层不变式（修正版）

单一权威来源：`constants/photo_budget.schema.json` + 生成器 `constants/generate.mjs`
（产出 TS / Rust 两份常量，CI 校验生成物与 schema 一致；不产出 C 头文件，理由见 §3.15 偏差记录）。

| 常量 | 值 | 说明 |
|---|---|---|
| `PHOTO_INDEX_MAX_BYTES` | 派生（已落地 2656） | 索引记录明文上界：由"名称 + 固定字段 + 聚合引用"派生（逐块项在块集记录内，§3.21.1）；密文 base64 上界 3616，达成 ~1 KiB 目标量级 |
| `PHOTO_THUMB_MAX_BYTES` | 65536 | 与扫描缓存管控阈值一致 |
| `PAYLOAD_CHUNK_SIZE_MIN/MAX` | 1 MiB / 8 MiB | 块大小自适应区间 |
| `PAYLOAD_MAX_CHUNKS` | 16384 | 单图块数上限 |
| `SCAN_BATCH_MAX_BYTES` | 生成量 | = `SHM 可用 × 水位线`（当前 SHM 8 MiB → 4.8 MiB） |
| `IPC_MAX_LINE_BYTES` | 16777216 | 与 worker 行协议上限一致（原值不动） |
| `DATAB64_CACHE_MAX_BYTES` | 65536 | 与 `PHOTO_THUMB_MAX_BYTES` 成对约束 |

跨层断言（生成器 + Rust/C 静态断言，TS 只做同值再导出）：

1. `PHOTO_INDEX_MAX_BYTES + 4096 ≤ SCAN_BATCH_MAX_BYTES`
2. `PHOTO_THUMB_MAX_BYTES ≤ DATAB64_CACHE_MAX_BYTES`
3. `PHOTO_INDEX_MAX_BYTES × 4/3 + 4096 ≤ IPC_MAX_LINE_BYTES`
4. `PAYLOAD_CHUNK_SIZE_MAX × 4/3 + 4096 ≤ IPC_MAX_LINE_BYTES`

落地后的断言集合以生成器为准（当前 11 条）：除上表 4 条语义外，另有"含缩略图的元数据记录密文 ≤ 缓存管控阈值""缓存管控阈值 ≤ 后端内联阈值""单批块上传载荷 ≤ 单次载荷上限""响应行落三层行上限""索引密文 ≤ 缓存管控阈值""块集记录密文 ≤ 缓存管控阈值""缩略图记录密文 ≤ 缓存管控阈值"；Rust 同源常量带编译期 `const` 断言（含新增 4 个 `PB_*` 常量，§3.21.3）。

## 8. 回滚与兼容

- **批次粒度回滚**：每批次独立提交，回滚 = 回退该批次提交；批次一不含数据格式变更，
  回滚零风险。
- **常量开关**：`SCAN_BATCH_MAX_BYTES` 等以编译期常量提供，若需临时放宽/收紧，
  改 schema 重新生成（受断言保护）。
- **格式兼容**：批次三起新旧格式并存读取；写入新格式需显式开关（默认关，
  内部验证通过后再开），杜绝"写得出、读不回"。

## 9. 明确不做（避免范围失控）

1. 不做二进制 IPC 帧协议（需重写 worker 行协议与两侧契约，收益小于风险，另行评估）。
2. 不做通用 Feature Flag 基建（现只有渲染开关注册表；回滚以批次 + 常量实现）。
3. 不做照片层引用计数去重（底层 extent 已按内容去重并维护 `ref_count`；
   照片层只保留导入前重复提示）。
4. 不做单图 32 GB / 库 100 TB 的规模承诺（需分片流式导入，另立专项）。
5. 不重写既有加密原语与已知密文格式（仅新增格式共存与惰性演进）。
