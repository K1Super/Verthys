# 清藏模块导入文件链路修复方案（第 3 版 · 二轮自审修订后）

> 定位：本文件是清藏（FileVerthys）「导入文件」链路的唯一施工方案。依据：《[审查清单](./清藏模块导入文件链路审查清单.md)》+ 一轮自审（Q-1~Q-18、§十.2）+ 二轮自审（R-1~R-12）。
> 第 3 版变更：**P0-1 独立为 Wave H hotfix（在线缺陷不绑迁移）**；P0-1 数据结构闭合（`Committed` 已含 `verthys_id`，仅需增 `chunk_ids`）；单遍路径补身份校验；**导出统一流式单路径**（消除双分支与内存表述错误）；base64 子项显式裁定；密码校验职责唯一化；D1 改为**单一常量入 schema**；锚点改代码块无歧义；新增 R 裁定表。
> 前提：不改动存储格式的**既有可读性**（旧 meta、旧内联块、v1 逐块盐加密全部保持可读可导出）；新增写入一律走新契约。
> 纪律：所有改动点给出 `文件:行号` 级落点与可验证验收标准；无长期特性开关、不留死代码。

## 一、修复总纲（六条纪律）

1. **单一权威**：分块尺寸、IPC 预算、名称/哈希长度、**单文件体量上限**一律引用跨层预算常量（权威源 `verthys-tauri/constants/photo_budget.schema.json` → `constants/generate.mjs` 生成 `photo_budget.rs`〔经 `shm_schema.rs` `include!` 共享〕与 `src/constants/photo_budget.generated.ts`；CI `--check` 门禁）。禁止新增字面量；现存字面量按 §5.1 收编。
2. **一处写入**：清藏的存储变更（块、meta、删除墓碑）一律经导入会话与唯一写者通道（`state/import_writer.rs`），禁止命令层直连 worker 写数据域。
3. **完整性前置、失败即失败**：写入前可证（引用已上传、载荷合规）、导出前可验（块齐全 + 逐块哈希 + 总长一致 + 源文件身份稳定）；任何越界/缺块/读少/校验不符一律**报错**，禁止静默截断与降级成功。
4. **结果式契约**：命令返回结构化 `ok/error_code`，前端按码分支并给出可执行文案；禁止字符串判等错误、禁止吞错。
5. **失败可收敛**：失败要么回滚（台账结算/补偿删除），要么可重试（去重跳过/幂等键）；禁止"看不见却占空间"与"看得见却打不开"。
6. **无死代码、无未裁定子项**：被取代的实现在同一波次内删除；审查发现的每个子项必须显式裁定（接受/改造），不允许"静默丢弃"。

## 二、目标架构与不变式

### 2.1 施工后链路

```
导入（FileVerthys → useFileImport 组合式）
  ├─ 选择文件（plugin-dialog 多选）→ user_file_stat(path)：{size, mtime_ms} 初始快照
  ├─ 会话初始化：verthysWalRecover → verthysImportBegin（含台账结算，见 P0-1）
  ├─ 逐文件（按是否存在待跳过集合选择读法）：
  │   ├─ 无遗留 committed 集合 → 单遍：读 4MiB 片 →（可选加密）→ 上传块 → 末了算 fileHash → 写 meta
  │   │     └─ 身份复查：每批边界 + 文件结束 stat 复查；收尾断言 已读字节 === 初始 size
  │   └─ 有遗留集合 → 两遍：Pass A 仅读+哈希 → 命中即"去重跳过"；
  │                未命中 → Pass B 读+（可选加密）+上传 → 同样做批边界/结束复查
  ├─ 块上传：verthysAddChunkBatch（4MiB 块 → 2 块/批，受 12MiB 与 8 条双预算约束）
  ├─ meta：verthysAddRecordsBatch（chunk_ids + chunk_hashes + schema v2 字段）
  ├─ verthysImportEnd(success = 全部文件成功且台账已落盘)
  ├─ persistVerthys → 列表提交（仅 metaId 已确认的条目）
  └─ verthysGcOrphanChunks（best-effort；内部先结算后回收）
导出（保存到本地）——统一流式单路径（无大小分支）
  ├─ 密码前置：v2 用 passwordCheck 判定（在弹保存路径对话框之前）；v1 无此机制
  ├─ 元数据前置：schema/chunkIds 长度/size 一致性 + chunkSize 校验（不读块）
  ├─ 逐块管道：getRecord → 缺失即失败 →(v2) BLAKE3 校验 → 解密 → append 流 → 累计 offset
  ├─ 收尾：offset === size → finalizeUserFileStream（fsync + rename 原子替换）
  └─ 任一步失败 → abortUserFileStream（删暂存）+ 明确错误；目标位置不产生文件
删除
  ├─ verthysDeleteRecords([...chunkIds, metaId])（单次批量事务）
  ├─ verthysForgetHashes([meta.hash])（释放去重；legacy meta 无 hash 则跳过并记日志）
  ├─ persistVerthys → 成功才移除 UI；失败回滚 UI + 明确错误 + 可重试
  └─ verthysGcOrphanChunks（best-effort）
```

### 2.2 硬性不变式（施工与测试共同锁定）

| 编号 | 不变式 | 校验点 |
| --- | --- | --- |
| INV-1 | 列表条目必有 `metaId`；其 `chunkIds` 全部已 commit | 列表重建 + 导入成功路径 |
| INV-2 | 成功计数只在该文件 meta 写入成功后递增 | 导入循环 |
| INV-3 | 导出字节数恒等于 meta.size；块序与 chunkIds 严格对齐 | 导出管道逐块断言 |
| INV-4 | 台账 owner ∈ {0} ∪ {已 commit 的 metaId}；**GC 删除 owner==0 的前置是"台账已与 WAL 结算、无未结算引用"** | 写者 + 会话创建结算 + GC 守卫（P0-1） |
| INV-5 | `end(success)` 仅在台账落盘成功后允许压缩 WAL | `import_end`（P0-1） |
| INV-6 | 任何失败路径不得产生"目标文件已存在但内容不完整"（直写与流式均为 tmp+fsync+rename） | 导出失败路径（`file_controller.rs:941-979`、`:1316-1355`） |
| INV-7 | 块记录名不承载原始文件名与分块序号（`chunk_{hash}`） | 写者命名派生 |
| INV-8 | **源文件身份稳定（全路径适用）**：`(size, mtime_ms)` 在文件开始、每个批边界、文件结束三处一致；且"已读总字节 === 初始 size"；任一不符即中止该文件（`E_FILE_CHANGED`） | 单遍与两遍路径均适用 |

## 三、决策点

| 编号 | 决策 | 裁定 | 依据/影响 |
| --- | --- | --- | --- |
| D1 | 单文件体量上限的权威源 | **收编为单一 schema 常量**：`photo_budget.schema.json` 新增 `constants.user_file_size_limit = 2147483648`；生成器由该键派生 `PB_USER_FILE_SIZE_LIMIT` 与 `PB_MAX_EXPORT_SINGLE_BYTES`（同源赋值 + `checks` 断言相等）；`file_controller.rs:69/:802/:933` 改用生成常量（删除本地字面量）；TS 侧同步生成供前端预检 | 纪律 1（R-9）。影响面已核实：Rust `file_controller.rs:1296`；前端 `usePhotoExport.ts:534-535`（照片导出预检，阈值随生成物自动更新为 2GiB——**照片侧为放宽**，需一条回归用例）；`crypto_const.ts:20` 再导出 |
| D2 | meta 记录名是否去文件名 | 保持 `meta_<文件名>`（容器整体加密，无外泄面；便于诊断） | 备选 `fvmeta_<hash16>` 仅影响可读性 |
| D3 | 流式读取形态与越界语义 | 无状态 `read_user_file(path, offset, length)` + `user_file_stat(path)`；**越界即报错**（客户端按 size 计算尾块，不静默截断） | 纪律 3；单次调用超时独立定义（§5） |
| D4 | 跨会话重复导入语义 | `fileHash = BLAKE3(明文 ‖ formatVer ‖ keyFingerprint)`：无密码时指纹为固定常量，有密码时为 v2 文件密钥的 BLAKE3 → 同内容同密码命中跳过；同内容不同密码视为不同条目 | Q-11；删除时 `forget_hashes` 释放 |
| D5 | `completedChunks` 处置 | 新写入不再写该字段（读取侧忽略历史值）；`chunkSize` 保留并在导出前置校验 | Q-18 |
| D6 | 块载荷 base64 放大是否接受 | **接受（显式降级）**：批量上限把放大限制在固定上界（≤ `PB_MAX_CHUNK_BATCH_B64` = 11,185,504B/批，与文件大小无关）；不改 worker 行协议（raw/JSON 混传需改动协议与引用校验，收益仅 ~1.7MB/批峰值） | R-4；验收口径按"批量上界"核算，不再声称"消除 base64" |
| D7 | 导出路径是否保留 ≤64MiB 内存分支 | **不保留：统一流式单路径**（与拾光导出口径一致；小文件为 1~N 次 4MiB append，代价可忽略） | R-10：消除双分支与"峰值与文件大小无关"的错误表述；零字节文件走 0 次 append + finalize |

## 四、修复项列表

### P0-1 ｜（共享写者）GC 误删窗口：**独立 hotfix（Wave H）**

- **问题**：台账 owner 改写只在写者内存，落盘在批末且失败被吞；`WalEntry::Committed` 不携带块引用；`process_end` 不落盘台账。窗口：**meta 已 committed 而台账仍为 owner=0** → 下一次 GC 删除被 committed meta 引用的块 → 数据"看得见却打不开"，且去重键仍在、重导被跳过。
- **根因**：块归属持久化与 meta 提交持久化不同步、失败静默降级；恢复路径无归属结算。
- **证据**：`import_writer.rs:455-461`（内存改写）、`:499-507`（批末落盘失败仅记 error，注释"GC 退化为保守不删"与事实不符）、`:756-778`（end 不落盘）；`verthys_wal.rs:68-75`（`Committed` 无 `chunk_ids`）；`verthys_batch_controller.rs:141-165`（会话创建不结算）、`:633-654`（GC 无二次确认）；触发点 `importPipeline.ts:1008`、`usePhotoDelete.ts:347`。
- **数据结构闭合（R-1 已核实）**：`WalEntry::Committed` **已含 `verthys_id: u64`**（`verthys_wal.rs:69-75`），`WalSnapshot` **已含 `committed_ids: HashMap<hash, verthys_id>`**（`:107`）。因此 **只需为 `Committed` 增 `#[serde(default)] chunk_ids: Vec<u64>`**，快照即可构造 `committed_chunk_owners: HashMap<chunk_id, verthys_id>`（由同一 `Committed` 条目的 `verthys_id` 与新增 `chunk_ids` 笛卡尔绑定）；旧 WAL 行反序列化为空 `chunk_ids`（不结算、GC 保守拒绝，见第 4 步）。
- **修复设计（四件套闭环）**：
  1. **WAL 携带引用**：`Committed` 增 `chunk_ids`（`#[serde(default)]`）；写入点 `import_writer.rs:426-432` 传入 `rec.chunk_ids`；快照累积 `committed_chunk_owners`。
  2. **会话创建即结算**：`ImportSession::new` 载入快照后，对 `committed_chunk_owners` 逐条 `ledger.set_owner(chunk_id, verthys_id)` → `save_chunk_ledger`；**落盘失败 → `verthys_import_begin` 拒绝创建会话**。落点：`verthys_batch_controller.rs:141-165`。
  3. **落盘义务收紧**：批末台账落盘失败 → 置会话标志 `ledger_dirty`（不再吞错）；`import_end(success=true)` 必须先成功落盘台账，否则返回 Err 且**不压缩 WAL**；`import_end(false)` 原样保留。落点：`import_writer.rs:499-507`、`:756-778`。
  4. **GC 前置守卫**：`verthys_gc_orphan_chunks` 先结算（加载 WAL 快照 → 有 `chunk_ids` 的 committed 条目则改写归属并落盘；对**无法证明归属**的历史条目，把台账中仍为孤儿候选的条目冻结为不可回收值）再回收；结算落盘失败 → **拒绝本次回收**。落点：`verthys_batch_controller.rs:597-700`。
     - 施工细化（相对冻结版的差异，已评审记录）：冻结比"拒绝 GC"更优——被冻结条目永不进入回收面（`garbage_ids()` 只返回归属为 0 的条目），因此无需靠拒绝回收来兜底，也不会让容器长期失去回收能力；代价是历史孤儿块永久保留（安全优先，空间可接受）。
- **实施记录（Wave H 已交付）**：
  - `repository/verthys_wal.rs`：`Committed.chunk_ids`（`Option` + `serde(default)`，缺省即历史条目）、`WalSnapshot.committed_chunk_owners` / `has_unsettleable_commits`、`apply_settlement` / `settle_chunk_owners` / `SettlementOutcome`、`ImportSession::new` 结算（先结算后截断 WAL）、`ImportSession.ledger_dirty`。
  - `repository/verthys_chunks.rs`：`UNVERIFIABLE_OWNER` 冻结值、`owner_of` 查询、`garbage_ids` 语义注明排除冻结项。
  - `state/import_writer.rs`：`Committed` 写入携带 `chunk_ids`；批末台账落盘失败置脏（不再吞错）；`process_end(success)` 先落盘台账，失败即拒绝结束并保留会话与 WAL。
  - `controller/verthys_batch_controller.rs`：GC 回收前结算守卫。
  - 验证：`cargo test --lib` 411 通过；新增 8 例（WAL 5 / 写者 2 / 台账 1）；`cargo clippy --all-targets -- -D warnings` 零告警；`verthys-worker` 33 通过。
- **发布形态（R-2）**：**Wave H 独立 hotfix，先于一切清藏改动上线**（它同时消除拾光链路的在线误删风险，不得与迁移捆在同一波次）。清藏迁移（Wave 2）以"H 已上线"为前置。
- **验收标准**：模拟"WAL 含 committed chunk_ids + 台账 owner=0"→ GC 先结算、不误删；模拟台账落盘失败 → `end(success)` 返回 Err 且 WAL 未压缩；正常路径 owner 持久化后 GC 回收真孤儿。
- **回归防线**：Rust 单测三态（结算/end 失败/GC 守卫）；照片链路"导入-删除-重导"E2E 回归。

### P1-1 ｜ meta 写入失败仍计成功（假成功 + 孤儿块）

- **回归防线**：`useFileImport.spec.ts`（meta 失败/块失败/正常）；Wave 2 追加"失败文件块被 GC 回收"断言。

### P1-2 ｜ 导出静默损坏：统一流式单路径管道

- **证据**：`FileVerthys.vue:548-552 / :568-573 / :587-589`。
- **修复设计**（D7：统一流式；R-5/R-12：密码职责唯一化）：
  1. **密码前置（唯一判定点）**：v2 meta → `passwordCheck` 解密校验，失败即 `E_PWD_WRONG`（发生在**弹保存路径对话框之前**，用户不白选路径）；v1 meta → 无该机制，不前置判定。
  2. **元数据前置（不读块）**：`chunkIds.length === totalChunks`；`size === 0 ⇔ chunkIds.length === 0`；`chunkSize === CHUNK_SIZE`；v2 的 `chunkHashes.length === chunkIds.length`。
  3. **管道**：`i = 0..N-1`：`getRecord(chunkIds[i])` → null 即 abort（`E_CHUNK_MISSING`，含第 i+1 块）→（v2）`BLAKE3(块密文) === chunkHashes[i]` 否则 abort（`E_CHUNK_CORRUPTED`）→ 解密（**解密失败一律 `E_CHUNK_CORRUPTED`**，不再用"全部失败=密码错"的启发式）→ `appendUserFileChunk` → `offset += len` → 非尾块长度断言。
  4. **收尾**：`offset === size` → `finalizeUserFileStream`（fsync + rename 原子替换，`file_controller.rs:1327-1355`）。
  5. **失败路径**：`abortUserFileStream`（删暂存）+ 明确错误；目标位置不产生文件（INV-6）。
  6. **内存口径（R-10 修正）**：峰值 = 单块密文/明文 + base64（≤ ~7MiB），**与文件大小无关**（因无内存装配分支）。
  7. **v1 文案口径（R-12）**：v1 无 `passwordCheck` → 解密失败统一提示"**密码错误或数据已损坏**"，并给出可执行引导（先核对密码；若密码确认无误，提示可能数据损坏，建议从备份恢复或联系支持）；v2 精确区分两种原因。
- **验收标准**：缺块/哈希不符/损坏 → 精确分类；v2 错误密码在选路径前即失败；v1 错误密码显示合并文案且引导可执行；1GiB 正确路径与源文件逐字节一致、内存峰值 ≤ 128MiB。
- **回归防线**：导出矩阵（缺块/错序/哈希/密码〔v2〕/合并文案〔v1〕/长度不符/空文件/1GiB 流式）。

### P2-1 ｜ 架构收敛：迁移到导入会话 + 台账 + 去重跳过

- **证据**：`FileVerthys.vue:5 / :374-477`；对照 `verthys.ts:511-560`、`verthys_batch_controller.rs:248-279`。
- **修复设计**：
  1. **Rust 改动**：`constants.rs::record_types` 增 `TYPE_FILEVERTHYS_CHUNK = 4`；`import_writer.rs:644-654` 白名单加入；名称沿用 `chunk_{hash}`（INV-7）。meta 路径无需类型白名单。
  2. **术语（Q-7 + R-8 修正）**：本链路提供"**文件级去重跳过**"；**块级重传不保证幂等**——有密码分支每块唯一 IV，重传产生不同密文与不同 hash（新增块记录，旧块由台账 + GC 回收）；仅无密码分支（块 = 明文）同 hash 幂等复用。模块头注释与 UI 文案按此修订，不得再写"块级幂等重传"。
  3. **前端管线**：`useFileImport.ts`；块批 2 块/次（4MiB 块 base64 5.33MiB × 2 ≤ 11.19MiB 预算；口径见 D6）。
  4. **hash 语义（Q-3 已核实）**：块 `hash` 是客户端会话内幂等键（后端不重算，`types.rs:797-802`）；meta 的 `chunk_hashes` 后端**不校验**（`:373-393` 仅校验 `chunk_ids` 引用存在性），导出完整性由前端消费（P1-2）。
  5. **去重跳过（D4）**：`fileHash` 命中 → 跳过并显式报告；删除链路 `verthysForgetHashes` 释放。
  6. **中断恢复**：中断 → `verthysImportEnd(false)` 保留 WAL；下次 `import_begin` 结算（P0-1）+ 恢复跳过集合。
  7. **删除旧路径**：`FileVerthys.vue` 内 `verthysAddRecord` 全部移除。
- **验收标准**：100 文件导入中杀 worker → 重启重试 → 已提交文件跳过、无重复记录、无孤儿增长；重复导入同文件显式跳过。

### P2-2 ｜ 流式读取 + 明文清零 + 源文件身份稳定 + base64 裁定

- **证据**：`file_controller.rs:818-831`；`verthys.ts:1429-1432`；`FileVerthys.vue:421`；原则 `verthys.ts:2-22`。
- **修复设计**：
  1. `read_user_file` 增 `offset/length`（D3）：`length ≤ PB_WRITE_FILE_CHUNK_BYTES`(4MiB)；**越界即报错**；单次调用超时 `USER_FILE_CHUNK_OP_TIMEOUT = 15s`（整文件读取的 120s 语义保留给 `read_user_file` 缺省形态）。
  2. 新增 `user_file_stat(path) → {size, mtime_ms}`（授权链同 `read_user_file`）：分块规划（totalChunks/进度）+ 身份快照。
  3. **身份稳定（R-3 修正，全路径）**：文件开始采集快照；**单遍与两遍路径均在每批边界与文件结束复查**；收尾断言"已读总字节 === 初始 size"；不符 → `E_FILE_CHANGED` 中止该文件（已上传块留台账供 GC）。残余风险（同长同 mtime 的对抗性改写）在 §十.3 声明。
  4. 单遍优先（Q-16）：`committedHashes` 为空 → 单遍；非空 → 两遍（Pass A 只读+哈希判定跳过）。
  5. 明文清零：每块缓冲用后 `fill(0)`。
  6. **base64 子项裁定（R-4 → D6）**：迁移后块上传仍为 base64（`ChunkBlob.data_b64`），放大被批预算限制在固定上界（≤ 11.19MiB/批，与文件大小无关）；不新增 raw 通道（协议与校验改动成本 > 收益）。**本子项显式关闭**，验收口径按批上界核算。
- **验收标准**：1GiB 导入内存峰值 ≤ 128MiB；无整文件读取；导入中修改源文件（长度变化或 mtime 变化）→ 中止；批上界实测 ≤ 11.19MiB。
- **回归防线**：Rust 单测（offset/length 边界 + 缺省行为 + stat 契约）；vitest（迭代器边界/批边界身份复查/结束断言）。

### P2-3 ｜ 文件级 KDF（v2）与密码校验职责

- **修复设计**：
  1. meta 增 `kdf: {version:2, saltB64, iterations}` 与 `passwordCheck`（AEAD 加密固定明文 `verthys-filecheck-v1`）。
  2. 块密文 v2 = `iv(12) ‖ ct`；密钥 PBKDF2(pwd, salt, 150k) **派生一次**；块循环仅 AES-GCM。
  3. 解密分流：v2 文件级密钥；v1（`salt|iv|ct`）走 `decryptPasswordField`（`crypto.ts:1419-1428`）——存量零迁移。
  4. **职责唯一化（R-5）**：`passwordCheck` 是 v2 **唯一**密码判定点（导出前置）；管道内块解密失败一律报损坏；v1 无判定点 → 合并文案（R-12）。
  5. 安全论证（Q-10）：`passwordCheck` 是密码校验 oracle（与块数据的 AEAD oracle 同类，不新增可离线攻击的新界面），价值是提前失败点与原因分离；安全下限由 PBKDF2 150k + 密码强度承担。
  6. 与 D4 联动：`keyFingerprint` 取 v2 文件密钥的 BLAKE3（无密码为固定常量）。
- **验收标准**：1GiB 带密码文件 KDF 占比 ≤ 5%；v2 错误密码即时精确提示；v1 显示合并文案；v1 存量往返通过；同内容不同密码可并存。
- **回归防线**：`crypto-filekey.spec.ts`（v2 往返/v1 兼容/篡改检测/passwordCheck/指纹去重键）。

### Wave 3 —— 加密与体量（依赖 Wave 2）

3.1 KDF v2 + `passwordCheck` + 指纹去重键 → 3.2 D1 常量收编（schema + 生成 + 三处引用 + 照片导出预检回归）→ 3.3（按实测决定）BLAKE3 移入 Worker → 3.4 磁盘空间预检

**出口门**：1GiB 内存/耗时达标；v1 往返；照片导出上限放宽回归；常量门 `--check` 通过。

> **施工裁定（实现前冻结）**：
> 1. **无密码条目不写** `kdf`/`passwordCheck`（明文件无密码校验面）；`encrypted: true` 的条目两者必写。
> 2. **去重键维持"内容 + 形态标志"口径**（D4 的"指纹取文件密钥 BLAKE3"**不采纳**）：文件盐每次随机 → 密钥指纹不稳定（续传重试会把已提交文件重复导入，破坏 Wave 2 已验收的中断续传跳过）；若改为稳定值则必然是口令派生量，而会话日志（`<容器>.import.wal` 与其快照）为明文 JSON，落盘即等于公开口令验证器（可离线爆破）。结论：去重键不引入任何密钥/口令材料；同内容不同口令共用一键（沿用既有边界：删除后可用新口令重导）。据此，§9.1"同内容不同密码可并存"回写为"删除后重导可换口令"。
> 3. **2GiB 边界语义**：`size > limit` 拒绝（恰好 2GiB 允许）；前端预检文案按 GB 显示（避免 "2048 MB"）。
> 4. **磁盘预检时机**：导入 = `user_file_stat` 之后、读块之前（容器卷 = 当前会话容器路径所在卷；阈值 `size × 1.05`）；导出 = 选定保存路径之后、开流之前（目标卷；阈值 `size`）。失败一律前置拒绝且零副作用。
> 5. **`check_disk_space(path?)`**：独立命令，`path` 缺省 = 当前会话容器路径（无路径/未解锁即报错）；实现复用 `util::disk`（新增字节口径查询，MB 口径函数改为其派生）。
> 6. **crypto 层接口**（`lib/crypto.ts` 扩展，测试落 `crypto-filekey.spec.ts`）：`FileKdfV2{version,saltB64,iterations}`、`FileKeyV2{key,kdf}`、`createFileKeyV2`（随机盐一次派生，原始密钥导入句柄后即刻清零）、`unlockFileKeyV2`、`encryptChunkV2`（`iv(12)‖ct+tag`）、`decryptChunkV2`、`buildPasswordCheckV2` / `verifyPasswordCheckV2`（固定明文）；`passwordCheck` 为唯一密码判定点。
> 7. **导入管线接口**：deps 增 `v2?: FileKeySuite`（有密码时必用文件级密钥，每文件派生一次；历史逐块盐写入路径删除——无未来用途，不留死代码）；去重键沿用 `fileHashSuffix(encrypted)` 布尔口径（见裁定 2）。
> 8. **导出管线接口**：条目增 `kdf?`/`passwordCheck?`；deps 增 `openV2Decryptor`（成功返回块解密会话；密码不匹配返回 null → `E_PWD_WRONG`，发生在选路径之前）；v2 块解密失败一律 `E_CHUNK_CORRUPTED`（不再用"全部失败=密码错"启发式）；v1 保持合并文案并补可执行引导。

## 十、残余未决核实项

1. **（已闭合）D1 消费方核实**：导出上限消费方为 `file_controller.rs:1296`（流式追加）与前端 `writeUserFileStream`（拾光导出、清藏导出），D1 定稿为"统一单文件体量上限"。
2. **（已闭合）BLAKE3 后端选型**：实测纯 JS 实现 28~29 MB/s（1GiB ≈ 36s，不可接受）；项目既有依赖 hash-wasm（WASM）实测流式 512 MB/s、逐块 4MiB 489 MB/s（每块约 8ms），且两者摘要逐字节一致。**裁定：批量哈希改用 hash-wasm 的流式实例**（同一算法、零新增依赖、无需移入 Worker），照片链路现实现不动。
3. **（已闭合）extent 去重生效范围**：核心层验收测试实跑通过（`verthys_tests.exe v3ext_dedup` → `[OK] v3ext_dedup_no_rewrite`）。分层结论：去重键为写入 extent 的字节——无密码分支写入明文，跨文件同内容块共享 extent（去重生效）；有密码分支每块唯一随机盐/IV → 密文互异（去重不生效，与 §7.3 一致）。
4. **已知设计边界（声明而非修复）**：单遍路径对"长度不变且 mtime 被改写者还原"的对抗性修改不可检测（本地非对抗场景由批边界 mtime 复查覆盖）；如需更强保证需引入读后整体重读比对（代价 2× I/O），本方案不采纳。
5. **（已闭合）T-1 事实核实**：core 为 V3-only；非 V3 容器在解锁格式门禁即被 `VERTHYS_ERR_FORMAT` 拒绝（`verthys_api.c:952-959`），不存在"已解锁但格式需升级"状态 → 裁定 **B 分支**（全仓删除死分支），锚点 C 已启用并注入即红。
