# 拾光模块总修复方案

> 定位：可直接施工的统一执行文档。收敛全部残余缺陷、接缝缺口与纪律破口，并成为本文件集内唯一的总方案。
> 前置：加载链路、导入链路、导出链路的主体修复已核实落地；关键门禁可复现（复跑值见「验收判据」）。
> 约束：无外部依赖；无数据模型变更；不做数据迁移；不引入不存在的基础设施；构建与部署由项目方执行。

---

## 修复原则

1. **一处定义、一处消费**。跨层数值只有一个权威定义点；由权威来源产出的常量必须存在真实消费者。
   仅参与派生公式的输入、仅用于编译期断言的输入，如实归类，不伪装成有消费者。
2. **接缝必须有组合用例**。凡涉及布局开关或跨批次约定的能力，必须在既有测试套件中给出显式用例，
   或以可执行的验收步骤落地；不以「声明式注册表」等无实现机制的形式充当门禁。
3. **契约必须机器校验**。符号集合、常量消费、部署产物哈希的一致性由脚本校验，不依赖人工同步。
4. **存量兼容、零迁移**。旧数据保持可读（双布局并存解析）；迁移仅通过可选重打包完成。
   回滚以批次为单位，不引入特性开关系统。

## 一、回灌契约与瘦身布局接缝（严重）

### 缺陷实质

回灌入口以「是否已解密」作为「是否已加载」的判据。瘦身布局的索引内缩略图恒为空（缩略图在独立记录），
回灌重建得到空缩略图却仍标记已加载；可视区解密对已加载项短路，切回模块后整页缩略图永久空白且无法自愈。

### 目标行为

| `meta` 存在 | 布局 | `thumbId` | 回灌结果 |
| --- | --- | --- | --- |
| 否 | — | — | 待解密态（占位项） |
| 是 | 既有布局 | — | 已加载；缩略图按 `thumbB64` 重建（为空则置空，不保留陈旧地址） |
| 是 | 瘦身布局 | 大于零 | **回到待解密态**，由可视区按引用回填 |
| 是 | 瘦身布局 | 零 | 已加载，缩略图置空（源照片本身无缩略图） |

### 改法（`verthys-tauri/src/composables/photo-album/utils.ts`）

```ts
import { isSlimPhotoMeta } from "../../constants/crypto_const";

/**
 * 回灌入口：把模块缓存项恢复为列表项。
 *
 * 「已加载」与「具备可渲染的缩略图来源」绑定：瘦身布局的缩略图在独立记录中，
 * 回灌时无法就地重建，必须回到待解密态由可视区按引用回填；否则已加载短路会
 * 使缩略图永久空白。重建器缺省时沿用缓存字段，但不为不可渲染项沿用——
 * 上一会话的地址可能已被释放。
 */
export function rehydrateEntries(
  cached: readonly PhotoEntry[],
  rebuildThumb?: (thumbB64: string) => string,
): PhotoEntry[] {
  return cached.map((p) => {
    const meta = p.meta;
    const decrypted = meta != null;
    const needsThumbRefill = meta != null && isSlimPhotoMeta(meta);

    let thumb = "";
    if (decrypted && !needsThumbRefill) {
      const b64 = meta?.thumbB64 ?? "";
      thumb = rebuildThumb ? (b64 ? rebuildThumb(b64) : "") : p.thumb;
    }

    return {
      ...p,
      loaded: decrypted && !needsThumbRefill,
      failed: false,
      thumb,
      size: decrypted ? p.size : "",
    };
  });
}
```

要点：

- `isSlimPhotoMeta` 已包含「布局为瘦身且缩略图引用大于零」，无需重复判定；
- 重建器存在且内联缩略图为空时必须置空（保留陈旧地址会渲染失效图）；
- 无重建器的调用沿用缓存字段的既有语义仅适用于可渲染项；
- 可视区链路无需改动（按引用取数、解密、回填的能力已具备）。

### 测试（`utils.spec.ts` 新增，既有用例不得回归）

- 瘦身且带引用：回灌后 `loaded === false`、`thumb === ""`；
- 瘦身且无引用：回灌后 `loaded === true`；
- 既有布局且内联缩略图非空：重建得到地址、`loaded === true`；
- 既有用例「重建器存在但 meta 无缩略图数据时置空」必须保持通过（该用例会捕获"沿用陈旧地址"的回归）。

### 前置与验收

必须在写入布局切换或重打包入口向用户开放之前落地。真机：布局切为瘦身后导入三张，
进入模块、切走、切回，缩略图自动补齐，无需点击。

## 二、跨层常量唯一化与消费门禁（严重）

### 缺陷实质

- 落盘服务的重试次数、退避间隔、自查超时已进入预算表并由生成器产出，但前端与 Rust 双侧均无消费者；
  真实行为使用硬编码（重试次数与权威值不一致），自查环节无限等待。
- 另一批同语义值在两侧各写一份（手写字面量），无绑定、无断言，漂移不可见。

### 改法一：落盘服务接线（`verthys-tauri/src/cache/domain/verthys-flush-service.ts`）

顶部导入生成常量，删除本地同名常量与字面量；模块自有的单次超时与等待超时保留（属本模块语义）。

```ts
import {
  FLUSH_MAX_RETRIES,
  FLUSH_RETRY_BACKOFF_MS,
  FLUSH_VERIFY_TIMEOUT_MS,
} from "../../constants/photo_budget.generated";
```

为落盘自查加超时包裹（原调用点直接替换）：

```ts
// 自查走 worker 进程内持锁句柄，IPC 无响应时不能无限等待；
// 超时按可重试失败处理——与 IO 失败的重试动作一致（重试或重建会话）。
const verify = await Promise.race([
  verthysVerifyDiskPersist(),
  new Promise<null>((resolve) =>
    this.trackedSetTimeout(() => resolve(null), FLUSH_VERIFY_TIMEOUT_MS),
  ),
]);
if (!verify) {
  this.lastFlushError = `落盘自查超时 ${FLUSH_VERIFY_TIMEOUT_MS}ms`;
  if (attempt === FLUSH_MAX_RETRIES) {
    return { kind: "verify_failed", statusCode: VER_PERSIST_E_IO, detail: this.lastFlushError };
  }
  await this.backoff(attempt);
  continue;
}
```

注释同步：类头与常量区说明改为「次数、退避、自查超时由跨层预算常量给出」。

### 改法二：无消费者常量裁决

- `flush` 与 `session` 超时三组常量属**前端语义**，Rust 侧无消费者且不应有；
  从 Rust 发射段移除对应行，仅保留 TS 侧并完成接线（session 三常量已在调用点消费，仅清理 Rust 冗余发射）。
- 仅用于编译期断言的常量（如元数据/索引/块集预算的断言输入）不要求外部消费者，
  但不允许把它们伪装成"已声明消费者"。

### 改法三：其余同语义双写清理

| 值 | 权威来源动作 | 消费点 |
| --- | --- | --- |
| 照片单文件上限 | `photo_max_bytes` 增发 TS 侧常量 | 前端导入闸门（已有 `MAX_PHOTO_BYTES` 消费点，改为再导出生成值，删除字面量） |
| 记录名上限 | `max_record_name_bytes` 增发 Rust 侧常量 | Rust 写者与主机命令（已有消费点，改为引用生成值，删除字面量） |
| 导出分片字节 | 新增 `write_file_chunk_bytes`，发射两侧 | Rust 追加命令（已有消费点）；前端不另存字面量 |
| 单文件导出上限 | 新增 `max_export_single_bytes`，发射两侧 | Rust 累计上限（已有消费点）；前端在单文件导出入口消费：以总字节估算值与该上限比对并拦截（当前该常量前端无消费者，属死常量，必须二选一：接线或删除，不允许悬空） |

字面量删除后，前端常量模块统一改为「再导出生成值」，保持既有导入路径不变。

### 改法四：常量消费门（真实版，接入持续集成）

对**跨层行为常量**逐名检查生成文件之外的真实使用点（TS 与 Rust 各自清单）。
清单随新增常量扩展；接入顺序与接线同批次，避免门禁先红后绿。

```powershell
# ===== 常量消费门 =====
# 跨层行为常量必须有真实消费点：生成常量失去消费者时，权威来源即失效。
$tsSrc = Join-Path $projectRoot "verthys-tauri\src"
$rsRoots = @(
  (Join-Path $projectRoot "verthys-tauri\src-tauri\src"),
  (Join-Path $projectRoot "verthys-tauri\verthys-worker\src")
)
$tsGenerated = Join-Path $tsSrc "constants\photo_budget.generated.ts"
$rsGenerated = Join-Path $projectRoot "verthys-tauri\photo_budget.rs"

$tsRequired = @(
  'FLUSH_MAX_RETRIES', 'FLUSH_RETRY_BACKOFF_MS', 'FLUSH_VERIFY_TIMEOUT_MS',
  'SESSION_BEGIN_TIMEOUT_MS', 'SESSION_END_TIMEOUT_MS', 'SESSION_FORCE_CLOSE_TIMEOUT_MS',
  'DATAB64_CACHE_MAX_BYTES', 'PHOTO_INDEX_MAX_BYTES', 'PHOTO_THUMB_MAX_CHARS'
)
$rsRequired = @(
  'PB_IPC_MAX_RESPONSE_LINE_BYTES', 'PB_IPC_MAX_REQUEST_LINE_BYTES', 'PB_IPC_MAX_LINE_BYTES',
  'PB_ENUM_RESPONSE_DATA_BUDGET_BYTES', 'PB_SCAN_INDEX_INLINE_MAX_BYTES',
  'PB_IPC_MAX_PAYLOAD_BYTES', 'PB_MAX_CHUNKS_PER_IPC'
)
$fail = $false
foreach ($name in $tsRequired) {
  $hits = Get-ChildItem -Path $tsSrc -Recurse -Filter *.ts |
    Where-Object { $_.FullName -ne $tsGenerated } |
    Select-String -Pattern "\b$name\b"
  if (-not $hits) { Write-Host "[常量消费门][RED] $name 无消费点"; $fail = $true }
}
foreach ($name in $rsRequired) {
  $hits = Get-ChildItem -Path $rsRoots -Recurse -Filter *.rs |
    Where-Object { $_.FullName -ne $rsGenerated } |
    Select-String -Pattern "\b$name\b"
  if (-not $hits) { Write-Host "[常量消费门][RED] $name 无消费点"; $fail = $true }
}
if ($fail) { $exitCode = 1 } else { Write-Host "[常量消费门] 通过" }
```

### 验收

- 行为级单测（新增 `verthys-flush-service.spec.ts`，mock 库层函数并使用假定时器）：
  持续 flush 失败时实际调用次数等于权威值；自查悬挂时超时后按重试预算推进并落在 `verify_failed`；
- 常量生成校验通过（条数以实际输出为准，不手写数字）；
- 常量消费门通过；导出契约门（见第五节）通过。

## 三、完整性校验下沉与主线程长任务消除（严重）

### 缺陷实质

查看器与导出在渲染前于主线程对全部块密文做解码与逐块哈希（纯脚本同步实现）。
单图上限较大时该阶段可造成秒级主线程阻塞，且无阶段反馈；与"派生与 AEAD 已下沉 Worker"的既有目标相悖。

### 目标

逐块校验在 Worker 内完成，与解密同一任务；主线程只做块数与哈希项数的常数级判定；
校验失败按确定性失败拒绝，不回退主线程重算（主线程回退分支本身保留校验，属降级路径）。

### 改法

**协议（`photo-crypto-protocol.ts`，可加性）**：在 `PhotoDecryptChunksRequest` 增加可选字段
`expectedHashes?: string[]`（缺省或空数组表示不校验；空哈希数组属历史记录，兼容保留）。

**Worker（`photo-crypto.worker.ts` 的 `processDecryptChunks`）**：逐块解密前校验，失败即整体失败：

```ts
// 完整性校验与解密同任务：Worker 侧解码一次密文用于哈希比对；
// 不一致即拒绝该任务，绝不产出未校验的明文。
// 注意：Worker 侧抛出普通错误即可，池会按任务类别把失败响应归类为确定性拒绝；
// 不可也无需引用池侧的错误类型（跨线程无法传递该类型实例）。
if (expectedHashes && expectedHashes.length > 0) {
  const actual = bytesToHex(blake3(base64ToBytes(chunksB64[c]), { dkLen: FILE_HASH_LEN }));
  if (actual !== expectedHashes[c]) {
    throw new Error(`块密文哈希校验失败（第 ${c + 1}/${chunksB64.length} 块）`);
  }
}
```

（`blake3`、`base64ToBytes`、`bytesToHex`、`FILE_HASH_LEN` 已在 Worker 内导入使用，无需新增依赖。）

**桥（`photo-decrypt-bridge.ts`）**：保持既有形参顺序，追加可选形参并透传：

```ts
export async function decryptChunksPreferWorker(
  chunksB64: string[],
  photoKey: string,
  fileHashHex: string,
  label: string,
  slim?: SlimChunkParams,
  expectedHashes?: string[],
): Promise<Uint8Array[]> {
  // submitDecryptChunks 请求体追加 expectedHashes；
  // 主线程回退分支（decryptChunksOnMainThread）同样执行逐块校验——
  // 回退属降级路径，接受其主线程成本，但不降低校验标准。
}
```

**查看器（`usePhotoViewer.ts`）**：主线程只保留常数级判定，逐块校验交由 Worker：

```ts
const expected = refs.inlineCipher.length > 0 ? refs.inlineCipher.length : refs.ids.length;
// 空哈希数组属历史记录（无权威值，不比对）；非空必须与密文块数一致，
// 不一致视为数据损坏，不进入解密。
const hashesPartial = refs.hashes.length > 0 && refs.hashes.length !== cipherB64.length;
if (cipherB64.length !== expected || hashesPartial) {

    ? `缺失 ${notFound} 块`

    : "块数不一致";
  console.error(`[onView] 照片数据不完整：${detail}`);
  showError("此照片数据已损坏，请删除后重新导入");
  commitViewer(seq, thumbUrlOf(ph.thumb));
  return;
}

const slim = isSlimLayout(meta) && meta.wrappedFileKey
  ? { wrappedFileKey: meta.wrappedFileKey, chunkTotal: cipherB64.length }
  : undefined;
plaintexts = await decryptChunksPreferWorker(
  cipherB64, photoKey.value, meta.fileHash, ph.name, slim,
  refs.hashes.length > 0 ? refs.hashes : undefined,
);
```

（删除该文件对主线程哈希函数与比较函数的调用；若导入因此不再被使用，同步清理导入。）

**导出（`usePhotoExport.ts`）**：同构改造——透传哈希项，失败归因保持既有专用错误类型不变。

### 验收

- 单测：Worker 可用路径下主线程哈希函数不被调用；哈希不符明确拒绝且不回退；
  `expectedHashes` 缺省或空数组保持历史兼容；主线程回退路径仍执行校验；
- 性能：大图点击查看时，入口到首个异步等待之间的同步段不含兆字节级计算（真机核对）。

## 五、导出符号契约门禁（改进）

权威清单（`core/verthys.def`）与验收基线（`ci/export_baseline.txt`）集合必须相等；
基线当前缺少一个新增导出且无任何脚本消费。先补齐基线（按字母序追加缺失符号），
再把集合比对接入持续集成（注意递归遍历需用目录枚举，路径通配 `**` 在 PowerShell 中不递归）：

```powershell
# ===== 导出契约门 =====
# verthys.def 为导出符号权威清单，基线为验收快照；集合不相等即失败。
Write-Host "[导出契约门] 校验导出符号与基线一致..."
$defSyms = (Select-String -Path (Join-Path $projectRoot "core\verthys.def") -Pattern '^\s*Verthys_\w+' |
  ForEach-Object { $_.Line.Trim() }) | Sort-Object
$baseSyms = (Get-Content (Join-Path $projectRoot "ci\export_baseline.txt") |
  Where-Object { $_.Trim() -ne '' }) | Sort-Object
$diff = Compare-Object $defSyms $baseSyms
if ($diff) {
  Write-Host "[导出契约门][RED] 导出符号与基线不一致："
  $diff | ForEach-Object { Write-Host ("  {0} {1}" -f $_.SideIndicator, $_.InputObject) }
  $exitCode = 1
} else {
  Write-Host "[导出契约门] 通过：$($defSyms.Count) 个符号一致"
}
```

反向演练：临时删除任一侧一行，门禁必须变红。

## 六、部署产物一致性（改进）

- 存在一份早期构建的 Worker 副本，与现行主副本哈希不一致；该副本不在运行时解析路径内，
  当前不可运行，但破坏可审计性且可能被后续脚本或人工误用。

- 声明修正：「所有候选路径哈希一致」改为「按解析路径枚举校验」，逐条列出运行时可解析的候选并逐一比对：
  开发解析优先的 Worker 构建产物、资源打包源、运行目录同级候选、动态库的部署副本。

验收：全量哈希复查通过；声明与校验方式一致。

## 七、读侧错误语义判别化（改进）

单条记录读取失败仅告警后返回空值，调用方无法区分「记录不存在 / 超出单条上限 / 通道异常」。

改法（保持兼容的渐进式）：新增判别式读取函数（失败携带原始错误与分类），
原函数保留为兼容包装并委托新函数（失败仍返回空值，既有调用方行为不变）；
需要归因的调用方（完整性巡检、回读路径）迁移到判别式版本，
结果文案区分「记录超出单条读取上限」与「读取通道异常，可重试」。

验收：模拟超限错误返回，断言判别式结果不被折叠为空值；既有调用方回归通过。

## 施工顺序与前置

批次一：回灌契约修正 + 常量接线（含双写清理、消费门、行为级用例）。两项互不依赖，可并行。
批次二：完整性校验下沉 + 块集防线（同一代码段一次改到位）+ Worker 重建与部署（项目方执行构建脚本）。
批次三：导出契约门 + 基线补齐 + 陈旧副本处置 + 读侧判别式化。
批次四：文档同步 + 全量门禁复跑 + 真机验收。

依赖说明：批次二不依赖批次一（两者代码面无交集）；批次三与其余独立；批次四收口。

## 机械门禁汇总

| 门禁 | 作用 | 接入点 |
| --- | --- | --- |
| 常量消费门 | 跨层行为常量失去消费者即失败 | 持续集成脚本 |
| 导出契约门 | 权威清单与基线集合不相等即失败 | 持续集成脚本 |
| 既有门禁 | 常量生成校验、锚点门、静态规则与架构分析、版本一致性 | 维持不变 |

明确不做：不引入特性开关系统、不引入指标系统、不建立「组合用例注册表」类无实现机制的声明式门禁；
组合覆盖由既有测试套件中的显式用例与真机验收清单承载。

## 回滚与兼容

- 回滚以批次为单位（代码回退），唯一编译期开关为既有的写入布局常量；不引入特性开关。
- 无数据模型变更、无数据迁移；存量数据保持可读（双布局并存解析），迁移仅通过可选重打包。
