### P0-1 落盘校验与 C 层会话字节范围锁结构性冲突 → 持久化门禁恒为假【P0 · 致命】

**证据链（代码 + 运行日志双向证实）**

1. C 层会话句柄持有超级块区**独占字节范围锁**，且贯穿整个解锁态：
   - `core/src/container/io/verthys_container_lock.c:192`：`LockFileEx(LOCKFILE_EXCLUSIVE_LOCK | LOCKFILE_FAIL_IMMEDIATELY)`，范围 `[0, VERTHYS_V3_WAL_REGION_OFFSET)` = 前 64KB。
   - `core/src/api/lifecycle/verthys_api.c:518` 解锁时 `verthys_container_open_exclusive` 打开并持锁；`:548-568` 解锁成功后 `ctx->v3` 与会话句柄长期保留；
   - 释锁仅发生在 `Verthys_Lock`/销毁路径（`verthys_api.c:338-347`、`:485`、`:575`、`:638`）。
2. 落盘校验以**另一个进程外部读**同一范围：`src-tauri/src/controller/verthys_controller.rs:1622-1631`（`std::fs::File::open` + 读取 `[0,128)`）。Windows 字节范围锁是**强制锁**，外部句柄读取被锁区间必失败（`ERROR_LOCK_VIOLATION`，即日志中的 `os error 33`）。
3. 门禁判定：`src/cache/domain/verthys-flush-service.ts:783-819` —— `verthysFlush` 成功后再做磁盘校验，校验失败按 flush 失败处理；`FLUSH_MAX_RETRIES = 2`（`:82`）、退避 `100ms`（`:86`）→ 两次必然同因失败 → `persistVerthys()` 返回 `false`。
4. 运行日志复现（用户容器实测）：每次 flush 都成对出现
   `[verthys_verify_disk_persist] 磁盘验证失败: … reason=读取头部失败: 另一个程序已锁定文件的一部分`（`main_ui.log` 08:46:57 两条、08:47:20~21 四条），与「2 次尝试 × 2 次 flush」精确吻合。

**影响**

- 所有以 `persistVerthys()` 为门禁的路径在**解锁态恒判失败**（数据实际已落盘：写者逐条 `add_record` 即时 fsync，`flush` 亦成功——这是门禁不可通过，而非数据未落盘）：
  - `usePhotoParse.ts:521-531`：解析导入「持久化失败，本次导入未生效，请重试」（见 P0-2）；
  - `usePhotoImport.ts:218-224`：普通导入每次成功导入后弹出「…持久化失败，重启后可能丢失…」**误报**；
  - `usePhotoDelete.ts:110-115`、`:254-256`：每次删除弹出「删除操作持久化失败」**误报**。
- 误报同时污染故障定位：真实的落盘故障与「锁冲突」共用同一文案与同一个 `ok=false`，无法区分。

**建议修复（不改代码，仅方案）**

- 首选：把落盘校验下沉到**worker 进程内**，用会话自有句柄读取（持锁进程通过自身句柄可自由读写被锁区间）——例如新增 `verify_persist` 操作或 C API `Verthys_VerifyPersist`，由 C 层基于 `ctx->v3->f` 完成超级块/结构校验后回报。
- 次选（临时缓解）：识别 `ERROR_LOCK_VIOLATION` 并与结构失败区分——锁冲突视为「文件存在且被本会话独占打开，结构校验不适用」，记录为独立事件（不判失败），结构失败仍判失败。
- 附带：把「flush 失败」与「校验不可用」在返回值/文案上分离，杜绝误报。

### P0-2 解析导入成功路径被 P0-1 阻断：记录已落盘但永不呈现【P0 · 致命】

**证据**：`usePhotoParse.ts:515-533` 成功路径要求 `persistOk === true` 才提交列表与缓存；为 `false` 时仅提示「持久化失败，本次导入未生效，请重试」并保留 `parsedPhotos` 供重试。

**影响链**：
1. 首次解析导入：管线已成功（WAL 压缩 `success=true`、记录在库）→ 门禁失败 → 相册不显示、缓存不同步、对话框停留；
2. 用户重试：`committedHashes` 已含该批哈希 → 生产者全部去重跳过 → 「导入 0 张，去重跳过 N 张」→ **照片在库中却永远进不了相册**（用户可感知为「导入无效/解析导入彻底坏了」）；
3. 该现象与用户报告「解析并导入后正常导入功能直接失效」的第二段完全一致（重试/重导全部被跳过）。

**建议修复**：修 P0-1 后，本项自动消解；另建议：门禁失败时给出可操作出口（例如「重新校验落盘」按钮或明确提示重试不会重复导入），避免「已落盘但界面宣称未生效」的语义撕裂。

### P1-1 导入会话 begin/end 结果未校验 → 会话泄漏与级联失败【P1 · 高】

**证据**
- `importPipeline.ts:428-450`（`runImpl`）与 `:948-970`（`runParsedImpl`）：仅捕获异常，**未检查 `beginResult.ok`**；`verthys.ts:499-509` 的 `verthysImportBegin` 在失败时返回 `ok:false`（不抛异常）。
- 全部会话结束点（`:755/776/804/825/858`、`:1275/1302/1323/1356`）均为 `await verthysImportEnd(...)` 且**丢弃返回值**；`verthys.ts:607-617` 同样以 `ok` 字段返回。

**影响**
- `import_begin` 被拒（`verthys_batch_controller.rs:112-118`「已有导入会话进行中」、`:121-130`「无法确定加密库路径」）时，管线仍继续：生产者照常读文件、加密，消费者每批写入被后端拒绝（`无活跃导入会话`）→ 用户看到「部分记录写入失败」（真实原因被掩盖），且**白做全部加密开销**。
- `import_end` 失败（写者重建窗口、超时）时会话残留 → 后续导入的 `begin` 被拒 → 会话级级联失败，需重启应用恢复（无单点恢复命令）。

**建议修复**：`beginResult.ok === false` 立即中止并透出后端原因；`end` 失败重试一次并显式提示；补一个受控的「强制关闭导入会话」恢复入口（写者 `End` 幂等）。

### P1-2 解析失败后重试复用已转移缓冲区 → 误导性失败【P1 · 高】

**证据**
- `usePhotoParse.ts:375-412`：`ownsBuffer` 为真（Tauri 经 `readUserFile` → `new Uint8Array(buf)`，`verthys.ts:1284-1287`）时直接 `postMessage(..., [transferBuffer])` **转移所有权**；
- 失败路径 `:421-428` 仅提示错误，**不清空 `parseFileData`**；对话框「开始解析」按钮的禁用条件仅 `!parseFileData || !parseToken`（`PhotoAlbum.vue:343`）。

**影响**：解析失败后不重新选文件直接再次点击「解析」→ 发送 0 字节缓冲 → 报「文件格式无法识别或已损坏」（实际文件完好），用户误判容器损坏。

**建议修复**：失败时清空 `parseFileData` 并提示重新选择；或保留文件路径、重试时重新读取；或改为复制而非转移（代价：多一份内存）。

### P1-3 解析导入进行中顶部动作仍可点击 → 互斥靠后端拒绝、状态不一致【P1 · 中高】

**证据**：顶部「导入照片」按钮禁用条件为 `importing`（`PhotoAlbum.vue:58-59`），而解析导入只置 `importingParsed`（`usePhotoParse.ts:468`，对话框内的进度条状态）；解析导入共用同一 `ImportPipeline` 实例，重入由 `running` 守卫兜底（`importPipeline.ts:398-412`）。

**影响**：解析导入过程中点击「导入照片」→ 打开文件对话框 → 选中后立刻得到「已有导入任务进行中，请等待完成」。逻辑安全（不会并发写），但用户已付出选文件成本；导出/解析按钮同样未与导入互斥。

**建议修复**：顶部动作统一取「忙碌信号」= `importing || importingParsed || parsing || exporting`，禁用态配 `cursor: not-allowed`；并让解析导入同步置 `importing`（或改用单一状态源）。

### P1-4 `FileVerthys` 内联模型与 12MiB 单条上限冲突（已声明边界）【P1 · 中高】

**证据**：`FileVerthys.vue:229/393-434` 以 `CHUNK_SIZE=4MB` 分块但**把全部块内联进单条 meta**；写入侧（含本轮新增护栏）单条上限 `MAX_IPC_PAYLOAD_BYTES = 12MiB`（`constants.rs:167`、`verthys_controller.rs:1716-1729`）。

**影响**：≈9MB 以上文件导入必然被拒（「记录载荷超过单条上限 12582912 字节」）。相较修复前「超限请求直接断开 worker 协议（全链路级联失败）」，当前为**明确报错**（已收敛）；但功能边界（大文件不可导入）与 UI 前置校验缺失仍未达标，用户只在点击导入后才看到技术性错误。

**建议修复**：`FileVerthys` 迁移到照片链路已验证的外置块模型（`chunk_ids` 引用 + 块记录 + 同会话引用校验）；短期先在导入对话框按体量前置拒绝并给出友好说明。

### P2-1 预热逻辑按 v2 魔数判定 → V3 容器恒跳过，且日志误导【P2 · 中】

**证据**：`verthys_controller.rs:491-505` 校验 `header[0..4] == 'VERT'` 且 `version == 0x0002`；而本项目容器独家 V3（首帧头 `'V3RP'`）。用户日志 08:42:49 实测：`[verthys_preheat] 非 .verthys 文件格式，跳过预热` → `prefetch_done=false`。

**影响**：预热/温缓存预取对 V3 容器永不生效（性能特性形同虚设）；日志「非 .verthys 文件格式」会误导故障排查（暗示文件损坏）。

**建议修复**：改为 V3 魔数（`V3RP`）判定并实现 V3 预热路径，或删除 dead 分支与误导文案。

### P2-2 读取侧吞错：`verthysGetRecord` 一律返回 `null`【P2 · 中】

**证据**：`verthys.ts:673-685`：`if (!r.ok) return null;` —— 与「记录不存在」「记录过大（`record_too_large`）」「worker 通信失败」不可区分。

**影响**：本轮新增的单条读取护栏错误在调用方全部退化为「记录缺失」，用户/日志无法定位原因（典型：存量超限记录、worker 异常）。

**建议修复**：返回判别式结果（`{ok:false, error}`）或抛出；调用方按类分流提示。

### P2-3 删除墓碑写入吞错 → 去重锁可能静默未释放【P2 · 中】

**证据**：`verthys.ts:581-584` `verthysForgetHashes` 丢弃返回；`usePhotoDelete.ts:266-272`（批量）与 `:91-93`（单删）均 best-effort try/catch。

**影响**：墓碑失败（WAL 追加失败/无 WAL）时删除照常成功，但该文件哈希仍留在去重集合 → 之后重新导入同一文件被静默跳过（「导入 0 张」），用户与开发均无信号。

**建议修复**：检查返回值 + 一次重试；仍失败则写入审计/可见提示（「该照片去重锁未释放，重新导入可能被跳过」）。

### P2-4 四分类不变量仅在 DEV 校验【P2 · 中】

**证据**：`importPipeline.ts` 的 `assertResultInvariant` 以 `import.meta.env.DEV` 为前提（生产构建被裁剪）。

**影响**：`imported + failed + skipped + undecryptable === total` 是导入结果记账的唯一不变量；生产环境静默，一旦分类错位（重复计数/漏计）无法察觉，直接表现为用户可见的「数字对不上」。

**建议修复**：生产也输出结构化告警（含计数与 total），或暴露为观测计数。

### P2-5 落盘校验的注释与实现漂移【P2 · 中】

**证据**：`verthys.ts:429-445` 注释仍写「magic 'VERT'」「mtime 时效：文件修改时间在 15s 内（核心检测项）」；实现为 V3 `'V3RP'` 帧头 + 结构/大小校验（`verthys_controller.rs:1619-1682`），mtime 判据已退役（代码内注明）。

**影响**：注释误导后续维护者按失效判据排障（且与项目「注释不得与代码冲突」的规范相悖）。

**建议修复**：按现行实现重写该注释（仅描述可验证行为）。

### P2-6 0 块照片被误分类为「无法用当前密钥解密」【P2 · 中】

**证据**：`parse-crypto.worker.ts:121-145` 可导入性预检要求 `lm.chunkCount > 0`；`chunkCount === 0` 的照片 `meta` 恒为 `null` → `usePhotoParse` 计为 `undecryptable` 并提示「无法用当前拾光密钥解密」。

**影响**：合法但零块的容器成员被错误归因并永久不可导入（提示原因与事实不符）。

**建议修复**：`chunkCount === 0` 走可导入分支（组装无块 meta），或单独归类说明。

### P2-7 flush 重试预算与失败原因无区分【P2 · 中】

**证据**：`verthys-flush-service.ts:80-86`：`FLUSH_MAX_RETRIES = 2`、退避 100ms；失败原因只有两种弱区分文案（`verthysFlush 第 N 次失败` / `磁盘验证失败第 N 次`）。

**影响**：锁冲突类失败重试无意义（见 P0-1），却推高噪音与门禁抖动；真实 IO 故障与校验不可用同案处理。

**建议修复**：随 P0-1 一并治理：按失败类别决定重试与语义。

### P2-8 解析预览与结果对象常驻整批块密文【P2 · 中】

**证据**：`parse-crypto.worker.ts` 预览装配把 `chunkDataB64`（单张可达数 MB）与 `chunkB64List` 同时挂到预览对象；`usePhotoParse.ts` 的 `parsedPhotos` 在导入成功后被保留至 1.5s 定时清理（`:570-578`）。

**影响**：大 .venc 场景下（上限受 `PARSE_MAX_CONTAINER_BYTES` 约束）常驻内存为「容器体量 × 常数」，与加载链路清单 P1-4（已解密密文常驻）同类。

**建议修复**：导入后立即释放块数据引用（仅保留展示所需字段）；或让预览只保留缩略图与元信息。

### P2-9（交叉引用，不重复计数）记录读取回退的并发与量级

`src/cache/domain/verthys-cache-domain.ts:723-729`：>64KB 记录走 `Promise.all(fallbackIds.map(getFullRecord))` 无并发上限，导入完成后回读时可能瞬时并发大量 MB 级 IPC。该问题归口「加载链路审查清单」（P1-3/S2 族），此处仅标注与导入链路的耦合点。
