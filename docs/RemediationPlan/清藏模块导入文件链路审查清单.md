# 清藏模块「导入文件」全链路审查清单（单条写入路径 · 落盘与导出校验 · 与照片批量流水线对照）

> 审查性质：只读审查（未改动任何代码）。
> 审查对象：清藏（FileVerthys）「导入文件」全链路 = 文件选择 → 读取 → 分块加密 → 逐块 IPC 写入 → meta 引用 → 缓存/列表提交 → 落盘校验 → 列表重建 → 保存（导出）→ 删除级联。
> 审查方法：源代码走查（前端 → IPC → Rust 控制器 → worker 行协议 → C 层事务/WAL）+ 跨层常量比对 + CI/构建/部署文件核对 + 既有测试实跑（`cargo test` 41 项，见第七章）。
> 结论先行：**发现 2 项 P1（数据完整性：假成功 / 静默损坏）、7 项 P2（架构分裂、内存放大、契约悬空、吞错泄漏）、6 项 P3（注释漂移、测试与 CI 缺口）**；同时排除 6 项疑似风险（含"GC 误删清藏数据"这一高危猜测，经证据核验不成立）。第八章给出整改优先级与手工 E2E 验收清单。
> 整改状态（2026-09-28 回填）：P1-1~P2-5、P2-7、P3-1~P3-6 已按波次整改完成（P0-1 另有方案自审新增项，已随 Wave H 独立 hotfix 交付）；P2-6 已由 T-1 按 B 分支全仓收口（死分支删除 + 锚点 C 启用并注入即红）。逐项状态、波次与证据见 §十。

## 一、审查结论摘要

| 类别 | 结论 |
| --- | --- |
| 单条写入链路（读取→分块→IPC→core 事务） | 基本可用：授权闸门、名称/载荷上限、core 单条事务 + WAL fsync 均真实生效 |
| **meta 写入失败后的成功语义** | **未达标：metaId 为 null 仍计成功、仍入列表、仍提示"已加密导入"（P1-1）** |
| **保存（导出）时的块缺失处理** | **未达标：缺块被静默跳过，按声明 size 拼装，无块数/长度/哈希校验 → 静默损坏文件仍提示成功（P1-2）** |
| 断点续传 / WAL 会话 / 去重 | 未达标：模块头注释宣称"支持断点导入"，实际无会话、无 checkpoint、无去重（P2-1） |
| 传输与内存模型 | 未达标：整文件驻留 JS + 逐块 base64（全项目唯一违反"二进制直传"原则的导入路径），大文件存在 OOM/超时风险（P2-2） |
| 独立密码成本与校验 | 未达标：逐块 PBKDF2(150k)（成本随块数线性），密码错误无前置校验（P2-3） |
| 边界（0 字节文件） | 未达标：提示导入成功但列表/保存均不可用（P2-4） |
| 删除级联 | 部分达标：级联 ID 已实现，但逐条删除失败被静默吞掉（P2-5） |
| 错误契约 | 未达标：`VERTHYS_WRITE_BLOCKED` 在 Rust/worker/core 全仓无生产者，4 个模块的"格式升级"分支为死代码（P2-6） |
| 写入串行化 | 未达标：单条路径绕过单写者/WAL 通道，15s 超时窗口可造成"已提交但前端视为失败"（P2-7） |
| 测试与 CI | 未达标：清藏导入链路 0 前端单测；Rust 侧 19 项相关测试全部只覆盖照片链路；CI 锚点未覆盖单条写入路径（P3-5~P3-6） |

### 2.3 与照片（拾光）导入流水线的结构性差异

## 三、缺陷清单

### P1-1｜meta 写入失败仍计成功并提交列表（假成功 + 永久孤儿块）

- 现象：`verthysAddRecord(META)` 返回 `null`（worker 失败/名称或载荷被拒/超时）时，代码仅跳过缓存同步，**不抛错、不计失败**，条目照常入列表、`successCount++`、toast 提示"已加密导入"。
- 证据：
  - `FileVerthys.vue:451-455`：`if (metaId !== null) { addFullRecord(...) }`，无 else。
  - `FileVerthys.vue:458-468`：无条件 `newItems.push({... metaId: metaId || undefined ...}); successCount++;`。
  - `FileVerthys.vue:503`：单文件路径提示`已加密导入 <name>`。
  - 列表重建只认 meta 记录（`FileVerthys.vue:741-792`）→ 重启后该条目永久消失，而块记录已由 core 事务 COMMIT（WAL fsync，verthys_api.c:699-735）永久落盘。
  - 清藏块不进台账（`set_owner` 调用点仅 `import_writer.rs:459/:672`）→ `verthys_gc_orphan_chunks` 永不回收（`verthys_batch_controller.rs:633-634`）。
- 影响：不可恢复的"幽灵文件"：用户看到成功提示，重启后文件消失；其密文块与 extent 永久占用空间（extent 内容去重只在"再次导入同一内容"时复用，不构成回收）。
- 整改方向：`metaId === null` 即计失败并抛出；对已写入的块执行补偿删除（按 chunkIds 逐条删除）；失败提示带原因。

### P1-2｜保存（导出）时块缺失被静默跳过 → 输出损坏/截断文件却提示成功

- 现象：`doSave` 遍历 `chunkIds` 时 `if (!r) continue;` 跳过缺失块，随后按 `f.size` 开缓冲、按存在块顺序拼接，**不校验块数、不校验累计长度、不校验内容哈希**，写盘成功后提示"已保存到本地"。
- 证据：
  - `FileVerthys.vue:548-552`：缺块 `continue`。
  - `FileVerthys.vue:568-573`：`new Uint8Array(f.size)` + `fullBytes.set(chunk, offset)`，无 `offset === f.size` 断言、无 `chunks.length === totalChunks` 校验。
  - `FileVerthys.vue:587-589`：写入成功即 toast，成功语义与数据正确性解耦。
  - meta 无内容哈希/总长校验字段（`FileVerthys.vue:439-449`），读侧无完整性依据。
- 影响：任何触发块缺失的场景（部分失败导入、异常删除、容器局部损坏）→ 用户导出的是**中段错位/尾段补零**的文件，且被提示成功；这是最易被忽视的数据损坏路径。
- 整改方向：缺块立即失败并给出明确文案；拼接后强校验（块数 + 累计长度 + 可选整体哈希）；meta 增补 `sha256`/`sizeCheck` 字段并在读侧校验。

### P2-1｜无 WAL 会话、无断点续传、无去重：与照片流水线双架构分裂

- 现象与证据：
  - `FileVerthys.vue:5` 注释宣称"支持断点导入"，但 `startImport`（:374-477）每次从第 0 块开始，全链路无 `verthys_import_begin/checkpoint/import_end` 调用（全仓检索确认这些命令仅照片链路使用）。
  - 照片链路：`verthys.ts:511-560` 五命令封装 + WAL 续传 + `committed_hashes` 去重；清藏链路全部缺席。
  - 块归属：照片上传即 `set_owner(id, 0)` 记账（`import_writer.rs:459/:672`），meta 入库改写 owner；清藏块从不入账。
- 影响：
  1. 中断/失败后已提交块成为**持久孤儿**（core 每事务 fsync，崩溃即持久），无回收路径（GC 只读台账）→ 空间只增不减；
  2. 崩溃/强退后无续传：重试从头写入，产生重复块**记录**（extent 内容去重可避免 payload 重复，但索引条目与 LID 不复用，条目数持续增长）；
  3. 双架构并存 → 同一容器下两套写入语义、两套回收语义，维护与审计成本翻倍。
- 整改方向（首选）：清藏接入导入会话与批量 API（`add_chunk_batch` 天然适合外置块模型）；或退而求其次：单条路径也登记 ChunkLedger（owner=0 → meta 成功后改写），让 GC 覆盖。

### P2-2｜整文件内存驻留 + 逐块 base64：全项目唯一未遵守"二进制直传"原则的导入路径

- 证据：
  - `readUserFile` 一次性把整文件读入 JS 堆（上限 2GiB，`file_controller.rs:69`；Rust 侧同样整文件 `Vec` 聚合，:818-831）。
  - 每块 `bytesToBase64(chunkData)`（`FileVerthys.vue:421`）→ JSON 单行 ≥5.33MiB/块（4MiB→base64 = 5,592,408B，未越 12MiB 单条上限，但放大 1.33×）。
  - 对照原则与既有能力：`verthys.ts:2-22` 明示"文件二进制数据经 raw IPC 直传，零 base64"；照片链路批量 ≤8 块/11MiB（`photo_budget.rs:52-58`）；导出侧已有流式 `write_user_file_stream`（`file_controller.rs` 流式三命令）而导入侧无对应流式读。
- 影响：1GiB 文件 = 256 次 base64 编解码 + 256 次 IPC 往返；峰值内存 ≈ 文件全量 + 块 base64 + worker/core 副本；叠加单条 15s 超时（`state/mod.rs:444-451`），慢盘大文件易触发超时、界面卡顿甚至 OOM。
- 附带安全一致性：`fileBytes`/`chunkBytes` 导入后未清零（对照拾光 `fullBytes.fill(0)` 的既定标准），明文常驻 JS 堆直至 GC。
- 整改方向：分块 raw IPC 读取（复用 `PB_WRITE_FILE_CHUNK_BYTES` 口径）+ 批量写入；导入结束清零明文缓冲。

### P2-3｜独立密码逐块 PBKDF2，成本线性增长；密码错误无前置校验

- 证据：`PBKDF2_ITER = 150000`（`crypto_const.ts:28`）；`encryptPasswordField` 每块新随机 salt 并重新派生（`crypto.ts:1404-1416`）；导入侧每块调用（`FileVerthys.vue:414-418`）；保存侧逐块解密（:559-567），错误仅提示"密码错误或数据已损坏"（:533-535）。
- 影响：1GiB = 256 次 KDF（导入 + 导出各一遍，合计 512 次）；密码错误要到"保存到本地"阶段才暴露，且无法区分"密码错"与"数据损坏"。
- 整改方向：文件级密钥派生一次 + 每块唯一 IV/子密钥；导入时写入一个校验块（AEAD 认证标签），保存入口先验证密码。

### P2-4｜0 字节文件边界：提示成功但列表/保存均不可用

- 证据：`totalChunks = Math.ceil(0 / 4MiB) = 0` → `chunkIds = []`（`FileVerthys.vue:397/:443`）；列表重建条件为 `chunkIds.length > 0`（:775-789）→ 重启后永不显示；`doSave` 分支直接报"无数据可保存"（:553-556）。
- 影响：假成功 + 功能不可用（会话内可见、重启消失、无法导出）。
- 整改方向：列表接纳 `chunkIds` 为空的合法 meta（以 metaId 存在为准）；保存路径支持零块空文件。

### P2-5｜删除级联静默吞错 → UI 已删、后端残留（或重启复活）

- 证据：`FileVerthys.vue:639-645` 逐条删除时 `catch (e) { if (e.message === "VERTHYS_WRITE_BLOCKED") throw e; }`——其余错误全部吞掉；`:650-653` 仅校验落盘返回值；而 UI 移除与"已删除"toast 在 IPC 之前完成（:612-614）。
- 影响：部分删除失败（worker 超时、锁冲突等）→ 后端残留块记录（无台账、GC 不覆盖）；若 meta 删除失败，重启后条目"复活"，与注释声称已根治的目标相悖。
- 整改方向：聚合逐条结果，任一失败即回滚 UI 并明确报错；失败 ID 留待重试。

### P2-6｜悬空错误契约：`VERTHYS_WRITE_BLOCKED` 无生产者

- 证据：全仓（排除构建产物）检索该字符串，仅存在于前端消费点（`FileVerthys.vue:470/:643/:656`、`AccountVerthys.vue`、`CertManager.vue`、照片链路共 20+ 处）；Rust / worker / core 无任何生产点；错误包装器（`verthys_error.ts:66-91`）也不合成该串。
- 影响：4 个模块的"当前加密库格式需要升级"提示分支为死代码。两种可能均需处理：(a) 后端确有写入门但以其它码/文案上抛 → 用户拿不到升级指引；(b) 写入门缺失 → 旧格式写入未被阻断（需业务确认预期）。
- 整改方向：定义结构化 `error_code`（如 `E_WRITE_BLOCKED`）由后端稳定上抛、前端按码映射；或删除死分支。

### P2-7｜单条写入绕过单写者/WAL，超时窗口可产生"已提交但前端视为失败"

- 证据：`verthys_add_record` 直接 `state.send`（`verthys_controller.rs:1610`；默认 15s，`state/mod.rs:444-451`），不经过 import_writer 的单写者串行与 WAL pending/committed 记账。
- 影响：慢盘/worker 重建时，单条记录可能已在 core 侧 COMMIT（持久），但前端因超时计失败 → 重复导入产生重复条目与孤儿块；且无 WAL 去重兜底（照片链路有 committed_hashes）。
- 整改方向：统一经单写者通道；或为单条写入引入幂等键（name+hash）与会话记账。

## 四、已核验排除项（防误判，含高危猜测的证伪）

| 疑似风险 | 结论 | 依据 |
| --- | --- | --- |
| 孤儿块 GC 会误删清藏分块数据（灾难级猜测） | **不成立** | GC 只删除「台账」中 `owner==0` 的 id（`verthys_chunks.rs:57-66`、`verthys_batch_controller.rs:633-634`）；清藏块从不入账（`set_owner` 仅 `import_writer.rs:459/:672`）。代价是 P2-1 的"泄漏"而非"误删" |
| 4MiB 块 base64 越 12MiB 单条上限 | **不成立** | 4MiB → base64 5,592,408B < `PB_IPC_MAX_PAYLOAD_BYTES` 12,582,912（`photo_budget.rs:49`）；worker 单行上限 16MiB（`:64-67`） |

## 八、整改优先级与验收标准

### 8.1 建议顺序

| 顺序 | 项 | 目标 |
| --- | --- | --- |
| 1 | P1-1 | meta 失败即失败：抛错 + 补偿删除 + 明确文案 |
| 2 | P1-2 | 保存强校验：缺块即失败；块数/长度/（新增）哈希全量校验 |
| 3 | P2-5 / P2-4 | 删除失败可见可重试；0 字节文件全路径支持 |
| 4 | P2-1 | 架构收敛：清藏接入导入会话 + 批量 API + 台账登记 |
| 5 | P2-6 / P2-7 | 错误码契约落地；单条写入串行化或幂等 |
| 6 | P2-3 / P2-2 | 密钥派生层级优化；流式读取 + 明文清零 |
| 7 | P3-* | 注释/字段/交互/测试/CI 锚点补齐 |

### 8.2 每项验收标准（可直接转测试用例）

- **P1-1**：mock `verthysAddRecord` 对 meta 返回 null → 断言：`failCount=1`、列表无该条目、无成功 toast、已写入块被补偿删除（或明确留痕）。
- **P1-2**：构造 `chunkIds=[1,3]`（缺中间块）→ 断言：保存操作失败且提示可读原因；另测 `chunks.length !== totalChunks` 与 `offset !== size` 两分支。
- **P2-4**：导入 0 字节文件 → 断言：可保存为 0 字节文件；重启后条目仍在列表。
- **P2-5**：mock 某条 `verthysDeleteRecord` 抛普通错误 → 断言：UI 回滚 + 错误提示 + 失败 ID 可重试；不出现"已删除"假提示。
- **P2-1**：中断导入（杀 worker）→ 重启 → 断言：孤儿块被回收（GC 返回值 ≥ 已写块数）或续传跳过已提交块。
- **P2-2**：1GiB 文件导入内存峰值 ≤ 阈值（如 512MB）且无 15s 超时；导入后明文缓冲清零（可注入断言）。
- **P2-6**：后端写入门用例：旧格式容器写入 → 断言返回结构化 `E_WRITE_BLOCKED` 且前端展示升级指引。

### 8.3 手工 E2E 清单（需交互式桌面，本次未执行）

1. 0 字节 / 51MB / 1GB / 2.1GB 文件导入 → 观察：成功语义、失败文案、内存峰值、超时。
2. 导入中途任务管理器结束 `verthys-worker` → 重试导入 → 对比 GC 返回值与容器体积。
3. 导入中途强制结束主进程 → 重启 → 检查列表一致性与孤儿块。
4. 独立密码：错误密码保存（文案区分）/ 正确密码保存（原文件逐字节比对）。
5. 同一文件重复导入 → 观察条目数与 extent 空间（内容去重生效范围）。
6. 批量导入 200 个文件（混合大小/含失败项）→ 失败计数与失败原因可见性。
