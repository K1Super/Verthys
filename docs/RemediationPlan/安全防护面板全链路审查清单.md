## 一、审查结论摘要

用户报告的问题（拖拽端点在退出面板后重进不指示当前状态、直接回中位）**已定位到确定根因**：滑块的视觉位置由组件 DOM 直写 CSS 变量 `--pos/--posw` 驱动，而唯一入口的 `watch(..., { immediate: true })` 在组件挂载**之前**同步执行（`trackEl` 仍为 `null`，写入被静默跳过），挂载后没有任何补写钩子；重进面板时模型值与预设权威档位一致（无变化），watcher 不再触发，CSS 回落默认值 `50`（中位）。这与用户观察完全吻合，且与后端档位状态无关——是前端「单一事实源被 DOM 直写架构绕开且缺少挂载期播种」的结构缺陷。

功能生效性审查结论（详见第四节）：**不可接受**。UI 展示的 12 项特性中，仅 `anti_inject`、`memory_guard` 由档位真实驱动；`anti_debug` 的档位标志在 C 层无任何消费者（性能档"关闭反调试"不成立）；`integrity_check`、`shadow_sleep`、`module_patrol`、`usb_clone_detect`、`trace_cleanup` 五项**不存在任何执行路径**（展示即全部）；且 `shadow_sleep` 在 SECURE/PERFORMANCE 两档与 C 层真实行为**方向相反**。

持久化审查结论（详见第五节）：受信文件 `tmp + rename` 的原子提交方向正确，但缺少 `fsync` 耐久性保证、缺少并发写互斥、缺少切档回读校验；更关键的是**信任链在解锁收尾处发生反转**——用前端本地缓存值（localStorage）回写"权威"文件，并与恢复链产生无仲裁竞态，可导致静默降级。

C 层实现结论（详见第六节）：双缓冲原子发布设计正确，但被「缓存指针读者」击穿（`anti_debug_v2` 永久持有旧缓冲指针，二次换档即指向被清零缓冲，存在全零配置读取窗口）；C 运行时预设**没有任何启动期/解锁期应用路径**，SECURE 档全部强化项（激进反调试、挂起锁定等）在解锁窗口不生效；档位结构体 20 个字段中 11 个只写不读。

缺陷统计：**P0 致命 5 项，P1 高 7 项，P2 中 7 项，P3 低 4 项，共 23 项**。

```

      ▼

      ▼

恢复链：解锁 → globalKeyReady=true
  ├─ SecurityCenter.watch → restoreSecurityPreset() → security_load_preset_state() → applySecurityPreset(后端码)
  └─ global-verthys.verifyGlobalKey 收尾 → applySecurityPreset(keyState.securityPreset.value)   ← 本地缓存值，无仲裁
```

关键事实源梳理：

| 数据 | 事实源 | 副本 | 备注 |
| --- | --- | --- | --- |
| 当前档位（运行态） | `keyState.securityPreset`（内存 ref） | localStorage `verthys_security_preset` | 副本可被本地篡改 |

## 三、用户报告缺陷专项（P0-1）：拖拽端点重进面板回中位

### 3.1 症状

在三档（性能/平衡/安全）切换面板中拖动游标至「性能」或「安全」并生效后，退出面板（切模块或退回引导区）再进入：模式仍是原档位（后端与状态均正确），但游标天平与潮汐亮层指示**回到 50%（中位）**，直到用户再次拖动才恢复正确。

### 3.2 根因（确定）

`SecurityDashboard.vue:547-556`：

- 滑块视觉位置由 `writePosToDom / writeLitPos` 直写 CSS 变量 `--pos / --posw`（模板中 `bs-track` 不绑定任何 Vue style，见 `SecurityDashboard.vue:160-167`）；
- 唯一写入驱动是 `watch(orbitSliderPos, ..., { immediate: true })`。`immediate: true` 的回调在 `<script setup>` 执行期**同步**触发，此时组件尚未挂载，`trackEl.value === null`，`writePosToDom`（`:515-519`）与 `writeLitPos`（`:532-542`）**直接 return**，写入被静默丢弃；
- 组件挂载后**没有任何补写钩子**（文件内仅有 `onBeforeUnmount`，`SecurityDashboard.vue:706-709`，无 `onMounted`）；
- `tiltLoop` 仅在 `dragging === true` 时写 `--pos`（`:576-593`），静止态不写。

重进面板时的实际序列：`usePreset` 在 setup 期已依据 `securityPresetRef` 把 `orbitSliderPos` 播种为锚点位置（`usePreset.ts:131-136`，例如 SECURE → 100）→ `SecurityDashboard` setup 期 immediate watch 因 `trackEl=null` 空转 → 挂载后 `loadPresetConfig → syncOrbitFromPresetRef`（`usePreset.ts:326-334`）写入**同值** 100，ref 无变化、watcher 不触发 → `--pos` 从未被写过一次。CSS 回落：

- `dashboard.css:372`：`transform: translateX(calc(var(--pos, 50) * 1cqw))` → 游标落 50%；
- `dashboard.css:299`：`clip-path: inset(0 calc(100% - var(--posw, 50%)) 0 0)` → 亮层只点亮一半（中位）。

### 3.3 同类次生症状

- `activeAnchorIdx` 初值为 `ref(1)`（`usePreset.ts:147`），setup 期只播种了 `orbitSliderPos` 未播种它；重进面板瞬间"当前档"高亮在「平衡」，需等异步 `loadPresetConfig` 才收敛；
- CUSTOM(3) 档下 `syncOrbitFromPresetRef` 直接 return（`usePreset.ts:328`），锚点"当前"高亮与游标位置停留在上一标准档，与"自定义"模式语义不符。

### 3.4 整改方向

1. 写入补齐：在 `onMounted` 中显式 `writePosToDom/writeLitPos(orbitSliderPos.value, false)` 播种一次（**唯一可靠方案**）；同时将 `activeAnchorIdx` 初值改为按 `securityPresetRef` 推导。
   注意：`watch` 增加 `flush: 'post'` **不足以**修正此缺陷——Vue 3.5.39 的 `runtime-core.cjs.js:868`（`runsImmediately = cb && immediate || …`）与 `@vue/reactivity.cjs.js:1957-1962`（`immediate` 分支直接同步调用 `job(true)`，绕过任何调度器）证明 immediate 回调恒在 watch 创建时同步执行、与 flush 选项无关。
2. 架构层根治：直写 DOM 的旁路必须与「单一事实源」建立**挂载期播种 + 变更期同步**双通道契约，禁止仅依赖「变更触发」单向同步；建议把 `--pos/--posw` 播种封装进同一 `syncVisualState(pos)` 入口，由 `onMounted` 与 watch 共用。

## 四、功能生效性逐项审查（12 特性 × 真实执行路径）

C 层档位结构体共 20 字段（`security_preset.h:20-56`），与 UI/Rust 的 12 项 `PresetFeatures` **非一一对应**。逐字段追查消费点结论：

C 层「只写不读」字段（全仓检索无任何读取方）：`lazy_integrity`、`distributed_anchors`、`resource_encrypt`、`file_exclusive_lock`、`usb_guard`、`usb_shadow_sleep_min`、`log_encrypted`、`session_lock_on_system_lock`、`session_lock_on_display_off`、`export_reauth`、`remote_control_block`、`anti_debug`、`trace_cleanup`，以及仅由 `anti_debug_v2_get_kdf_iters()` 读取而**该函数全仓无调用者**的 `kdf_iters_normal/punish`。

C 层真实消费字段：`memory_lock`（`memory_guard.c:259-262`）、`anti_dump`（`memory_guard.c:321-324, 563-564`）、`anti_inject`（`anti_inject.c:458-459` 等多处）、`anti_debug_aggressive`（`anti_debug_v2.c:194`，经缓存指针——本身是缺陷，见 P0-2）。

| # | 特性（UI 标签） | 档位开关是否有执行路径 | 结论 |
| --- | --- | --- | --- |
| 1 | anti_debug 调试检测 | 检测逻辑**无条件**运行（`anti_debug_v2.c:164-201`），`cfg->anti_debug` 无消费者；仅 SECURE 的激进退出经缓存指针读取 | **档位开关无效**：性能档"关闭反调试"不成立 |
| 2 | anti_inject 注入拦截 | `anti_inject.c` 多处按 `cfg->anti_inject` 门控 | 生效（唯一无瑕项） |
| 3 | integrity_check 完整校验 | C 档位字段（lazy_integrity/distributed_anchors）无消费者；`Verthys_VerifyIntegrity` 仅测试引用，无 worker/前端入口 | **不生效**（展示即全部） |
| 4 | memory_guard 内存保护 | memory_lock / anti_dump 双消费点 | 生效 |
| 5 | key_separation 密钥分立 | CNG 内核托管为架构恒开能力，非档位驱动 | 生效（恒开，与 LOCKED 语义一致） |
| 6 | emergency_response 紧急熔断 | `emergency.c:224-231`：三档恒为 1、无条件启用 | 生效（恒开） |
| 7 | session_lock_on_idle 空闲锁定 | 前端会话计时器按档位应用（`security-session.ts:135`） | 0/1/2 生效；**CUSTOM 未应用**（见 P1-6） |
| 8 | shadow_sleep 影子休眠 | 前端 `securityUsbShadowSleep` 等包装器**全仓无调用者**；C 字段无消费者；Rust `ShadowSleep` 无调用者 | **不生效**，且两档矩阵与 C 相反（见 P0-3） |
| 9 | module_patrol 模块巡检 | `security_module_patrol` 命令存在，前端包装器无调用者、无调度 | **不生效**（无周期执行） |

| 11 | usb_clone_detect 克隆检测 | 前端 USB 包装器无调用者；预设无驱动 | **不生效** |
| 12 | trace_cleanup 痕迹清理 | C 字段无消费者；前端无调用者 | **不生效** |

结论：12 项中 6 项无任何执行路径（3/8/9/11/12 及 1 的档位语义），UI 的能力状态栏（`cap-board`）与特性谱线（`bs-spectra`）展示的是**配置意图而非真实能力**——违反"禁止恒等伪装计数"的自我约定（`SecurityDashboard.vue:263-265` 注释）。

## 五、持久化实现审查

### 5.1 受信文件（Rust）

- 路径：`<verthys_path>.preset.json`，与状态文件同域（`preset_persistence.rs:33-35`）；
- 原子提交：`tmp + rename`（`:64-82`），方向正确；
- 校验：`code ∈ 0..=3`、`code=3` 必须携带自定义特性（`:54-59`），损坏不静默降级（返回 Err）；
- 回滚：切档失败时按旧文件原样恢复，旧文件不存在则删除（`preset.rs:315-337`）。

缺陷：

- **无耐久性保证**：写临时文件与 rename 前后均无 `File::sync_all`/目录刷盘，"原子"仅覆盖崩溃时序可见性，不覆盖掉电持久性；
- **无并发写互斥**：写序列未持锁，两次并发 `security_apply_preset` 可交错写同一 `.tmp` → rename 出混合内容；`last_applied_preset` 的 Mutex 仅保护内存字段；
- **无回读校验**：apply 成功后返回 `preset_config_static(code)`（Rust 硬编码表，`preset.rs:297-308`），从不查询 C 层实际生效配置；worker `switch_preset` 的 ack 仅确认切换调用返回 OK（`dispatch.rs:355-364`），不代表各子系统已按新配置运行；
- **信任链反转（P0-5）**：解锁收尾 `global-verthys.ts:1327-1331` 以 `keyState.securityPreset.value`（源自 localStorage 的本地缓存）调用 apply——该调用会**落盘覆盖受信文件**；与 `SecurityCenter.vue:530-540` 的恢复链（读受信文件）并发，且此路径不递增 `presetEpoch`（仲裁仅覆盖用户显式切换，`usePreset.ts:302/354`），最终落盘值取决于两条异步链的时序，可静默降级；
- **迁移后缓存空洞**：`restoreSecurityPreset` 迁移分支在 apply 之后 `removeItem` 两个键（`security-session.ts:211-213`），若用户此后未显式切档，下次启动 `loadSecurityPreset()` 读到空 → `keyState.securityPreset` 初始为 0（`key_state.ts:115,174-185`）→ 解锁收尾再次以 0 覆盖受信文件（确定性降级路径）；
- 恢复失败仅 `console.warn`（`SecurityCenter.vue:539`）：安全关键配置未恢复对用户完全不可见（fail-open 不可观测）。

### 5.2 本地缓存（localStorage）

- `loadSecurityPreset` 有 0~3 整数校验（`key_state.ts:174-185`），但 localStorage 本身可被本地进程篡改，而它现在是"可回写权威"的输入源（P0-5 的放大器）；缓存与受信文件之间没有任何版本/世代戳（epoch/哈希）用于拒绝过期回写；
- `saveCustomFeatures` 对锁定特性强制 true（`key_state.ts:215-223`）——前端防线合理，但 CUSTOM 的自定义特性除 `highSec` 两项外无任何执行路径（第四节 #8/9/11/12），自定义落盘长期看是"死数据"。

### 5.3 启动恢复链

```
后端有值 → applySecurityPreset(后端码)（正确方向）
后端无值 + localStorage 有值 → 迁移：apply 本地 → 清空本地键
两端均无 → 保存默认 0 + apply(0)
```

- 竞态仲裁仅防"用户在恢复期间显式切换"（epoch 校验，`security-session.ts:184-198`），**未防解锁收尾的 apply（P0-5）**；
- C 运行时预设无启动期应用路径（见第六节 P0-4）：受信文件虽在，但 C 层直到解锁后前端 apply 才知晓档位。

## 六、C 层实现审查

### 6.1 双缓冲被缓存指针击穿（P0-2）

- 设计（`security_preset.c:135-163`）：非活跃缓冲清零后填充，`InterlockedExchangePointer` 原子发布；注释声明"旧缓冲继续服务已捕获旧指针的读者，直至其成为下一次切换的非活跃缓冲被清零复用"——该不变式**仅对"读取后立即释放指针"的读者成立**；
- 反例：`anti_debug_v2.c:145` 在 init 时把 `s_config = security_get_config()` **永久缓存**，其后 `:194`（激进退出判定）与 `:208-219`（KDF 迭代）均经该缓存指针读取。二次换档时该缓冲成为非活跃缓冲并被 `verthys_secure_zero` 清零——**并发读者可观测到全零配置**（`anti_debug_aggressive=0`、`kdf_iters_*=0`），且日常状态下反调试子系统读取的是"恰好占用该缓冲槽的档位"，而非当前活跃档位 → 换档不跟随 + 潜在的防护瞬时归零窗口，正是该双缓冲要根治的 TOCTOU 缺陷本身。
- 另一重隐患：仅 2 个缓冲，若短时间内连续两次切换且首次切换的读者仍在读，ABA 复归后同一缓冲会被二次清零（概率低但存在）。

### 6.2 运行时预设无启动期应用（P0-4）

- `security_preset_init` 全仓唯一调用点是自身的兜底分支（`security_preset.c:113,143`），即**任何进程启动后 C 层都以 BALANCED 惰性初始化**；
- 创建容器时 `verthys_api_v3_create(ctx, path, pw, len, preset)` 只把档位写入容器上下文/TLV（`verthys_api.c:554-556, 591-628`），**不调用** `security_preset_init/switch`；容器头档位仅影响 `verthys_v3_warmcache_disabled_by_preset`；
- 解锁路径同样不按容器档位初始化运行时配置；
- 结果：SECURE 档的用户，其解锁窗口（口令输入、Argon2id 派生、密钥装载）运行在 BALANCED 配置下——`anti_debug_aggressive`、挂起即锁等高安全行为在此窗口全部缺席；`Verthys_SwitchSecurityPreset` 是纯内存切换（内存-only），且直到前端解锁收尾才被调用。

### 6.3 线程安全与健壮性

- `s_initialized` 非原子、init 与 switch 的首次并发入口存在重复初始化竞态（低危，实测影响小）；
- `security_get_config()` 惰性 init 分支存在"publish 后置 initialized"顺序，读者可拿到已发布缓冲（安全方向正确）；
- 越界档位：switch/init 均返回 -1（`security_preset.c:127,155`），FFI 层再映射为 `VERTHYS_ERR_INVALID`（`verthys_api.c:1048`），链路闭环正确；
- `security_preset_name` 全仓无调用者（死接口）。

## 八、设计不合规项汇总（对照顶级实现规则）

1. **单一事实源被旁路架空**：滑块视觉事实源存在两套（Vue model 与 DOM CSS 变量），且同步契约只有"变更触发"单向通道——顶级实现要求"播种 + 变更 + 失效重同步"三态闭环（P0-1/P1-10/P2-14）。
2. **持久化权威可被缓存回写**：本地缓存（可篡改、可过期）不得作为权威文件的写输入；权威校验必须先读后写、带世代戳拒绝过期回写（P0-5）。
3. **失败不可观测**：安全关键配置的恢复/切档失败只能 `console.warn`，与"fail-closed / 可见报告"原则相悖（P1-11/P2-17）。
4. **展示与能力脱钩**：UI 开关必须一一映射真实执行路径，禁止"配置意图"冒充"能力状态"（P0-3/P1-12）。
5. **跨语言矩阵双源**：三档矩阵同时存在于 TS/Rust/C 三处且无一致性校验，任何单侧修改都会静默漂移（P0-3/P1-8）。
6. **并发与耐久细节缺失**：受信文件写路径无 fsync、无互斥；C 双缓冲对"长持有读者"无保护（P1-7/P0-2）。
7. **生命周期时机错误**：运行时防护档位应在解锁前即按受信来源生效，而非解锁后由 UI 补发（P0-4）。
8. **死代码与死接口**：多处返回但无人消费的状态、无调用者的包装器/命令/函数，违反"无冗余 API 面"（P2-14/P1-12/P3-23）。
