> 状态：**已全量实施**（Batch 1→4 落地、四批次门禁全绿，2026-09-23）；Batch 3 的 α 决策点未实施（待设计评审）；Batch 5 未触发
> 时间：2026-09-23
> 上游结论：H1（透明窗口 + 强制 GPU 光栅化 → WebView2 GPU 进程挂起）为**主根因**；S1~S5（交互瞬间渲染爆发）为**放大因素**；三档切换组件逻辑**已排除**（全链路有界、IPC 异步、后端日志健康）

## 一、修复总策略：风险阶梯 + 三层架构不动摇 + 设计语言零破坏

| 原则 | 内容 | 不可违反 |
|---|---|---|
| P-1 风险阶梯 | 先摘除主根因（配置层，单参数字符串变更），独立验收通过后再动放大因素——每批次保持**单一因果归因**，杜绝"大混合改动后无法定位回归" | 不得把 P0 与渲染层重构合并提交 |
| P-2 三层解耦 | 项目既有信号层（useGlobalIdleScheduler）→ 感知层（frame-gate 单点配置）→ 表现层（各引擎）的架构是本次修复的**载体**：唤醒策略只改信号层，档位参数只改 frame-gate，表现层仅在 Batch 3 做等价替换 | 不得在组件内散落硬编码档位/唤醒参数 |
| P-3 设计语言 | 视觉替换必须**语义等价或升级**（潮汐亮层＝能量进程语义、氛围色＝模式语言），仅用高级白/灰/黑体系 | 禁止引入新视觉元素或降级为简化样式 |
| P-4 可回滚 | 每批次回滚代价 ≤ 单文件/单配置恢复；每批次自带验收矩阵与门禁 | 全部门禁（vue-tsc / vitest / build / src-tauri / worker / run_ci）必须全绿 |
| P-5 注释规范 | 新增/修改注释仅描述当前代码可验证的用途、行为与约束 | 无外部文档引用与编号，不编造无法从代码确定的内容 |

## 三、Batch 1 —— 摘除 GPU 强制参数（主根因根治，最高优先）

### 3.1 变更点

位置：`verthys-tauri/src-tauri/tauri.conf.json`（L25 `additionalBrowserArgs`）

**现值：**
```
--enable-gpu-rasterization --enable-zero-copy --ignore-gpu-blocklist --js-flags="--max-old-space-size=1024 --expose-gc"
```

**目标值（本批次）：**
```
--js-flags="--max-old-space-size=1024 --expose-gc"
```

即移除 `--enable-gpu-rasterization`、`--enable-zero-copy`、`--ignore-gpu-blocklist` 三项；`transparent: true`、`decorations: false` 与本批次的 js-flags **保持不变**（视觉零变化，GC 治理归属 Batch 4）。

### 3.2 设计推理

- 主根因机制：透明分层窗口 + 强制 GPU 光栅化 + 无视阻断列表，在双显卡机型（RTX 3050 Laptop + Iris Xe）上把 WebView2 GPU 进程推入不稳定运行域；交互尖峰到达时 GPU 进程挂起（Crashpad 空、无 TDR 事件，均为 stall 而非 crash 的证据）。
- 移除三项参数后，WebView2 回归**自身稳定合成决策路径**：能力达标的适配器仍会自动启用 GPU 光栅化（不损失有条件下的性能）；阻断列表恢复生效，不兼容的驱动/适配器组合自动降级到稳定路径——**把"命中不稳定组合"的决定权从强制配置交还给经过验证的自适应逻辑**。
- `--enable-zero-copy` 在分层窗口下收益未知、风险明确，属同等摘除。

### 3.3 方案对比（为什么选"保透明去参数"）

| 方案 | 内容 | 评定 |
|---|---|---|
| **A（选定）** | 保透明窗口，仅移除三个强制 GPU 参数 | 外观零变化；直击"强制参数 × 双显卡"不稳定因；成本＝一行配置；回滚＝恢复字符串 |
| B（阶梯二，兜底） | 若 A 验收失败，改不透明窗口 + 窗内自绘背景 | Windows 11 不透明窗口自动获得系统圆角与阴影；但需将现有透明视觉（自绘圆角/边角透空）迁移为窗内绘制，成本中高，仅作 fallback |
| C（否决） | 强制全局软件渲染 | 4600 粒子 WebGL + 双 Canvas 引擎无法在软件光栅化下支撑，性能崩坏 |

**执行策略：先落 A 并跑完整验收矩阵；仅当 A 验收项 1~3 仍未通过时，启动 B 作为阶梯二（B 需另行评审视觉迁移细节）。**

### 3.4 本批次验收（必须全过）

1. 冷启动 → 解锁 → 进入安全防护分区 → 三档锚点各点击 5 次：不卡、不冻、档位标签即时更新。
2. 滑块 0→100 全程来回 10 次（含快速甩动）：无 100ms 以上停帧，无全窗口冻结。
3. 切档瞬间点击"立即锁定"与窗口关闭按钮：**立即响应**（原卡死时二者必死）。
4. 10 分钟静置观察（含失焦/再聚焦、最小化/恢复）：GPU 进程存活（任务管理器 `msedgewebview2.exe` GPU 子进程无消失/挂起）。
5. 复核 Crashpad 目录无新增（本方案预期不再产生 stall 特征）与系统事件日志无新增 TDR。
6. 全部门禁绿色。

### 3.5 回滚

恢复 `additionalBrowserArgs` 原字符串，验收项 1~3 回归基线对比即可判定。

## 四、Batch 2 —— 交互唤醒分级 + 氛围过渡门控（信号层治理 S1/S3）

### 4.1 B2-1：唤醒分级塑形（改信号层，不动档位参数）

位置：`verthys-tauri/src/composables/useGlobalIdleScheduler.ts`（`onUserActivity`、`ACTIVITY_EVENTS` 装配）

现状问题：`pointerdown/pointermove` 等事件**立即**置 `active`（60fps、DPR 满配）；点击/滑动的第一毫秒，全屏 WebGL 从 idle 5fps 瞬间满载，GPU 尖峰与用户操作同帧叠加（S1）。

变更设计：

- 引入**两段唤醒**：指针类事件（pointerdown/pointermove/wheel/touchstart）→ 先置 `settling`（30fps、DPR 1.5，填充率约为满配的 56%）；持续活动满 400ms 后经一次性定时器升 `active`。
- `keydown` 维持即时 `active`（键盘可达性语义要求即时满响应，且键盘路径无拖拽尖峰）。
- **直通豁免不变**：`forceResetIdle`（引擎转场/渡越等显式满帧需求）绕过分级直达 `active`——既有调用方（ParticleBackground 渡越、枢纽引擎激活等）行为零变化。
- 分级状态复用现有 `scheduleTransitions` 的定时器体系，新增常量集中收口（唤醒升温时长、事件分级映射表），不得散落魔法数。
- 帧门控/DPR/密度表（frame-gate.ts）**不变**——settling 档已具备 30fps/1.5DPR 完整语义，本变更只是让唤醒路径"先落到 settling 再升温"，零新增档位。

效果：点击/滑动的首 400ms GPU 负载仅为原尖峰的约 56%（帧率减半叠加填充率下降），拆穿"S1 尖峰与 S2~S4 同帧叠加"的组合链。

### 4.2 B2-2：氛围类切换迟滞与过渡门控（表现层门控 S3）

位置：`usePreset.ts`（`presetAmbienceMode` computed）、`dashboard.css`（`.ambience-glow`）

变更设计：

- **阈值迟滞**：`presetAmbienceMode` 的 25/75 切换阈值增加 ±6 迟滞带（进入带 25/75，退出带 19/81），消除滑块在阈值附近来回抖动引发的类切换风暴。
- **拖拽冻结**：`SecurityDashboard.vue` 拖拽态（`.is-dragging`）期间禁用 `.ambience-glow` 的 `transition: background 0.8s`（与既有 `.is-dragging .bs-survey--lit { transition: none }` 同手法），氛围色更新退化为瞬时静态切换；拖拽结束（松手吸附成功后）恢复过渡并以目标类完成 0.8s 渐变——**切档成功瞬间的正常仪式感完整保留**。
- 行为不变量：`flow--${presetAmbienceMode}` 走线状态类与文字语义随类同步，不受迟滞影响（迟滞仅作用于类切换频率，不改变类与档位的映射正确性——最终稳定态与后端权威档位一致）。

### 4.3 本批次验收

- 复用 Batch 1 验收项 1~3；追加：拖拽悬停在 25/75 阈值附近往复 20 次，类切换次数显著下降、无闪烁；松手后氛围色以 0.8s 渐变完成过渡。
- 观察项（**不改代码**，用于后续决策）：B2-1 落地后若 S4（120ms 节流联动 patch）仍可感知掉帧，再评估将双星数值等高频 patch 从 model 联动中拆出——本次不实施，避免过度工程。

### 4.4 回滚

恢复调度器即时置 active 行为；删除迟滞与 `.is-dragging` 门控两处选择器。

## 五、Batch 3 —— 拖拽逐帧 clip-path 等价替换（表现层，S2）

### 5.1 现状与问题

`SecurityDashboard.vue` 拖拽期每帧写入 `--posw` → `dashboard.css` L290 `.bs-survey--lit { clip-path: inset(0 calc(100% - var(--posw, 50%)) 0 0) }` 逐帧变化（`.is-dragging` 已关过渡）——每帧整层重栅格化（S2）。

### 5.2 候选方案对比

| 方案 | 机制 | 结论 |
|---|---|---|
| α：scaleX 合成器路径 | 亮层置入 `overflow: hidden` 包裹层，内容层 `transform: scaleX(var(--posw))`、`transform-origin: left` | **合成器加速、零重栅格化**；视觉语义从"裁剪推进"变为"宽度压缩"——潮汐亮带内部密度随之挤压，属视觉语义变化，需设计裁定 |
| β：mask 推进 | 亮层以 mask 控制可见域 | mask 为 paint 属性，逐帧更新仍重绘制，**不优于现状** |
| γ：量化 + 抽帧降频 | 拖拽期 `--posw` 按 2% 步进量化（≤50 档）并降采样至 30Hz | 视觉结构零改动；重栅格化频率降约一半，风险最低 |
| δ：width 推进 + 子层补偿 | 宽度驱动布局再反向补偿 | layout thrash，**否决** |

### 5.3 推荐执行序列

1. **先落 γ**：零视觉变化收敛 S2 尖峰（30Hz 抽帧复用 tiltLoop 现有帧循环的半步抽帧机制，不新增渲染管线）。
2. **α 作为设计决策点**：若"宽度压缩"的视觉语义经评审可接受（潮汐亮带能量进程意象在压缩下依然成立），再将 γ 升级为 α（纯合成器路径，彻底消除拖拽重栅格化）；评审标准：α 效果必须**等价或更优**于现状，而非妥协降级。

**决策点标注：γ 为默认必做项；α 待视觉评审后决定是否升级，实施前需确认。**

### 5.4 本批次验收

- 拖拽全程 DevTools Performance 采样：`.bs-survey--lit` 层重栅格化帧占比显著下降；帧预算无超时。
- 视觉走查：亮带推进与松手吸附动画和现状一致（γ）/ 语义一致（α 升级时）。
- 结合门禁全绿。

### 5.5 回滚

γ 为纯量化参数回退；α 还原为 clip-path 版本即可。

## 六、Batch 4 —— GC 与堆上限治理（S5 收尾）

### 6.1 变更点

1. `tauri.conf.json`：移除 `--js-flags="--max-old-space-size=1024 --expose-gc"` 整段。

   理由：`--expose-gc` 把强制 GC 能力暴露给页面 JS（生产环境属多余攻击面）；1GB 堆上限在三引擎 + 缓冲的负载下会逼近上限引发 Major GC 风暴（S5），交还 V8 默认动态堆策略。

2. `src/utils/gc.ts`：`tryGc`/`scheduleGc` 在 `--expose-gc` 缺失时已安全 no-op（现代码 `typeof win.gc !== "function"` 守卫完整），**函数签名与调用点保持兼容，不删除调用链**；同步校准注释——现注释声称 `--gc-interval=100`、`--optimize-for-size` 等 flags，与实际配置不符，改写为仅描述可验证行为（缺失原生 gc 时安全跳过；该辅助仅在本环境显式启用 gc 时生效）。

### 6.2 本批次验收

- 内存观测：10 分钟运行期任务管理器进程内存曲线无异常增长（无 1GB 钳制后的失控迹象）。
- 模块切换/批量数据加载路径无功能回归（tryGc 静默跳过符合设计）。
- 门禁全绿。

### 6.3 回滚

恢复 js-flags 字符串即可。
