# 安全中枢防护全链路深度排查报告

- 日期：2026-09-23
- 范围：安全中枢（SecurityCenter）三档/自定义模式的「切换生效链」「持久化链」「卡死风险」全链路（Vue3 前端 → Rust 命令层 → verthys-worker → C 核心）
- 性质：**只读排查**，未做任何代码修改；本报告仅输出问题清单与证据，修复方案留待后续单独立项
- 排查方式：日志取证 + 前后端/worker/C 四层逐层静态贯通验证 + 调用方全量 grep 交叉验证（含 .def 导出、worker op 清单、命令注册表、localStorage 读写点）

---

## 一、结论摘要（TL;DR）

| 用户症状 | 判定根因 | 严重度 |
|---|---|---|
| 切换模式不生效/假生效 | **三档预设没有任何"运行时生效"链路**：前端只改内存 ref + localStorage + 一个恒失败的高安全开关；Worker/C 层无切档命令；C 层切档函数零调用方 | 最高 |
| 切换三档直接卡死应用 | `onApplyPreset` 的 await 无超时 + 后端同步命令持 session_guard 锁可能被长操作阻塞 → `presetApplying` 恒 true → 中枢交互全冻结；另存在挂载/就绪时按旧值重写覆盖用户切换的竞态 | 高 |
| 重启后恢复原模式/自定义丢失 | 预设持久化仅前端 localStorage 单点（后端无落盘）；自定义特性开关只在"保存并应用"按钮时落盘；挂载/解锁恢复路径可能用旧值覆盖新选择 | 高 |

---

## 二、问题清单

### A 类：切换不生效 / 假生效（防护未真正变更）

#### A1【最高】三档预设不存在"运行时生效"链路，C 层切档函数零调用方
- **位置**：
  - 前端：`verthys-tauri/src/session/security-session.ts:95-136`（applySecurityPreset）
  - 前端：`verthys-tauri/src/composables/security-center/usePreset.ts:279-309`（onApplyPreset）
  - Rust：`verthys-tauri/src-tauri/src/security_commands/commands/preset.rs:22-88`（security_get_preset_config，静态查表）
  - worker：`verthys-tauri/verthys-worker/src/runtime/dispatch.rs` 全部 op 清单（无任何 preset/switch 类 op）
  - C：`core/src/security/preset/security_preset.c:119-163`（init/switch 双缓冲实现）
  - C：`core/verthys.def`（导出清单，无运行时切档 API）
- **证据链**：
  1. 前端 `applySecurityPreset(code)`（security-session.ts:95）只做四件事：写 `keyState.securityPreset.value`、`saveSecurityPreset`（localStorage）、设 `sessionTimeoutMs`、`securitySessionSetHighSecurity(preset===1)`。**没有调用任何 C 层预设应用接口**。
  2. 随后调用的 `securityGetPresetConfig`（preset.rs:22-88）是**静态查表**：按 code 返回硬编码 PresetFeatures，用于 UI 特性摘要条展示，不触发任何运行时行为变更。
  3. worker `dispatch.rs` 全部 op：ping/unlock/create_with_preset/lock/flush/add_record/get_record/…/derive_global_key/verify_global_key/…——**不存在** `switch_preset / set_preset` 类 op。
  4. `verthys.def` 唯一与 preset 相关的导出是 `Verthys_CreateWithPreset`（创建容器时把 preset 作为**创建参数**透传 `verthys_api_v3_create`，`core/src/api/lifecycle/verthys_api.c:1046-1075`）。
  5. C 层 `security_preset_switch`（security_preset.c:135）与 `security_preset_init`（119）**在 core/ 全仓无任何调用方**（grep 仅命中自身的 h/c 与注释），属于"存在但从未被触达"的运行时切档实现；`security_get_config` 未初始化时懒初始化为 BALANCED（:108-117）。
- **影响**：平衡/安全/性能三档之间的 12 项防护差异（anti_debug_aggressive、usb_shadow_sleep_min、session_lock_on_display_off、export_reauth、remote_control_block、kdf_iters_punish 等）**运行时永不变更**。用户切档＝改了个 UI 编号与会话超时，防护等级实际未变。

#### A2【高】高安全模式开关（set_high_security）恒定失败，且静默假成功
- **位置**：
  - 前端：`verthys-tauri/src/lib/verthys.ts:1314-1316`（securitySessionSetHighSecurity 只传 `{ enabled }`，无 auth_token）
  - Rust：`verthys-tauri/src-tauri/src/security_commands/commands/session.rs:101-149`
  - Rust：`verthys-tauri/src-tauri/src/security_commands/auth.rs:25-38`（仅 verify，无 issue）
- **证据链**：
  1. 后端要求一次性 `auth_token`（session.rs:108 `verify_and_consume_auth_token`），缺失即记 `PERMISSION_DENIED` 并返回 `SecurityResult::error`——注意是 **Ok(SecurityResult)**，不是 Err（session.rs:120-124）。
  2. 前端调用不带 token（verthys.ts:1314-1316）且 **不检查 SecurityResult.ok 字段**，await 不抛错 → 前端认为成功。
  3. `auth.rs` 只有 `verify_and_consume_auth_token`；`auth_tokens: Vec<String>`（state.rs:38）的**发放端不存在**——`mod.rs` 注释声称的 `auth: generate_auth_token` 仅存在于注释，grep 无实际定义/注册；前端也全无 token 生成调用（全仓 grep authToken 仅命中隐私模式用"用户主密码"的语义，与 auth_tokens 机制无关）。
- **影响**：`auth_tokens` 恒空 → 一切要求 auth_token 的命令恒 `PERMISSION_DENIED` → 高安全模式（电源挂起监听/更激进锁屏）从未真正启用，且 UI 无任何报错（假成功）。自定义模式的 `highSec` 布尔合成同样走了这条恒失败路径。

#### A3【高】自定义模式 12 项特性开关中，除 2 项外全部无消费方；落盘时机缺陷
- **位置**：`verthys-tauri/src/composables/security-center/usePreset.ts:234-270`（onToggleCustomFeature / onResetCustom / onApplyCustom）
- **证据链**：
  1. `onToggleCustomFeature`（:234-240）仅改内存 `customFeatures.value`，**不写 localStorage**；`onResetCustom`（:243-250）仅改内存；只有 `onApplyCustom`（:253-270）才 `saveCustomFeatures` + `applySecurityPreset(3)`。用户改完开关不点"保存并应用"即丢失。
  2. `applySecurityPreset(3)`（security-session.ts:106-121）只把 `session_lock_on_idle && clip_clear_on_lock` 合成一个布尔传给恒失败的 set_high_security（见 A2）；其余 10 项（module_patrol/usb_clone_detect/trace_cleanup/shadow_sleep 等）**前端无任何消费方**——既不对接 C 层 config，也不影响任何运行时行为。
  3. `loadCustomFeatures` 仅从 localStorage 读，`customFeatures` 初始即 localStorage 值（usePreset.ts:110）——未保存的改动天然丢失。
- **影响**：自定义模式同样是"改 UI 假象"；关闭某项防护对真实防护无影响，用户误以为已关闭（安全认知错误）。

#### A4【中】C 层安全配置首次读取存在无锁竞态（并发首读）
- **位置**：`core/src/security/preset/security_preset.c:108-133`
- **证据链**：`security_get_config` 首调检测 `s_config_active == NULL` 后直接调 `security_preset_init`，`s_initialized` 非原子、双缓冲写入无同步；多个子系统（anti_debug_v2/anti_inject/memory_guard/emergency）首读并发时可能同时 init、互相覆盖缓冲。
- **影响**：理论配置撕裂（实测依赖时序；低概率但存在）。

### B 类：切换模式卡死应用

#### B1【高】`onApplyPreset` 的 await 无超时 + 后端同步命令持锁 → `presetApplying` 恒 true 冻结中枢
- **位置**：
  - 前端：`verthys-tauri/src/composables/security-center/usePreset.ts:279-308`（presetApplying 守卫在 finally 才复位；await 无 withTimeout）
  - 前端：`verthys-tauri/src/lib/verthys.ts:1314-1316`（IPC 无超时）
  - Rust：`security_commands/commands/session.rs:101-149` + `security_commands/state.rs:131-144`（持 `session_guard` 锁）
  - Rust：`security_commands/commands/session.rs:31-73`（security_session_start 同样持锁；`SessionGuard::start` 内部创建隐藏窗口/注册 WTS 通知）
- **证据链**：
  1. `security_session_set_high_security` 与 `security_session_start` 共用 `session_guard` Mutex（state.rs:28）。
  2. 前端 `verifyGlobalKey` 对 `securitySessionStart` 为 5s 超时包装（global-verthys.ts:1328 附近），但 Tauri 命令是**同步函数**：若 `guard.start()` 或内部 Windows API 调用长时间持锁执行，超时的只是前端 Promise，**锁仍被占用**；随后的 `set_high_security` 在 `lock_session_guard_or_recover` 处阻塞等待 → IPC 卡住 → `applySecurityPreset` 的 await 永不返回 → `presetApplying` 恒 true → 滑块/锚点/自定义按钮与提示全冻 → 表现为"切换三档卡死"。
  3. `onApplyPreset` 全程无超时、错误仅 console.error（:303-305），IPC 挂起时无任何恢复路径。
- **影响**：切换模式瞬间的 UI 冻结（严重时需重启）。具体复现路径（start 持锁时长、是否恰撞锁）需运行时日志二次确认，但"无超时 await + 同步命令持锁"的静态风险成立。

#### B2【中】挂载/就绪恢复与用户切换的竞态覆盖（切了又变回去）
- **位置**：`verthys-tauri/src/components/modules/SecurityCenter.vue:482-488, 530-540`
- **证据链**：
  1. `onMounted` 与 `watch(globalKeyReadyRef)` 两处都会 `applySecurityPreset(securityPresetRef.value)`（用**当前 ref 值**）。
  2. 若该恢复调用先排队（ref 还是旧值 0/默认），用户随后点击切换到新档，恢复链异步滞后完成时会把 ref **写回旧值并再次 saveSecurityPreset** → 用户新选择被覆盖，UI 回滚、localStorage 也被写坏。
  3. `applySecurityPreset` 内先 `keyState.securityPreset.value = preset` 再 `saveSecurityPreset`，无版本/时间戳仲裁，后到者赢。
- **影响**：与"重启/重进中枢后模式恢复旧值"现象叠加（跨 B/C）。

### C 类：模式无法保存落盘 / 重启恢复原模式

#### C1【高】预设持久化仅前端 localStorage 单点，后端无落盘
- **位置**：`verthys-tauri/src/state/key_state.ts:115-120, 188-194`；grep src-tauri 无 preset 持久化字段
- **证据链**：
  1. `securityPreset` 全局唯一持久化是 `localStorage["verthys_security_preset"]`（key_manager_const.ts:101）。
  2. Rust 侧状态文件（repository/verthys_state.rs）与安全命令状态无"当前预设"写入。
  3. localStorage 存放于 WebView profile（EBWebView\Default\Local Storage）；**数据目录切换（便携模式回退 / 应用更新更换路径）即丢失**；`saveSecurityPreset` 的 try/catch 会静默吞写失败（仅 console.warn）。
- **影响**：模式存储无第二副本；目录漂移或写失败场景下重启必然回默认（与用户症状一致）。

#### C2【高】自定义特性配置仅在"保存并应用"按钮时落盘（见 A3-1）
- **影响**：用户改开关后直接退出/切走即丢失；重启后"恢复原有模式"。

#### C3【中】UI 模式标签/滑块显示依赖 activeAnchorIdx（而非 securityPresetRef）
- **位置**：`usePreset.ts:161-165`（currentModeLabel）、`:124-135`
- **证据链**：`currentModeLabel` 取 `labels[activeAnchorIdx.value]`，初始恒 1（平衡）；`loadPresetConfig` 不在时（加载失败/未执行）即使 ref=2（性能）UI 仍显示"平衡"、滑块停在中间 → "看起来没生效/恢复成原样"。

### D 类：架构与契约缺口

#### D1【最高】缺少"前端 → Rust → worker → C"的运行时切档贯通链路
- 全链路现状：`onApplyPreset(code)` → `applySecurityPreset`（只恭喜 UI/localStorage）→ `securityGetPresetConfig`（查表）→（结束）。Worker/C 层 `security_preset_switch` 无可达调用路径。**需要新增一层切档命令（TRUSTED）做安全授权与一层 FFI 透传**——实施阶段另行设计。

#### D2【中】文档/UI 语义与实现不符
- UI 特性列表 desc 标"C 层固定启用"（usePreset.ts:86-97），实际 C 层运行时配置只可能是"从未 init 的 BALANCED"或"创建容器时的档位"，三档差异从不呈现；preset.rs/preset.c 注释描述的能力与可达路径不一致。

#### D3【低·待验证】解锁后 C 层配置不按容器预设恢复
- 容器创建时可带 SECURE/PERFORMANCE（Verthys_CreateWithPreset），但解锁路径未证实会按该 preset 调 `security_preset_init/switch`；C 层 `get_config` 懒初始化恒 BALANCED。**需在实施阶段确认 `verthys_api_v3_create`/`Verthys_Unlock` 与 preset 的关联**。

## 三、链路现状图（文字版）

```
用户点击"安全"档
  └─ usePreset.onApplyPreset(1)
       ├─ security-session.applySecurityPreset(1)
       │    ├─ keyState.securityPreset.value = 1          ✔ 内存
       │    ├─ saveSecurityPreset(1) → localStorage        ✔ 本地（仅此一层持久化）
       │    ├─ sessionTimeoutMs = PRESET_SESSION_TIMEOUT_MS[1]  ✔ 会话超时
       │    ├─ securitySessionSetHighSecurity(preset===1)
       │    │    └─ ipc 无 token → PERMISSION_DENIED（Ok 包装，前端不检查）✘ 恒失败
       │    └─ securityGetPresetConfig(1) → 静态查表       ✔ 仅 UI 展示
       └─ （终点）✘ —— 没有任何 IPC 到达 worker / C
            worker dispatch: 无 switch_preset op            ✘
            C verthys.def: 无运行时切档导出                 ✘
            C security_preset_switch: 零调用方              ✘ 死实现
```

## 四、待运行时复现/二次确认项（不阻断出清单）

1. B1 卡死：抓 `security_session_start` 持锁时长与 `set_high_security` 阻塞点（加日志或 windbg/fiddler 复现）。
2. D3：解锁后 C 层 `security_get_config().preset` 实测值是否等于容器创建档位。
3. C1：数据目录切换是否导致 localStorage 目录漂移丢失模式。
4. "重启恢复原模式"是否由 B2 竞态（挂载恢复覆盖）与 C3（显示层错位）叠加造成，需一次完整重启复现比对。

## 五、建议修复顺序（仅方向，本次不实施）

1. **打通运行时切档链路**（A1/D1，最高优先）：新增授权命令 + worker op + C 导出 `Verthys_SwitchSecurityPreset`（挂到 verthys.def），前端 onApplyPreset await 该命令并检查真实结果。
2. **修复 auth_token 机制**（A2/D4）：实现 `generate_auth_token` 发放（或取消该机制改为状态机授权），前端补传 token 并校验 `SecurityResult.ok`。
3. **给 onApplyPreset 全部 IPC 加超时 + 失败复位**（B1），并化解 session_guard 锁长持（start 改异步/独立线程）。
4. **消除 B2 竞态**：恢复链加版本仲裁，仅当"无用户交互 pending"时才应用。
5. **持久化加固**（C1/C2）：预设与自定义配置落盘到后端受信文件（与 .verthys_state 同域），自定义开关即时持久化。
6. **UI 语义修正**（C3/D2）：label/滑块以 securityPresetRef 为唯一事实源；特性列表 desc 如实标注"受后端开关控制"。
7. **C 层 init 加锁**（A4）：首读 init 加临界区或一次性原子发布。
