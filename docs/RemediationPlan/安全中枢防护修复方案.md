# 安全中枢防护修复方案

## Decision Gate（已实读裁定）

| 待确认项 | 确认方法 | 结论 | 裁定依据（实读证据） |
| --- | --- | --- | --- |
| 锁获取与令牌校验先后（B1 锁阻断卡死链） | 实读函数体 | **分支 B：卡死链不成立** | set_high_security 先校验后锁；set_high_security_mode 仅 AtomicBool store；session_guard start 为独立消息线程（同步通道等待窗口创建线程，非主线程死锁）。防护退化为通用规则：前端 IPC 统一超时 + pending 复位兜底（已实施） |
| A4 并发可达性：多子系统是否并发首读 security_get_config | 实读调用点线程上下文 | **分支 B：A4 撤销** | worker 单线程 stdin 循环 + Worker 独占借用，C API 全串行，安全配置无并发首读方。不实施修改 |
| WebView 数据目录是否随应用数据目录漂移（C1"漂移丢失"） | 实读 Tauri 初始化配置 | **分支 B：不漂移** | tauri.conf.json 无 dataDirectory 配置，WebView2 固定于 %LOCALAPPDATA%\com.verthys.app，不随 data_dir 漂移。C1 撤销，持久化加固理由收敛为：单点脆弱 + 静默吞写失败 + 无权威源（已实施） |
| A2 是否孤立模式：前端是否普遍不校验 SecurityResult.ok | 全量 grep 调用点 | **系统性缺陷成立** | 4 个敏感命令 6 处后端恒 PERMISSION_DENIED（auth_token 无发放端），前端所有 SecurityResult 型命令以 Promise<void> 消费（无 ok 校验）。统一契约修复为最高优先级（已实施） |

## 修复目标：三条不变式

方案的一切设计都服务于让以下三条不变式成立。它们同时是验收标准。

**生效性**：任何"用户可见的防护状态变更"必须在后端（worker/C）有对应的真实状态变更。不允许只改 UI。

**可见性**：任何失败必须返回明确错误码并被前端处理。不允许"Ok 包装的错误"被静默吞掉，不允许 pending 标志因异常而永久卡住。

**单一事实源**：防护配置的权威副本在后端受信存储。前端缓存只是缓存，恢复时以后端为准。不存在"两个源互相覆盖"。

## 分项方案

### 授权模型统一（A2 / DG-5）

**设计意图**
当前 `auth_token` 机制的核心问题是：token 的发放端不存在，而校验端严格要求。补一个发放端是最小改动，但值得先问：这个机制该存在吗？

在 Tauri 应用中，IPC 调用者即本应用前端。威胁模型是"前端被注入/被绕过"。若 token 的发放也走前端可达的 IPC，则攻击者同样可获取 token，机制只增加复杂度不增加安全性。真正有效的授权信号是：**当前会话是否在近期完成过一次强验证**（主密码验证）。

**推荐方案：后端状态机授权，废除 token 流动**

- 定义 `SensitiveOpPolicy`：为每个敏感命令声明其所需的授权级别（如 `RequiresRecentStrongAuth { max_age: 5min }`）。
- 后端在 `verify_global_key` 成功时记录 `last_strong_auth_at`（进程内状态，随锁定时清零）。
- 敏感命令入口统一检查：`now - last_strong_auth_at > max_age` → 返回明确错误码 `E_NEED_REAUTH`。
- 前端统一处理 `E_NEED_REAUTH` → 弹出强验证 UI → 成功后重试原操作。此逻辑做一次，所有敏感命令共用。
- 删除 `auth_tokens` 相关死代码（`auth.rs` 的 verify_and_consume、state.rs 的 auth_tokens 字段、mod.rs 的注释声明）。

**备选方案：实现 token 发放端**
若架构上必须保留 token 语义，则：

- 实现 `generate_auth_token`，与 `verify_and_consume` 成对。
- 明确 token 的 TTL、一次性、绑定操作类型。
- 前端在调用敏感命令前先取 token 再传。
- 此方案缺陷：token 在前端流动，攻击面更大；且"取 token"本身是一个可被绕过的 IPC。

**取舍标准**：若威胁模型认为"前端 IPC 可被完全绕过"，则两方案等价。若认为"前端 IPC 需二次校验"，则推荐方案更强（授权状态在后端，前端无法伪造）。

**改动点**

| 层 | 文件 | 改动 |
| --- | --- | --- |
| Rust | `security_commands/auth.rs` | 删除或替换 `verify_and_consume_auth_token`；新增授权状态检查 |
| Rust | `security_commands/state.rs` | 删除 `auth_tokens` 字段；新增 `last_strong_auth_at` |
| Rust | `security_commands/commands/session.rs` | 命令入口改用新授权检查，返回明确错误码 |
| Rust | `security_commands/mod.rs` | 修正注释中的不实声明 |
| 前端 | `lib/verthys.ts:1314-1316` | 检查 `SecurityResult.ok`；处理 `E_NEED_REAUTH` |
| 前端 | 统一处理层 | 新增 `E_NEED_REAUTH` → 重试的统一逻辑 |

**契约**

- `SecurityResult` 语义收敛：`ok: false` 必然对应一个非空 `code`。不允许 `ok: false` + 空 code。
- `E_NEED_REAUTH` 是**可恢复**错误：前端应触发重新验证，而非提示失败。

**失败模式**

| 场景 | 期望行为 |
| --- | --- |
| 未做近期强验证 | 返回 `E_NEED_REAUTH`，前端弹验证框 |
| 强验证过期（超时） | 同上，且清空 `last_strong_auth_at` |
| 锁定/清空状态 | 返回 `E_LOCKED`（既有），优先于 reauth 检查 |

**测试与验收**

- 契约测试：无强验证时敏感命令返回 `E_NEED_REAUTH`；强验证后 5 分钟内成功；超时后再次要求 reauth。
- 回归：`E_NEED_REAUTH` 前端处理链路覆盖测试（弹框→重试→成功）。
- 验收：撤销 `auth_tokens` 后全仓 grep 无引用；A2 的"静默假成功"不再可能（错误码明确）。

### 运行时切档贯通链路（A1 / D1，条件：DG-1 分支 A）

**设计意图**
补全从 UI 到 C 层的完整切档链路，使切档真实生效、失败可见、可审计。

**链路设计**

```
前端 onApplyPreset(code)
  → ipc: security_apply_preset(code)        [新命令]
      → Rust: 授权检查（是否需要 reauth）
      → Rust: 校验 code 合法性
      → Rust: send_with_timeout → worker     [新增 op]
          → worker: switch_preset
              → C: Verthys_SwitchSecurityPreset(code)   [新导出]
                  → security_preset_switch(code)         [复用现有实现]
      → 返回真实结果
  → 前端检查 result.ok；失败则回滚前端状态
```

**关键设计点**

- **幂等**：切到当前档返回成功（no-op），不报错。
- **原子性**：C 层 `security_preset_switch` 必须先完整构建新配置、全部校验通过、再一次性发布（原子指针交换或等效）。当前实现是否满足需在实施时审查。
- **审计**：切档写审计（旧档、新档、结果）。切档是安全相关操作。
- **锁**：切档命令使用独立的 preset 锁，不与 `session_guard` 争锁。避免与锁问题耦合。
- **失败回滚**：前端 `applySecurityPreset` 当前"先改内存 ref 再落盘"的顺序必须反转——先调后端，成功后改前端状态。失败则保持原状态并提示。

**改动点**

| 层 | 文件 | 改动 |
| --- | --- | --- |
| C | `core/src/security/preset/security_preset.c` | 审查 switch 的原子性与校验；修复如需要 |
| C | `core/verthys.def` | 新增 `Verthys_SwitchSecurityPreset` 导出 |
| C | 头文件 | 声明新导出 |
| worker | `runtime/dispatch.rs` | 新增 `switch_preset` op；调用新 C 导出 |
| Rust | `security_commands/commands/preset.rs` | 新增 `security_apply_preset` 命令；接入授权检查 |
| Rust | `lib.rs` | 注册新命令 |
| 前端 | `session/security-session.ts:95-136` | `applySecurityPreset` 改为 await 后端命令、检查 ok、失败回滚 |
| 前端 | `composables/security-center/usePreset.ts:279-309` | 同上；`presetApplying` 全程有超时兜底 |

**契约**

- `security_apply_preset(code)` 返回 `SecurityResult<PresetConfig>`，成功时返回**新档的实际配置**（供 UI 渲染，替代静态查表）。
- `code` 非法 → `E_INVALID_PRESET`，不静默。
- worker/C 失败 → 透传错误码，不吞。

**失败模式**

| 场景 | 期望行为 |
| --- | --- |
| 切换过程中 C 层校验失败 | 返回错误，前端状态不变 |
| 切换成功但审计写失败 | 切档成功，审计失败单独告警（不阻塞） |
| 重复切到当前档 | 成功（幂等），不写"变更"审计 |

**测试与验收**

- 端到端：切档后 worker 收到 `switch_preset`，C 层 `security_get_config().preset` 等于目标档。
- 回归：切档失败时前端 UI 状态不变（不出现"UI 变了但实际没变"）。
- 验收：D1 的"零调用方"消失——`security_preset_switch` 有可达调用路径。

### 卡死防护（B1 / DG-2）

**设计意图**
无论 DG-2 结论如何，"无超时 await + 同步命令持锁"是系统性风险。本节做两层防护：**通用 IPC 超时契约**（不依赖具体机理）+ **锁粒度修正**（若 DG-2 分支 A）。

**通用防护（无条件实施）**

- 前端 IPC 统一超时：所有 `ipc()` 调用经过统一包装，带默认超时（如 10s）。超时视为错误，触发 pending 标志复位。
- pending 标志的兜底复位：`presetApplying` 等标志的复位不能只在 `finally`。任何超时/异常路径都必须复位。建议封装为 `withPendingGuard(flag, fn)` 模式，超时/异常自动复位。
- 后端锁获取超时：所有持锁的 Tauri 命令，锁获取使用 `try_lock` + 超时，超时返回 `E_BUSY`，绝不允许无限阻塞。这是后端侧的 fail-fast。
- 长操作移出锁外：审查 `SessionGuard::start` 内部（创建窗口、注册 WTS 通知），将这些长操作移出锁保护区。锁只保护状态读写，不保护 Windows API 调用。

**锁粒度修正（条件：DG-2 分支 A）**
若确认 `set_high_security` 会阻塞在 `session_guard` 上：

- 将 `session_guard` 拆分为"状态锁"（短持有）与"操作串行化"（独立机制，如 command 队列）。
- 或者：`security_session_start` 改为异步执行，返回 job id，前端轮询/事件通知结果。锁在 job 开始时短暂持有，执行期间释放。

**改动点**

| 层 | 文件 | 改动 |
| --- | --- | --- |
| 前端 | `lib/verthys.ts` | 统一 IPC 超时包装 |
| 前端 | 各 pending 标志处 | 改用 `withPendingGuard` |
| Rust | `security_commands/state.rs:131-144` | 锁获取加超时 |
| Rust | `security_commands/commands/session.rs:31-73` | 长操作移出锁外 / 改异步 |

**契约**

- 前端 IPC 超时是**可观测事件**（log + 可选 UI 提示），不是静默失败。
- `E_BUSY` 是**可重试**错误：前端可短暂退避后重试。

**测试与验收**

- 故障注入：模拟后端持锁不释放，断言前端在超时后 pending 复位、UI 可交互。
- 回归：`onApplyPreset` 在后端不响应时，`presetApplying` 不永久 true。
- 验收：手动复现原卡死场景（若可复现），确认不再冻结。

### 竞态消除（B2）

**设计意图**
消除"恢复链覆盖用户切换"的竞态。

**方案：版本仲裁**

- 前端维护 `presetEpoch`（单调递增整数，模块级）。
- 任何用户触发的切换递增 `presetEpoch`。
- 恢复链（`onMounted` / `watch(globalKeyReadyRef)`）在启动时记录 `presetEpoch`，异步完成后若 `presetEpoch` 已变，**丢弃结果**，不写状态、不落盘。
- 更简单的替代：`userInteracted` 标志。用户首次交互后置 true，恢复链仅当 `!userInteracted` 时应用。

推荐版本仲裁，因为它对未来其他竞态场景（如多窗口）也成立。

**改动点**

| 层 | 文件 | 改动 |
| --- | --- | --- |
| 前端 | `components/modules/SecurityCenter.vue:482-488, 530-540` | 恢复链加 epoch 检查 |
| 前端 | `session/security-session.ts` | `applySecurityPreset` 接受/返回 epoch（或由调用方仲裁） |

**测试与验收**

- 竞态测试：模拟"恢复链 pending 期间用户切换"，断言最终状态为用户选择，localStorage 未被写回旧值。
- 验收：B2 场景消失。

### 持久化加固（C1 / C2，条件：DG-4）

**设计意图**
建立单一事实源，消除 localStorage 单点。

**推荐方案：后端受信存储**

- 预设与自定义配置落盘到后端受信文件（与 `.verthys_state` 同域），或写入 verthys 容器元数据区（更强，随容器走）。
- 优先容器元数据：容器是唯一真正"跟着用户走"的载体，且受加密保护。若 C 层无元数据 API，则退化为独立状态文件 + 明确的数据目录策略。
- 前端 localStorage 保留为缓存，但**恢复时以后端为准**。

**写入时机**

- 任何配置变更**立即**落盘（废除"保存并应用"按钮的延迟落盘语义；落盘不依赖它）。
- 落盘失败必须报错（复用通用报错组件，严格按照要求实现报错的流程），不能静默吞（当前 C1 指出 `try/catch` 静默 warn）。

**迁移**

- 首次启动时，若后端无配置而 localStorage 有，迁移到后端并清除 localStorage。
- 迁移写审计。

**改动点**

| 层 | 文件 | 改动 |
| --- | --- | --- |
| Rust | `repository/verthys_state.rs` | 新增 preset / custom 配置字段（或独立文件） |
| Rust | `security_commands/commands/preset.rs` | 新增读写命令 |
| C（若走容器元数据） | 元数据 API | 新增或复用 |
| 前端 | `state/key_state.ts:115-120, 188-194` | 改为读后端；localStorage 降级为缓存 |
| 前端 | `composables/security-center/usePreset.ts:234-270` | 即时落盘；失败报错 |

**契约**

- 后端配置是权威。前端启动时先读后端；后端无值才读 localStorage（迁移场景）。
- 落盘失败返回错误码，前端提示。

**测试与验收**

- 持久化测试：切档 → 重启 → 档位保持。
- 迁移测试：仅 localStorage 有值 → 迁移 → 后端有值 + localStorage 清除。
- 验收：C1/C2 症状消失；DG-4 若成立，目录漂移不影响配置。

### 审计要求

所有安全相关操作必须写审计，且审计项在方案中显式列出：

- 切档（旧档、新档、结果、触发者）
- 授权（强验证成功/失败、reauth 触发）
- 配置变更（预设、自定义特性）
- 迁移（localStorage → 后端）

审计写入失败不阻塞主操作，但必须单独告警。

## 实施顺序与批次

按依赖关系与风险排序。每批次独立可验证、可回滚。

**批次：Decision Gate**
产出《DG 结论表》。所有后续批次以它为准。

**批次：授权模型 + 可见性契约**
理由：它影响所有敏感命令的行为，且 A2 的"静默假成功"是其他问题的观测障碍。先修它，后续问题的真实行为才能被观测。

**批次：运行时切档链路（条件 DG-1 分支 A）**
理由：DG-1 分支 A 时的最高优先项。

**批次：卡死防护**
通用防护无条件做；锁粒度修正视 DG-2。

**批次：持久化加固**
理由：在切档链路可用后，持久化才有意义。

**批次：竞态 + 显示层**
理由：依赖切档链路与持久化稳定。

**批次：C 层原子性（条件 DG-3）**

**批次：全局回归 + 门禁全绿 + 文档**
