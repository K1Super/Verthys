## 0. 执行约束

1. **禁止虚假阻断**：任何路径的 `BLOCKED` 必须绑定当前进程/当前 V4 会话可验证的事实，并带采样时间；不得以模块 `init()` 成功代替攻击路径闭合。
2. **禁止无证据降级后的静默处理**：降级必须携带原因码；架构限制必须在 UI 明示，不得伪装成阻断。
3. **内核托管暂缓**：在未实施内核托管前，`内存转储` 与 `休眠取证` 在解锁态只能诚实报告为降级；本方案不把它们改成阻断。
4. **单一事实源**：状态判据只在 C 核心计算；Rust/TS 仅透传与展示，禁止本地推导安全结论。
5. **每阶段可回退**：每个工作包独立可编译、可测试、可回滚；禁止跨阶段半成品混入。
6. **无死代码**：新增能力必须有生产调用点；被替换的旧路径必须删除或迁出产品构建，不得保留“以防万一”的分支。

## 1. 现状与缺陷登记

### 1.1 现状结论

- 7 条路径中：`进程读取` 真实；`跨设备迁移` 基本真实；`动态劫持` 真实但缺 OS 回读；`内存转储`、`休眠取证` 在 V4 解锁态真实降级且判据不可达；`挂起绕过`、`接口挂钩` 为名义阻断。
- V4 内容密钥（`VtyVault.kc` / Keyring / `modules[].mdek`、`VtyStore.kdir`）驻留普通 `calloc` 堆；`secure_allocator_alloc`、`memory_guard_lock` 无生产调用点。
- `SessionGuard` 的回调在 `SecurityState::new` 中为 no-op；系统锁屏/挂起/显示器关闭不会触发真实锁库。
- `anti_inject_init` 无调用点；仅 `anti_inject_check_modules` 在解锁后调用一次。
- `tamper_destroy_trigger`、`system32_loader_load` 无生产调用点。
- 现有攻击测试 A8 将“解锁态内存转储必须命中密钥”作为正控，证明项目当前模型是“锁定前可被转储”，不是“转储免疫”。

## 2. 目标态与设计

### 2.1 判据原则

| 状态 | 定义 | 允许的来源 |
| --- | --- | --- |
| `NOT_CHECKED` | 尚未采样 | 仅初始化前 |
| `BLOCKED` | 当前路径的攻击面已被真实闭合，或当前无资产可被攻击 | V4 会话事实、OS 查询、检测器最近一次有效结果 |
| `DEGRADED` | 防护能力缺失、被策略关闭，或受架构限制无法闭合 | 同上，必须带原因码 |
| `FAILED` | 关键防御模块缺失或检测到确定性入侵 | 模块失败、Hook 命中、TLS 缺失 |

硬性规则：

1. `BLOCKED` 必须同时具备：事实断言 + `checked_at_unix_ms` + 原因码；缺一不可。
2. 不得使用全局计数器（`s_kernel_handle_total`）作为 V4 判定依据。
3. 锁定态“无驻留密钥”按 `BLOCKED`（原因 `NO_RESIDENT_KEY`）处理，不得报降级。
4. 用户态上限导致的降级（内核托管暂缓、管理员挂起不可阻止）统一归入 `limited_count`，UI 显示“已加固（用户态上限）”，强调防护已生效但无法完全阻止，不得与可修复降级混淆。
5. 状态查询必须无副作用：不得调用任何 `*_init`、不得创建句柄/密钥、不得启动/停止定时器；只读取已初始化模块与 OS 查询结果。

### 2.2 V4 事实模型

新增内部结构（`defense_closure.h`）：

```c
typedef struct {
    uint32_t any_unlocked_v4;          /* 进程内任一 V4 会话已解锁 */
    uint32_t queried_unlocked_v4;      /* 被查询句柄的会话已解锁 */
    uint32_t queried_device_bound;     /* 设备根槽或 PCR 槽存在 */
    uint32_t queried_pcr_bound;
    uint32_t hibernation_state;        /* 0=禁用 1=启用 2=未知 */
    uint32_t sandbox_verified_mask;    /* OS 回读后的 mitigation 位 */
    uint32_t hook_scan_state;          /* 0=不可用 1=干净 2=异常 3=过期 */
    uint32_t policy_flags;             /* bit0=heartbeat bit1=suspend_lock bit2=anti_dump */
    uint64_t now_ms;
} DefenseFacts;

int defense_closure_check_facts(DefenseCheckMode mode,
                                const DefenseFacts *facts,
                                DefenseStatusReport *out);
```

- `Verthys_GetSecurityStatus` 校验 handle 在上下文注册表内，构建 facts 后调用 `_facts` 版本。
- BOOT（`Verthys_Init`）调用 `_facts` 并传零会话 facts；不触碰句柄。
- `defense_closure_check` 保留为无会话 facts 的兼容包装，供既有测试与 BOOT 使用。
- 并发约束（必须实现）：
  1. `any_unlocked_v4` 来自进程级原子计数，按 `ctx->v4` 的 NULL↔非 NULL 转换维护：首次 attach +1，非 NULL 替换保持不变，detach 为 NULL 时 −1；不遍历上下文、不读裸指针。
  2. `queried_*` 事实在共享模式持有 `ctx->api_mutex` 后读取 `ctx->state`/`ctx->v4`，复制完成后立即释放；随后才获取 `defense_closure` 的 `s_check_lock`，禁止嵌套 ctx 锁与检查锁。
  3. 禁止在已持 `ctx->api_mutex` 的 API 路径内调用 `Verthys_GetSecurityStatus`；状态查询由独立的 worker op 进入。
  4. 句柄校验与 facts 复制必须在 `s_ctx_registry_lock` 共享锁内完成，锁顺序为 registry → ctx；`Verthys_Deinit` 的注销在 registry 独占锁内完成，保证复制期间 ctx 不被释放。
  5. `ctx->v4` 的赋值/释放必须统一经三个辅助函数，禁止散落 `Interlocked`：
     - `v4_session_attach(ctx, v)`：NULL→v 计数 +1；替换旧值时释放旧值、计数不变。
     - `v4_session_detach(ctx)`：释放并计数 −1。
     - `v4_session_replace_externally_freed(ctx, v)`：仅用于 `Verthys_V4RotateCommit`（`vty_rotate_commit` 已释放旧库并返回新库），只赋值、不改计数。
  6. 必须审计全部 `ctx->v4` 赋值/释放点：`verthys_api.c` adopt/Deinit/Lock、`verthys_api_utils.c` 的 `ctx_zero_sensitive`、`verthys_api_v4.c` 的 RotateCommit；新增点必须使用上述辅助函数。
  7. 将 `s_ctx_registry_lock` 改为静态 `SRWLOCK_INIT`，移除 `s_ctx_registry_lock_init` 竞态；注册表读写与状态复制统一使用该锁。

### 2.4 七路径判定矩阵

| # | 路径 | BLOCKED 条件 | DEGRADED 条件 | FAILED 条件 | 主原因码 |
| --- | --- | --- | --- | --- | --- |
| 0 | 挂起绕过 | `any_unlocked_v4 == 0` | 有驻留密钥（无论看门狗是否启用） | 无 | 1 / 5 / 6 |
| 1 | 内存转储 | `any_unlocked_v4 == 0` | 有驻留密钥（`policy_flags` 仅用于 UI 提示，不改变判据） | 无 | 1 / 2 |
| 2 | 休眠取证 | `any_unlocked_v4 == 0` 或 `hibernation_state==0` | `hibernation_state==1/2` 且有驻留密钥 | 无 | 1/3/4/20 |
| 3 | 接口挂钩 | `hook_scan_state==1` 且 TLS 标志有效且直接系统调用可用 | `hook_scan_state==0/3` 或 syscall 不可用 | `hook_scan_state==2` 或 TLS 缺失 | 7/8/9/16/18 |
| 4 | 动态劫持 | OS 回读满足核心位（ProcessCreate/ImageLoad/Sys32/ACG） | 仅部分位满足 | 核心位缺失 | 10/11/12 |
| 5 | 进程读取 | `job_isolation_is_active()==1` | 无 | Job 未生效 | 13/16 |
| 6 | 跨设备迁移 | 会话已解锁且设备根/PCR 槽存在且机器密钥可用且硬件指纹就绪 | 无会话事实或绑定事实不可用 | 机器密钥/指纹初始化失败 | 14/15/16 |

说明：

- `内存转储` 与 `休眠取证` 在解锁态判定为 `DEGRADED`，原因 `V4_KEYS_USER_RESIDENT` / `HIBERNATION_ENABLED`，并标记为 architecture-limited。
- `挂起绕过` 在解锁态永远 `DEGRADED`，原因 `SUSPEND_UNPREVENTABLE`；看门狗只缩短暴露窗口，不改变阻断语义。
- `接口挂钩` 的“干净”必须有最近一次有效扫描（默认有效期 120 秒）；过期按 `EVIDENCE_STALE` 降级。

### 2.5 汇总与 stance

- `all_critical_blocked` 保持严格语义：7/7 `BLOCKED` 且无 `FAILED`。在未实施内核托管前，解锁态必然为 0；这是诚实结果，不得改语义。
- 新增 `limited_count`：`DEGRADED` 且属于已加固的用户态上限项路径数，仅统计原因 `V4_KEYS_USER_RESIDENT`（2）与 `SUSPEND_UNPREVENTABLE`（5）。`SUSPEND_GUARD_INACTIVE`（6）、`HIBERNATION_ENABLED`（3）、`HIBERNATION_UNKNOWN`（4）属于真实可修复降级，不计入 `limited_count`。
- 前端 stance 计算改为：
  1. `failed > 0` → `breach`
  2. `degraded > limited_count` → `degraded`
  3. `limited_count > 0` 且 `degraded == limited_count` → `limited`（展示“已加固”）
  4. `unchecked > 0` → `partial`
  5. `blocked == 7` → `ok`
  6. 其余 → `pending`

### 2.6 V4 密钥内存模型

| 对象 | 现状 | 目标 |
| --- | --- | --- |
| `VtyVault`（`kc`/Keyring/`modules[].mdek`/`k_recovery`/`keyfile_digest`） | `vty_alloc`（calloc） | 进程级共享 `SecureAllocator`：独立 `VirtualAlloc` 区段 + 前后 `PAGE_NOACCESS` + `VirtualLock`；释放前清零 |
| `VtyStore`（`kdir`） | `vty_alloc` | 同上 |
| `VtyRotateJob.module_pw[]` | `malloc` + 手动清零 | 进程级共享 `SecureAllocator`；分配后注册到 `memory_guard`；释放前注销 |
| 应急 KILL | 只清 `memory_guard` 注册区与 `key_separation` | 注册区覆盖 Vault/Store/口令，KILL 时统一清零 |
| 崩溃转储 | 无 | `WerRegisterExcludedMemoryBlock` 尽力排除安全块；API 不可用时记录能力不可用，不改变状态判据 |

实现要点：

1. `secure_allocator` 新增进程级 `secure_allocator_shared()`（`InitOnceExecuteOnce`，预算沿用全局 512MB；进程生命周期单例，不随 `Verthys_Deinit` 销毁；该单例不提供 destroy 路径，测试使用独立 `secure_allocator_create`）。密钥安全块始终 `VirtualLock`，不受 PERFORMANCE 预设的 `memory_lock` 开关影响。
2. `vty_keymanager_v4.c` 4 处 `vty_alloc(sizeof(VtyVault))`（约 808/1096/1486/1691 行）与 `vty_free`（约 2781 行）改为安全分配/释放；失败返回 `VTY_E_RESOURCE`，禁止回退普通堆。
3. `vty_store_v4.c` 631 行的 `VtyStore` 分配与 642/685/743 行释放改为安全分配/释放。
4. 安全块分配成功后调用 `memory_guard_register(ptr, len, "v4_vault"/"v4_store")`；释放前 `memory_guard_unregister(ptr)`。
5. `vty_rotate_v4.c` 的 `module_pw` 分配（约 497-503 行）改为安全分配并注册 `memory_guard`；释放（约 338-343 行）注销并安全释放。
6. `secure_allocator_alloc/free` 内部动态解析 `WerRegisterExcludedMemoryBlock` / `WerUnregisterExcludedMemoryBlock`，成功则登记/注销；解析失败或调用失败仅记录诊断，不视为安全失败。
7. 诚实边界：以上措施阻止换页与提高转储门槛，但**不能阻止已解锁进程的完整内存转储**；状态仍按 `V4_KEYS_USER_RESIDENT` 降级。`vty_vault_module_key*` 等接口返回的瞬时栈缓冲不在 WER 排除范围，操作期间发生崩溃仍可能在 dump 中留下瞬时明文；本方案通过调用点清零与崩溃路径最小化降低概率，不宣称彻底消除。
8. 移除 `VerthysContext` 的 per-ctx `secure_alloc` 字段（`core/src/container/shared/verthys_internal.h:101`）及 `Verthys_Init` 创建/`Verthys_Deinit` 销毁逻辑，统一改用 `secure_allocator_shared()`，避免两套分配器与死字段。

### 2.7 会话与电源联动

- `SecurityState::new` 不再使用 no-op 回调；在 `lib.rs` setup 后安装真实回调（`replace_session_guard`），回调捕获 `AppHandle`，执行同步锁库序列：
  1. 向 worker 发送 `{"op":"lock"}`，超时 3 秒；
  2. 销毁 worker 会话（`verthysWorkerDestroy` 等价路径）；
  3. 发出 `verthys://external-lock` 事件，载荷含 `reason`（`session-lock`/`suspend`/`logoff`/`disconnect`）。
- `SessionEvent::PowerSuspend` 改为**始终**触发 `on_lock`，不再受 high-security 门控；`DisplayOff` 仍按高安全档门控。
- 前端新增 `applyExternalLock(reason)`：只重置密钥状态与视图，不再次调用锁库命令，避免与已销毁 worker 竞态。
- 若锁库超时：直接终止 worker，仍发出事件；保证密钥随进程消亡。

### 2.8 检测能力扩展

| 能力 | 实现 | 运行时机 | 失败语义 |
| --- | --- | --- | --- |
| 休眠状态 | 新模块 `security/memory/hibernation_state.c/.h`；读 `HKLM\SYSTEM\CurrentControlSet\Control\Power\HibernateEnabled`/`HibernateEnabledDefault`；纯解析函数可注入测试 | 每次状态查询（注册表读取低成本） | 缺失/读取失败 = 未知（降级） |

| IAT 校验 | 同模块；解析自身 PE 导入表，仅校验来自 ntdll 且列入目标清单的导入项，与磁盘导出 RVA 对比 | 同上 | 解析失败 = 不可用；不覆盖项记入 `HOOK_SCAN_UNAVAILABLE` |

| 防注入周期巡检 | `anti_inject_init` 在 `Verthys_Init` 调用；`anti_inject_check_all()` 每 300 秒 + 解锁后一次 | 初始化/周期 | 检测命中按现有应急分级 |
| 反调试周期巡检 | `anti_debug_v2_check()` 每 60 秒 + 写路径入口 | 初始化/周期 | 命中按现有 KILL |
| 挂起看门狗 | 父进程创建匿名事件 + `DuplicateHandle` 注入 worker（句柄值经签名 IPC 传递），worker 独立线程每 500ms `SetEvent`；主进程等待 3 秒超时；超时后查询 worker 线程状态，全部 `Suspended` 则终止 worker 并触发 external-lock | worker 启动后持续 | 看门狗启动失败 = 降级原因 `SUSPEND_GUARD_INACTIVE` |

Hook 异常处置分级：

1. 首次不匹配且内存首字节呈 Hook 特征（`E9`/`EB`/`FF 25`/`68..C3`）→ `EMERG_LEVEL_TELEMETRY`，状态置异常，`接口挂钩` 报 `FAILED`。
2. 连续两次扫描均呈 Hook 特征 → `EMERG_LEVEL_KILL`。
3. 内存仍是标准 syscall stub，仅与磁盘基线不一致（Windows 更新未重启等）→ 记 `EVIDENCE_STALE` 并降级 + telemetry，**禁止 KILL**。
4. 基线文件读取失败、目标导出缺失 → 不 KILL，状态降级为 `HOOK_SCAN_UNAVAILABLE`。

### 2.9 状态 API 演进

`verthys.h` 中 `VerthysSecurityStatus` 采用**追加式扩展**，保持既有字段顺序：

```c
typedef struct {
    VerthysDefenseState path_state[7];
    uint32_t blocked_count;
    uint32_t degraded_count;
    uint32_t failed_count;
    uint8_t  all_critical_blocked;
    uint8_t  has_degraded;
    uint8_t  reserved[6];              /* 既有字段，保持不动 */
    /* 追加（API 0x0014） */
    uint32_t path_reason[7];           /* VerthysDefenseReason */
    uint32_t limited_count;            /* 已加固的用户态上限项数 */
    uint32_t policy_flags;             /* bit0=heartbeat bit1=suspend_lock bit2=anti_dump */
    uint32_t reserved2;
    uint64_t checked_at_unix_ms;
    uint32_t reserved3[2];
} VerthysSecurityStatus;
```

- `VERTHYS_API_VERSION`：`0x0013` → `0x0014`。
- 新增导出 `Verthys_NotifyRuntimeGuards(uint32_t flags)`（写入进程级完整掩码，非累加 OR）；加入 `verthys.def`。flags 定义：bit0=heartbeat 已运行，bit1=suspend_lock 已接线；C 将其并入 `policy_flags`。worker 维护完整掩码：心跳启动置 bit0；主进程通过内部 worker op `runtime_guards` 下发 bit1（停止守卫时下发 0），worker 合并后调用 FFI。
- 版本协商：`WORKER_KNOWN_API_VERSION` 同步 `0x0014`；旧 worker 加载新 DLL 必须拒绝；新 worker + 旧 DLL 时追加字段保持零值，按“证据不可用”降级。
- Rust FFI `VerthysSecurityStatusC`、worker `SecurityStatusReport`、controller `SecurityStatusReport`、TS `SecurityStatusReport` 同步扩展；`useDefenseStatus.ts` 消费原因码。
- 更新 `README.md`、`docs/CORE_API.md`、`docs/SECURITY_DESIGN.md`、`docs/ARCHITECTURE.md`、updater 清单的 API 版本断言。

## 6. 风险与回滚

| 风险 | 触发 | 对策 | 回滚 |
| --- | --- | --- | --- |
| ABI 布局错位 | C/Rust 结构不一致 | `_Static_assert` 偏移 + Rust `size_of` 测试 + 版本协商 | 回退 WP-02，保留旧结构 |
| 安全分配失败导致解锁失败 | 内存紧张/预算拒绝 | 明确返回 `VTY_E_RESOURCE`；不静默回退 | 回退 WP-03 |
| 应急清钥与并发使用冲突 | KILL 时其他线程仍持句柄 | KILL 仅终止路径；DEGRADE 走 ctx 锁；测试覆盖 | 回退注册范围 |
| Hook 扫描误报 KILL | Windows 热补丁/非标准 stub | 两级处置；首次 telemetry；二次 KILL；目标限 ntdll stub | 回退 WP-08 |
| 心跳误杀 | 系统极端卡顿 | 3 秒阈值 + 线程状态确认；心跳线程独立 | 回退 WP-09 |
| 心跳事件被伪造 | 同用户进程枚举命名对象 | 匿名事件 + `DuplicateHandle` + 句柄值签名传递 | 回退 WP-09 |
| 挂起锁库超时 | 存储 flush 慢 | 3 秒超时后终止 worker；保证不悬挂 | 回退 WP-04 |
| 电源事件误锁 | 频繁显示器关闭 | 仅 `PowerSuspend` 恒锁；`DisplayOff` 保持高安全门控 | 调整门控 |
| WER API 缺失 | 旧版 Windows | 动态解析失败仅诊断；不改变状态 | 无需回滚 |
| V3 代码迁出导致链接失败 | 遗漏调用点 | 先全仓检索 + 分对象构建；测试/legacy 覆盖 | 回退 WP-12 |

## 7. 验收定义（DoD）

1. 缺陷登记表 D-01～D-15 全部关闭，或有用户书面确认的“暂缓项”（仅允许内核托管与自动轮换暂缓）。
2. 7 路径状态矩阵经人工核对：锁定态无虚假阻断；休眠启用时解锁态为 4 阻断 + 3 降级（2 项已加固 + 1 项环境降级）；休眠禁用时为 5 阻断 + 2 降级（均为已加固项）；原因码与 UI 文案一致。
3. `defense_closure.c` 不再引用 V3 CNG 计数器/三权分立；产品构建不再链接 V3 防御代码。
4. V4 `VtyVault`/`VtyStore`/轮换口令全部经安全路径分配与注册；KILL 清钥测试通过。
5. 系统锁屏/注销/断连/挂起触发真实锁库；挂起 worker 3 秒内被处置。
6. Hook 扫描与休眠检测有真实证据，且无误杀 KILL（测试覆盖）。
7. 全量门禁绿：C/Rust/TS/攻击/发布构建。
8. 文档、审计口径、API 版本、测试数量全部同步。
9. 无新增死代码：每个新增函数/导出均有生产调用点与测试；被替换代码已删除。

## 8. 方案自审结论

- D-01～D-15 每条缺陷均有唯一工作包与至少一项测试覆盖（见附录 D），无悬空缺陷。
- WP-01～WP-13 每个工作包均定义了文件、实施内容、验收标准与测试，无“仅描述目标”的空包。
- 阶段依赖无环：P0 内部按 WP-01→02→03→04→05→06→11；P1 依赖 P0 的 facts/原因/事件；P2 依赖 P0 的判据删除与应急注册。
- 每阶段均有独立门禁与回滚点；任一门禁失败即停止，不带缺陷推进。
- 方案明确列出非目标与残余风险，未把“内核托管暂缓”“瞬时栈明文”包装成已解决。
- 本方案不改变“不在内核态实施”的用户约束；所有 BLOCKED 结论均可由当前进程/会话事实复现。
