# Verthys 升级与优化方案汇总

> 本文汇总**可升级项**与**更优处理方案**，与 03 的“必修阶段”分离：03 是**必须做**（缺陷修复），本文是**建议做**（增强）。
> 每项给出：现状（含证据）→ 建议方案 → 收益 → 成本 → 风险 → 优先级。
> 优先级：A（建议尽快）、B（中期）、C（长期/可选）。

---

## 1. 依赖与供应链

### 1.1 `vue` 及传递依赖升级（A）
- **现状**：`package.json:23` `"vue": "^3.5.13"`；实测 `npm audit` 命中 `vue 3.2.13–3.5.41` 漏洞区间（F1）。
- **建议**：升至 `^3.5.42`（或当前最新稳定），连带刷新 `@vue/server-renderer`。
- **收益**：清依赖门；消除供应链告警。
- **成本**：低（升版本 + 回归）。
- **风险**：组件行为差异（须以 `vitest` + GUI 实测覆盖）。
- **备注**：本项与 03 Phase 1 重叠——Phase 1 为**必修**，此处强调**version 策略**建议：npm 侧建议与 Rust 侧看齐，考虑对关键运行时依赖使用更严格锁定（或在 `package-lock.json` 基础上加 `overrides` 固定传递依赖）。

### 1.2 引入 Rust 依赖漏洞门（B）
- **现状**：`ci/` 有 `verify_vendor_hashes.ps1`、依赖快照，但**未见 `cargo audit` / `cargo-deny`**（02 清单 G-2 标注待核验）。
- **建议**：引入 `cargo-deny`（advisories + licenses + bans + sources 四合一），纳入 `run_ci.ps1`。
- **收益**：Rust 供应链（含传递依赖）漏洞/许可证自动拦截，与 npm audit 对齐。
- **成本**：中（工具引入 + 规则配置 + 白名单治理）。
- **风险**：初始告警量可能大，需分批治理（避免门一开就红）。
- **优先级**：B（建议随 Phase 1 后立项）。

### 1.3 SBOM 纳入发布产物（C）
- **现状**：记忆显示存在 SBOM（cyclonedx）为“可观测产物、不影响功能门禁”。
- **建议**：把 SBOM 生成与存档纳入发布流程（每次发布产出并存档），并校验与 `package-lock.json`/`Cargo.lock` 一致。
- **收益**：供应链可追溯、审计友好。
- **成本**：低。

## 2. panic 面与错误处理范式

### 2.1 统一“受控错误路径”范式（A）
- **现状**：生产路径 unwrap/expect 残留 21 处（F4）；模块内风格不一（有的 `?`，有的 `unwrap_or_else`）。
- **建议**：
  1. 定义统一范式：锁 → `unwrap_or_else(|e| e.into_inner())`（自愈）；IO/外部 → `?` 或显式 `match` + 日志；不可恢复 → 显式返回错误码（不 panic）。
  2. 在 `util/error.rs` 建立错误类型与转换（若已存在则补充覆盖）。
  3. CI 锚点守护（03 Phase 2C）。
- **收益**：消除 panic 面；风格一致；新代码有范式可循。
- **成本**：中。

### 2.2 前端错误边界与兜底（B）
- **现状**：前端有全局 toast 中心（`useToastCenter`），但组件级错误边界情况未系统化。
- **建议**：为关键模块加 Vue `errorCaptured` / 全局 `app.config.errorHandler` 兜底，避免单组件异常拖垮整页面。
- **收益**：健壮性提升。
- **成本**：低-中。

## 3. 架构与分层

### 3.1 分层基线清零（B）
- **现状**：`ci/ast_baseline.txt` 25 条“反向导入”豁免（F8）。
- **建议**：两条路径并行——
  1. 合理横切 → 扩充 `LAYER_HIERARCHY` 白名单（如明确 `state/` 为共享状态层，允许 controller/中间层引用）；
  2. 技术债 → 重构（如 util 引用上层者下沉接口）。
- **收益**：分层门从“豁免通过”变为“真实通过”，架构约束可信。
- **成本**：中-高（需逐条判定）。
- **风险**：误判将放松约束——**必须逐条书面裁定**。

### 3.2 建立 ADR（架构决策记录）（B）
- **现状**：审计报告已落在 `docs/ProductionAudit/`；当前无 ADR 目录，决策散落在修复台账。
- **建议**：新建 `docs/adr/` 存放 ADR，记录关键决策（如 layer2 空档、进程模型、KDF 参数、条目与失败语义裁定）。
- **收益**：后人可追溯“为什么这样设计”；避免重复争议。
- **成本**：低（持续投入）。

### 3.3 `layer2` 编号空档显式化（C）
- **现状**：`core/src/security` 无 `layer2_*`（O1）。
- **建议**：在架构文档/ADR 中显式说明编号约定（如 `memory` 承担 layer2 职责），而非留下“疑似缺失”。
- **成本**：极低。

## 4. 注释与规范机械化

### 4.1 注释红线纳入 CI 锚点（A）
- **现状**：注释/日志红线靠人工遵守，实际残留 14 处（F2+F5）。
- **建议**：新增锚点——扫描 `core/src`、`verthys-worker/src`、`verthys-tauri/src-tauri/src` 的 `\.md|docs/|第 *[0-9]+ *项|§`，命中即 red。
- **收益**：红线机械化，杜绝回退。
- **成本**：低（复用既有锚点模式）。
- **风险**：需先清理存量（否则门一开即红）→ 顺序：**先 Phase 2A 清理 → 再上锚点**。

### 4.2 黑名单“自然用语”口径裁定（B）
- **现状**：`依据/来源/方案` 等词在注释中作**自然中文**使用（如“依据 WAL 归属声明”“单一权威来源”），与黑名单字面冲突（02 清单 J-3）。
- **建议**：裁定口径——
  - **违规**：引用外部文档/编号（含“见/参考/详见/参见 + 文档/编号”）。
  - **可接受**：不作外部引用的自然用语。
  - 落地为正则规则（区分上下文），而非无条件禁词。
- **收益**：规范可执行、不误伤。
- **成本**：低-中（正则设计需谨慎，避免误报/漏报）。

### 4.3 注释“解释 Why”抽查机制（C）
- **建议**：代码评审清单加入“复杂逻辑分支注释须解释 Why”的抽查项。

## 5. 死代码与桩治理

### 5.1 移除模块级 `allow(dead_code)` + 定期死代码清理（A/B）
- **现状**：`lib.rs:62-74` 7 处模块级抑制（F7）；另有桩函数（F3）。
- **建议**：
  1. Phase 3B 移除模块级抑制、逐项处置真实死代码；
  2. 建立“死代码定期清理”流程（结合 grep + 编译器标记 + 文档裁定，沿用项目既有交叉验证方法）。
- **收益**：代码面真实收敛；降低维护成本。

### 5.2 进程模式收敛（A）
- **现状**：`--mode worker|inspector` 桩（F3）。
- **建议**：收敛为单模式（UI）或显式失败；若保留规划，写入 ADR + 路线图。
- **收益**：消除误导；明确进程模型。

## 6. 可观测性与运维

### 6.1 结构化日志字段标准化（B）
- **现状**：日志有模块前缀（`[module]`），但字段结构不统一。
- **建议**：定义固定字段（`trace_id`、`op`、`cost_ms`、`result`），关键路径（IPC、解密、IO、切档）统一输出；沿用既有脱敏管线。
- **收益**：可聚合分析、排障更快。

### 6.2 健康检查与自愈可见化（C）
- **建议**：为 worker 就绪、看门狗重启、熔断触发等建立“系统健康摘要”（前端可查），让异常可见。

### 6.3 审计事件覆盖度补全（B）
- **现状**：审计事件类型较全（含预设置/完整性/痕迹清理等）。
- **建议**：核对“每条安全关键操作是否都有审计点”，补缺口（02 清单 C/F 域）。

## 7. 性能

### 7.1 长任务下沉与预算（B）
- **现状**：前端已有“解密下沉 Worker”等实践。
- **建议**：系统梳理主线程重任务清单（哈希/解密/大列表渲染），全部下沉或分帧；建立“渲染预算”守护测试（已有 `frame-budget.spec.ts`，可扩展）。

### 7.2 大文件路径与背压（B）
- **建议**：核对导入/导出的分片读取与背压（分片大小、累计上限、背压阈值）在真实大文件下的表现，形成基准数据。

## 8. 安全增强

### 8.1 Release 产物 Authenticode 签名（A）
- **现状**：未签名 Release 每次启动产生 `INTEGRITY_CHECK` Failure 审计（观测项，见 01 §7 观察项）。
- **建议**：发布流程接入 Authenticode 签名，使启动自完整性核验为 Success（同时提升分发可信度、消除审计噪音）。
- **收益**：安全 + 观测双重收益。
- **成本**：中（证书 + 签名流程接入 CI/发布）。

### 8.2 C 侧静态分析工具补齐（B）
- **现状**：本机 `clang-tidy` 缺失，相关门不可跑（02 清单 I-12 相关）。
- **建议**：在 CI 环境（Linux/Win）安装 LLVM 工具链，启用 `clang-tidy`（UAF/栈地址逃逸/内存）与 MSVC `/analyze`。
- **收益**：C 内存安全静态兜底。
- **风险**：初始告警治理成本。

### 8.3 依赖完整性校验常态化（B）
- **建议**：`verify_vendor_hashes.ps1` 纳入 `run_ci.ps1` 常态执行；第三方哈希清单随依赖升级同步刷新。
