# Verthys 全项目摸排与风险识别报告

> 证据分级：【已证实】= 静态取证/门禁实测；【待核验】= 需运行态或手工确认；【已排除】= 经取证判定非缺陷。

## 1. 系统总览

### 1.1 进程模型（【已证实】）

```
┌──────────────────────────────────────────────────────────────────┐
│ 主 UI 进程（Tauri，含 WebView）  verthys-tauri/src-tauri          │
│   main.rs:67-77 按 --mode 派发（默认 ui，实际仅 ui 生效，见 F3）  │
│   lib.rs:322-329 .manage(AppState) + .manage(SecurityState)       │
├──────────────────────────────────────────────────────────────────┤
│ verthys-worker 子进程（独立 exe，Rust，无 WebView）              │
│   worker/session.rs:128-134  spawn: verthys-worker.exe <dll_path> │
│   CREATE_NO_WINDOW | BELOW_NORMAL_PRIORITY_CLASS，kill_on_drop    │
├──────────────────────────────────────────────────────────────────┤
│ C 核心安全 DLL（verthys.dll，由 worker 侧动态加载并 FFI 调用）    │
│   core/src/{api,container,crypto,index,security,transaction}      │
└──────────────────────────────────────────────────────────────────┘
```

- **信任边界**：主进程**永不加载 DLL、永不持有 VerthysHandle**，敏感运算全部下沉 worker 子进程（`lib.rs:44-47`）。子进程退出即销毁全部密钥与句柄。
- **通信**：宿主 ↔ worker 走 stdin/stdout JSON 行协议（`worker/actor.rs:177-260`、`main_loop.rs:45-101`）。

### 1.2 入口面（【已证实】）

| 入口 | 位置 | 约束 |
| --- | --- | --- |
| `main.rs` | `verthys-tauri/src-tauri/src/main.rs` | 入口单一职责（仅 6 项）；第一行安装 minimal panic hook；禁止加解密/IO |
| `lib.rs` | 同上 `lib.rs` | 模式派发 + 资源注册 + 命令注册（93 个 `#[tauri::command]`） |
| `run_process` | `lib.rs:216-301` | 参数解析 → 数据目录 → 日志管道 → panic hook → 资源守卫 |

### 1.3 命令面（【已证实】）

- `#[tauri::command]` 共 **93 处 / 19 文件**（实测）。分布：`controller/*` 64 处、`security_commands/commands/*` 29 处。
- 敏感命令授权闸门：`security_commands/auth.rs:20-25`（`require_session_authorized`：仅 `Locked/Unlocked` 放行，`NoKey` 拒绝）。
- 导入域批量命令闸门：CI 锚点 4 要求 `verthys_batch_controller.rs` 内 `require_unlocked` ≥ 8 处（防回退）。

## 7. 风险与缺陷台账（【已证实】部分）

> 严重度定义：**P1** = 影响安全/合规或阻断发布；**P2** = 明显质量/维护风险；**P3** = 轻微或一致性；**观测** = 待澄清。

### F1 ·【P1】依赖供应链：npm audit 3 条 high

- **证据**：`npm audit --json` → `metadata.vulnerabilities.high = 3`（critical/moderate/low 均 0）：
  1. `@vue/server-renderer` — high — *XSS via missing CR in attribute-name blacklist* — `fixAvailable: true`
  2. `source-map-js`（1.0.0–1.2.1）— high — *DoS via indexed source-map section offsets*（GHSA-68fv-2mgg-jv7q）— `fixAvailable: true`
  3. `vue`（3.2.13–3.5.41）— high — 传递依赖 `@vue/server-renderer` — `fixAvailable: true`
- **版本基线**：`package.json:23` `vue: ^3.5.13`（需 ≥ 3.5.42 方脱离漏洞区间）。
- **运行态可达性（静态判断）**：Verthys 为桌面应用，**不启用 Vue SSR**，`@vue/server-renderer` 不在运行路径；`source-map-js` 为构建期（Vite）依赖 → 运行态可直接利用性**低**。但依赖门禁（`npm audit --audit-level=high`）为退出码 1，属**合规阻断**。
- **影响**：CI/发布链若以 `npm audit` 为门禁则直接失败；供应链合规不达标。
- **建议**：升 `vue ≥ 3.5.42`（连带 `@vue/server-renderer`）；`npm audit fix` 处理 `source-map-js`；升级后复跑 `npm audit --audit-level=high` 至 exit 0。
- **红线**：升级后必须复跑 `vitest`（388）与 `vue-tsc`，禁止直接跳过验证合入。

### F2 ·【P2】注释/日志红线：外部文档名 + 条款号（4 处）

- **证据**：
  - `verthys-tauri/src-tauri/src/security/cleanup.rs:619` — `"[secure_delete] SECURITY.md 第 2 项：检测到稀疏文件..."`
  - `verthys-tauri/src-tauri/src/security/cleanup.rs:702` — `"... SECURITY.md 第 2 项：覆写超过 {} 秒上限..."`
  - `verthys-tauri/src-tauri/src/security/usb_guard.rs:559` — `"... SECURITY.md 第 6 项：USB 注册表已达上限..."`
  - `verthys-tauri/src-tauri/src/security/usb_guard.rs:918` — `"[shadow_sleep] SECURITY.md 第 7 项：定时器到期..."`
- **性质**：同时含**文档名**（`.md`，黑名单词）与**条款号**（“第 N 项”），违反“注释/日志禁止外部文档引用与编号”红线。且属运行期日志串，会写入日志文件。
- **影响**：合规不达标；日志中泄露内部文档结构。
- **建议**：删除 `SECURITY.md 第 N 项：` 前缀，改为自包含语义描述（如“检测到稀疏文件，仅覆写已分配区域”）。

### F3 ·【P2】进程模式桩函数（死代码 + 误导）

- **证据**：
  - `verthys-tauri/src-tauri/src/lib.rs:583` — `// TODO：接入 WorkerSession Actor 主循环` 后 `loop { sleep(60s) }`（`run_secure_worker`）
  - `verthys-tauri/src-tauri/src/lib.rs:595` — `// TODO：接入安全巡检逻辑` 后 `loop { sleep(60s) }`（`run_inspector_proc`）
  - `verthys-tauri/src-tauri/src/main.rs:71-76` — `--mode worker|inspector` 派发至上述桩
  - 实际 worker：`worker/session.rs:128-129` 以 `verthys-worker.exe <dll_path>` 启动，**不带 `--mode`**
- **性质**：`--mode worker/inspector` 在本项目**不可达/无用**（真实 worker 为独立 exe）；桩函数若被误用将永久挂起且无就绪信号。
- **影响**：误导性死代码；维护者可能误认为存在进程内 worker 模式。
- **建议**：二选一——(a) 删除桩与 `--mode worker|inspector` 分支（保留 `ui`）；(b) 若确有规划，实现并挂门禁。**禁止保留无说明的桩**。

### F4 ·【P2】生产路径 panic 面：21 处（含 3 处测试模块）

- **证据**（脚本实测：`#[cfg(test)]` 之前的 `.unwrap()/.expect()`）：
  | 文件 | 生产路径数量 |
  | --- | --- |
  | `security/session_guard.rs` | 6 |
  | `infrastructure/shared_memory.rs` | 4 |
  | `security/background_patrol.rs` | 3 |
  | `security_commands/tests.rs` | 3（`mod tests` 由 `#[cfg(test)]` 门控，实为测试） |
  | `infrastructure/log_pipe.rs` | 2 |
  | `lib.rs` | 1 |
  | `infrastructure/console_handler.rs` | 1 |
  | `infrastructure/path_resolver.rs` | 1 |
- **性质**：多数为 `Mutex::lock().unwrap()`（锁中毒即 panic）与线程 `spawn(...).expect(...)`。历史曾达 200+，现已大幅治理。
- **影响**：理论 panic 面；在 `panic = "unwind"` 配置下由 catch_unwind/hook 兜底，但生产路径仍应清零。
- **建议**：按模块逐个改为受控错误路径（`unwrap_or_else(|e| e.into_inner())` 或显式错误传播），并在 CI 增加“src-tauri 生产路径 unwrap 计数不得上升”的防回退锚点。

### F5 ·【P3】注释/日志红线：孤立条款号（10 处）

- **证据**：
  - `security/brute_force.rs:309,324,335,402` — “第 2/4/3 项”
  - `security/session_guard.rs:359,682,692,712,798,815` — “第 2/6/3 项”
- **性质**：无文档名但仍是**外部条款编号引用**（脱离外部文档无法理解“第 N 项”指什么）。
- **建议**：删除“第 N 项”前缀，改写为自包含描述。

### F6 ·【P3】清零规范：全仓唯一 `ZeroMemory`

- **证据**：`core/src/security/anti_analysis/anti_debug_v2.c:106` — `ZeroMemory(&ctx, sizeof(ctx));`（全仓唯一；其余为 `SecureZeroMemory` / `verthys_secure_zero`）。
- **性质**：该处为 `GetThreadContext` 前的**预清零**，用毕敏感清零已由 `verthys_secure_zero`（`:122`）承担 → **功能安全影响低**；但项目红线曾要求此处置为 `SecureZeroMemory`，属**已知项未闭环**。
- **建议**：改为 `SecureZeroMemory`（或 `verthys_secure_zero`）以统一口径并消除“唯一例外”。

### F7 ·【P3】模块级 `#[allow(dead_code)]`（7 模块）

- **证据**：`verthys-tauri/src-tauri/src/lib.rs:62-74` — 对 `controller`、`entry_template`、`infrastructure`、`middleware`、`repository`、`service`、`util` 施加模块级 `allow(dead_code)`。
- **性质**：整模块范围内**私有**死代码不再被编译器标记（pub 项在 lib crate 本就不告警）。
- **影响**：死代码检出能力被削弱。
- **建议**：移除模块级 allow，改为对确实需要的少量项精确豁免（`clippy -D warnings` 将暴露真实死代码）。

### F8 ·【P3】分层门 25 条“反向导入”存量豁免

- **证据**：`ci/ast_baseline.txt:2-26`（25 条 `反向导入|<file>|<line>`）：`controller/*` 引用 `state/`、`security/`；`infrastructure/shared_memory.rs`、`repository/verthys_repository.rs`、`service/verthys_service.rs`、`util/mod.rs` 等。
- **性质**：分层白名单（`ast_analyze/src/main.rs:44-51`）**不含** `state/`、`security/`、`worker/`，故这些引用被判“反向导入”并以基线豁免通过。
- **影响**：分层门部分以豁免通过；需判断这些引用是**合理横切**还是**技术债**。
- **建议**：逐条复核（见 02 清单 A-3）；对合理者补入白名单（消除豁免），对不合理者重构依赖方向。

### O1 ·【观测】`layer2` 层缺失

## 9. 摸排结论

- **架构骨架健壮**：进程隔离、分层（主红线无违规）、单一事实源、原子写与补偿机制齐备；门禁体系（版本/锚点/常量/导出/AST）已机械化。
- **主要风险集中在“合规与债”**：依赖漏洞（F1）、注释红线残留（F2/F5）、桩死代码（F3）、panic 面残留（F4）、死代码抑制（F7）、分层豁免（F8）。
- **不存在**在静态取证中已确证的 P0（致命功能/安全失效）缺陷；但**运行态与业务全链路（V1–V8）必须实测后才能下最终结论**。
