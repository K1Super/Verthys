# G0-A2 — 批量导入锚点推迟：安全评审

> 状态：评审完成，判定“有条件通过原型” · 最后更新：2026-11-18 · 维护人：K1Super
>
> 评审对象：[G0-A2-DEFERRED-ANCHOR-DESIGN.md](G0-A2-DEFERRED-ANCHOR-DESIGN.md)
>
> 结论：方向可接受，但必须先落实以下安全约束才能进入隔离原型：
> 硬上限由 C 层强制；Begin 先提交当前锚点；非导入写入在会话中拒绝；
> Commit/Flush/Lock/Deinit 必须收口；失败一律锁定（fail-closed）。

---

## 1. 资产与目标

| 资产 | 说明 |
|---|---|
| 回退锚点 | `rollback.state`：每库 generation + 见证槽 + 公钥指纹，设备密钥 MAC 保护 |
| 容器 generation | 单调递增；低于锚点必须拒绝 |
| TPM 见证密钥 | 每次锚点推进轮换；旧键删除/撤销 |
| 导入数据 | 新增的照片块与 meta 记录；不修改既有记录内容 |

安全目标：

1. 旧于锚点的容器状态必须拒绝。
2. 锚点滞后必须有界，且不得覆盖导入前已完成的写入。
3. 推迟期间不得执行删除/改密/轮换等会扩大回退影响的写入。
4. 任何锚点提交失败都不得静默降级为“无回退保护”。
5. 不新增密钥材料暴露面，不改变容器与状态文件格式。

## 2. 新增威胁：锚点滞后窗口

推迟期间：

```text
锚点        A  = 最后一次成功提交的 generation
容器        G  = 当前已落盘的 generation，G > A
允许回放    [A, G] 内的任一容器副本（check 只拒绝 < A）
```

窗口内的回放影响：

- 只能回放“新增记录”；删除/改密/轮换在会话中被拒绝。
- 导入前完成的写入已被 Begin 的预提交覆盖，不在窗口内。
- 崩溃后窗口持续到下一次解锁；解锁路径会把锚点推进到当前容器代。

因此窗口的实质影响是：**最多丢失窗口内新导入的记录**，不会让已删除的数据复活。
这是本方案可接受的前提，也是评审的核心判断。

## 3. 关键发现

### F1（严重）推迟必须由 C 层硬上限约束

调用方可以忘记 Commit、崩溃或故意保持会话。仅依赖宿主调用 `Commit` 会让
窗口无界。

要求：

- `MAX_GENS`（建议 32）与 `MAX_MS`（建议 30s）编译进 C 层，不提供运行期放大。
- 每次保存检查代数差与时长；任一超限即在本次保存内强制提交锚点。
- 上限触发后的提交失败必须锁定会话（`v->unlocked = 0`），与现有
  `vty_vault_save_meta` 失败路径一致。
- 必须有“第 32 代未推进保存触发提交”“31s 后首次保存触发提交”的用例。

### F2（严重）Begin 必须先提交当前锚点

若 Begin 只置标志，窗口会覆盖从上次保存到 Begin 之间的所有写入（可能包含
上一次导入之外的删除/修改）。

要求：

- `Verthys_BulkImportBegin` 先调用一次 `vty_rollback_commit(current_generation)`，
  成功后才置 `defer_anchor`；失败则 Begin 失败、不进入会话。
- 代数未变化时该预提交只做见证校验（约 15–47ms）；存在未推进写入时才建键。
  不得为了省一次提交而跳过。

### F3（高）会话中拒绝非导入写入

删除、导入、改密、PCR、keyfile、模块、轮换等操作若在窗口内执行，会把
“数据复活”纳入回退影响。

要求：

- 上述入口检测到 `defer_anchor` 时返回 `VERTHYS_ERR_POLICY`，不做隐式提交。
- 调用方必须先 `BulkImportCommit`。
- 需要逐一覆盖公共 API，不能只覆盖 `DeleteRecord`。

### F4（高）Commit/Flush/Lock/Deinit 必须收口

要求：

- `BulkImportCommit`：清除会话 → 提交锚点 → 成功返回；失败锁定并返回错误。
- `Flush`：提交锚点并保留会话（重置 floor 与计时）。
- `Lock`/`Deinit`：释放密钥前尝试提交；失败时 Lock 返回错误、Deinit 记录
  结构化日志，密钥仍清零。不得留下“已解锁但锚点滞后”的活动会话。
- 任何路径都不得在未成功提交的情况下静默清除 `defer_anchor` 并继续写入。

### F5（高）上限触发的提交发生在容器写入之后

保存流程是“写容器元数据 → 回读认证 → 提交锚点”。上限触发时容器已落盘，
提交失败只能锁定，不能回滚容器。

要求：

- 与现有失败语义一致：`v->unlocked = 0`，返回错误；下次解锁补推进。
- 调用方可能看到“写入返回错误但数据已落盘”；这是现有锚点失败路径的既有
  行为，必须在 API 文档中说明，避免上层误重试造成重复记录。

### F6（中）崩溃后的窗口必须被接受而不是判损坏

要求：

- 打开路径不得把 `container_gen > anchor_gen` 判为损坏；现有
  `vty_rollback_check` 已允许，补用例锁定该语义。
- 解锁后的 `commit` 必须把锚点推进到当前代；失败按 F4/F5 处理。
- 崩溃注入覆盖：推迟保存中 kill、上限提交中 kill、Commit 中 kill。

### F7（中）旧 DLL/旧宿主的特性探测

要求：

- worker 按可选符号解析 `Verthys_BulkImportBegin/Commit`；缺失时返回“不支持”。
- 宿主不得在 Begin 未成功时假设推迟已生效；回退路径仍是逐次锚点提交。
- 不得出现“Begin 被忽略但仍按会话结束处理”的静默降级。

### F8（中）并发与单写者约束

要求：

- `defer_anchor` 的读写必须在 `ctx->api_mutex` 内，与 AddRecords/Lock 串行。
- 推迟会话只适用于单写者场景；同一 vault 的其他进程写入不在本设计承诺内，
  需在文档中明确（现有导入写者已是单写者）。
- 多线程 AddRecords 与会话边界需有并发用例。

### F9（中）会话超时与看门狗

C 层上限只在“下一次保存/提交”时触发；进程保持空闲时窗口会一直存在到
Lock/Deinit。

要求：

- 宿主 import writer 对超过 60s 未结束的会话强制 `Commit`（或取消导入后 Commit）。
- `Lock`/`Deinit` 必须收口。
- 由于窗口只覆盖新增记录且上限 32 代/30s，空闲延长不扩大窗口深度，
  但会延长“可回放副本仍被接受”的时间；按中风险接受并记录。

### F10（低）日志与指标

- 记录会话开始/结束、滞后代数、强制提交次数与失败分类。
- 不记录容器 UUID 明文、路径、密钥名与指纹之外的密钥材料（沿用现有规范）。

### F11（低）API 暴露面

- 新 API 只影响调用方自己的已解锁会话；不能跨库、不能用于锁定态，
  不构成权限提升。
- 仍应在 `verthys.h` 中明确：推迟期间的安全语义、上限与失败行为。

## 4. 安全不变量

| 编号 | 不变量 |
|---|---|
| I1 | 容器代始终 ≥ 锚点代 |
| I2 | 进程活动期间滞后 ≤ `MAX_GENS` 且 ≤ `MAX_MS` |
| I3 | 窗口不覆盖 Begin 之前的写入 |
| I4 | 会话中只允许新增记录，非导入写入被拒绝 |
| I5 | 锚点提交失败后库被锁定，不再接受写入 |
| I6 | 低于锚点的容器状态仍被拒绝 |
| I7 | Begin/Commit/Lock/Deinit 之外的路径不得改变推迟状态 |
| I8 | 不改变 G0-A 的密钥/槽位不变量与 `rollback.state` 布局 |

## 5. 滥用用例与预期

| 用例 | 预期 |
|---|---|
| 打开会话后忘记 Commit，继续写 32 代 | 第 32 代未推进保存触发提交；滞后回到 0 |
| 打开会话后空闲 5 分钟再写 | 下一次保存因时长上限强制提交（或 Lock 时提交） |
| 会话中调用 DeleteRecord | 拒绝 `VERTHYS_ERR_POLICY`，锚点不变 |
| 会话中调用改密/轮换 | 拒绝；调用方必须先 Commit |
| Begin 时锚点提交失败 | Begin 失败，不进入推迟；库锁定 |
| Commit 时 TPM 删除/创建失败 | Commit 返回错误并锁定；下次解锁补推进 |
| 导入中进程被杀 | 容器代 > 锚点；下次解锁接受并补推进；再下一次可回放窗口关闭 |
| Commit 后回放窗口内的副本 | 拒绝（容器代 < 锚点） |
| 旧 DLL 无新符号 | worker 返回不支持；宿主走逐次提交，行为与现状一致 |
| 并发 AddRecords + Commit | 互斥串行；不得出现半提交或状态撕裂 |

## 6. 评审判定

**有条件通过原型**，前置条件：

1. F1 硬上限（代数 + 时长）由 C 层强制并有触发用例。
2. F2 Begin 预提交成功后才进入会话。
3. F3 非导入写入拒绝清单覆盖全部公共写入口。
4. F4 Commit/Flush/Lock/Deinit 收口与失败锁定语义落地。
5. F5/F6 崩溃与回放用例覆盖窗口边界。
6. F7 旧 DLL/旧宿主特性探测与回退路径。
7. F9 宿主看门狗与会话超时。

未满足前不得进入生产实现；通过隔离原型后仍需产品确认窗口上限与失败提示。

## 7. 残余风险

| 风险 | 处置 |
|---|---|
| 窗口内最多 32 代/30s 的新增记录可被回放 | 设计已限定为新增记录；产品确认可接受；上限不可由调用方放大 |
| 进程空闲时窗口持续到 Lock/Deinit | 宿主看门狗 60s 强制提交；空闲不扩大深度 |
| 上限触发提交失败导致“数据已落盘但 API 报错” | 与现有锚点失败语义一致；文档说明；解锁后补推进 |
| 推迟减少 TPM 轮换次数、旧键存活更久 | 威胁模型不含 TPM 私钥提取；每次提交仍删除/撤销旧键 |
| 多进程同时写同一 vault | 超出设计范围；导入写者必须保持单写者 |
| 没有 NV 单调计数器 | 窗口无法彻底消除；接受有界窗口 |
