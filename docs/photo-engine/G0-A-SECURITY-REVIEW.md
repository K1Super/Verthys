# G0-A — TPM 见证密钥预置：安全评审

> 状态：安全评审判定“有条件通过原型”；隔离原型已提供部分证据，生产化验证仍待执行 · 最后更新：2026-11-18 · 维护人：K1Super
>
> 评审对象：[G0-A-DESIGN.md](G0-A-DESIGN.md)
>
> 结论：设计方向可接受，但必须先修正以下安全约束，才能进入原型：
> 旧键删除失败必须 fail-closed；新库首次提交前不得预置；预置键必须验证后才可引用；
> 已验证条目缓存必须可证明；关闭/崩溃必须清理未引用键。

---

## 1. 资产与安全目标

| 资产 | 说明 |
|---|---|
| 回退锚点状态 | `rollback.state`：每库 generation + witness slot + 公钥指纹，设备密钥 MAC 保护 |
| TPM 见证密钥 | 持久化 ECDSA P-256 密钥，不绑定 PCR；旧状态回放时指纹必须不符 |
| 容器 generation | 单调递增；低于锚点必须拒绝 |
| 预置密钥槽 | 已创建但未被状态引用的下一把见证密钥 |
| 已验证条目缓存 | 进程内缓存，避免每次提交打开 TPM 校验 |

安全目标：

1. 任何旧 generation 的状态回放都必须 fail-closed。
2. 旧 generation 对应的 TPM 密钥必须在提交成功后不可再作为有效见证。
3. 预置键不得被任何当前或历史有效状态引用，直到提交写入其指纹。
4. 崩溃、断电、TPM 故障、删除失败均不得静默降级为“无回退保护”。
5. 预置机制不得新增密钥材料泄露面，不得记录私钥/密钥句柄。

## 2. 威胁模型

| 威胁 | 能力 |
|---|---|
| 本地回放攻击者 | 可复制/替换 `rollback.state`、容器文件、旧备份；不能伪造 MAC、不能导出 TPM 私钥 |
| 本地恶意进程 | 可尝试打开/覆盖同名 TPM 键、并发提交、删除状态文件 |
| 崩溃/断电 | 任意时刻终止进程/断电 |
| TPM 故障 | 建键、打开、删除、Finalize 失败；TPM 被清除 |
| 应用自身缺陷 | 锁顺序、缓存、失败路径、关闭顺序错误 |

不在范围：拥有管理员/内核权限、可读进程内存、可控制 TPM 固件的攻击者；TPM 私钥泄露。

## 3. 关键发现

### F1（严重）旧键删除失败被忽略

现状 `drop_stale_witness` 忽略 `vty_tpm_witness_delete` 的返回值
（[vty_rollback.c](file:///c:/Users/Administrator/Desktop/Verthys/core/src/security/rollback/vty_rollback.c#L472-L483)）。

后果：状态已指向新键，但旧键仍存在；攻击者回放旧状态文件时，旧键指纹仍匹配，
回退保护被绕过。

要求：

- 提交成功后必须确保旧键失效；删除失败时调用 `revoke`（OVERWRITE 原槽）使旧指纹失效。
- 删除与撤销都失败 → 返回错误并把该库锚点标记为 `ANCHOR_DIRTY`，后续提交 fail-closed。
- 启动/解锁清理未引用槽失败同样 fail-closed。
- 必须新增故障注入测试，证明删除失败不会返回成功。

### F2（严重）新库首次提交前不得预置

现状新库提交检查 `any_new != 0` 即拒绝
（[vty_rollback.c](file:///c:/Users/Administrator/Desktop/Verthys/core/src/security/rollback/vty_rollback.c#L580-L587)）。
预置键会让 `vty_tpm_witness_any` 返回 1，导致新库首次提交被误判为回退。

要求：

- 只有 rollback.state 中已存在该库条目（即首次提交已完成）后，才允许预置。
- 新库首次提交仍走同步建键；之后后台补预置。
- 或者引入可验证的“未引用预置键”标记，但不得仅凭键存在就放行；默认采用“首次提交后再预置”。

### F3（高）预置键必须在使用前验证

预置键在后台创建，可能被其他进程覆盖、删除，或 Finalize 未真正持久化。

要求：

- 预置键只有在 `create + Finalize + fingerprint` 全部成功后才标记 READY。
- 提交取用预置键前必须验证其指纹（可缓存建键时的指纹，但需确认键仍存在且匹配）；
  验证失败则丢弃并回退同步建键。
- 不能用“内存里有指纹”替代“TPM 里确实存在匹配键”。

### F4（高）已验证条目缓存必须可证明

缓存跳过 TPM 校验，必须保证不会接受回放状态。

要求：

- 缓存键必须包含 `vault_uuid + generation + slot + fingerprint`，与状态文件条目逐字段比较。
- 只有完全一致才跳过 TPM 校验；任一字段不同必须重新校验。
- 缓存只保存在进程内，锁库/登出/Deinit 清空并零化。
- 跨进程提交导致状态变化时，缓存不匹配，必须重新校验。
- 缓存不得成为“状态文件被替换但仍放行”的路径；状态 MAC 校验必须先通过。

### F5（高）预置键与旧状态引用关系

预置槽可能正是上一代状态引用的槽。覆盖/删除它会使上一代状态失效，这是期望行为；
但必须确保**当前状态**引用的槽永远不被预置线程覆盖。

要求：

- 池状态必须记录 `current_slot`，预置只允许写非当前槽。
- 提交切换 current_slot 后，先删除旧键，再把旧槽标记为 FREE 并允许后台补池。
- 锁顺序固定：`RollbackState` → pool lock；后台建键不得反向持有。
- 多库场景下按 `witness_id` 分区；不得跨库复用槽位。

### F6（高）崩溃窗口：状态已写、旧键未删

要求：

- 启动/解锁时扫描当前库的两个槽；删除或撤销所有非当前槽。
- 清理失败 → fail-closed，禁止继续提交。
- 崩溃矩阵测试必须覆盖“状态写后、删键前 kill”。

### F7（中）两槽饥饿与 TPM 争用

后台建键约 397–639ms；连续提交可能在预置完成前到达。

要求：

- 无预置键时允许有界等待，超时后同步建键；不得跳过锚点。
- 导入侧必须合并提交，避免每张照片/每批都推进锚点。
- 若实测两槽不足，再评估第三槽；不得默认扩槽，先验证 TPM 容量。
- 争用导致提交延迟属于可用性风险，不是安全降级；必须在性能报告中量化。

### F8（中）关闭与线程生命周期

要求：

- `vty_rollback_shutdown` 由核心 Deinit 显式调用；停止并 join 后台线程后才能卸载 DLL。
- 关闭时不得在 TPM 调用中途强制 TerminateThread；可等待有限时间，超时留下孤儿键由下次启动清理。
- 预置键、缓存、指纹在关闭时零化。
- 不得在 `DllMain` 内做 TPM/线程操作。

### F9（中）TPM 被清除/重置

要求：

- 当前见证缺失/指纹不符 → 维持现有 fail-closed 行为；不得因预置机制自动重建当前锚点。
- 预置键缺失可重建；当前键缺失必须走既有恢复/重置流程。
- 不得把“预置键存在”误判为“锚点有效”。

### F10（低）日志与错误信息

- 不记录密钥名、指纹以外的私钥材料、路径、容器 UUID 明文（按现有日志规范）。
- 错误分类只返回 `VTY_E_TPM` / `VTY_E_ROLLBACK` 等，不暴露内部槽位细节给前端。

## 4. 安全不变量

| 编号 | 不变量 |
|---|---|
| I1 | 当前状态只能引用已 Finalize、指纹匹配的 TPM 键 |
| I2 | 提交成功后旧键必须已删除或已撤销；否则不得返回成功 |
| I3 | 预置键在提交写入其指纹前，不得被任何状态引用 |
| I4 | 每个库同一时刻至多一个 current slot；预置只写非 current 槽 |
| I5 | generation 低于锚点的状态必须拒绝 |
| I6 | 崩溃后至少有一个状态/键组合可打开；旧 generation 不得同时具备匹配键 |
| I7 | 缓存命中不得绕过状态 MAC 校验；缓存字段必须与状态条目完全一致 |
| I8 | 关闭/卸载前后台线程必须停止；不得留下 TPM 调用 |

## 5. 滥用用例与预期

| 用例 | 预期 |
|---|---|
| 回放旧 `rollback.state` + 旧容器 | 指纹不符/键已删 → fail-closed |
| 删除失败后回放旧状态 | 撤销旧指纹或 `ANCHOR_DIRTY` → fail-closed |
| 预置键被覆盖 | 提交前验证失败 → 丢弃并同步建键；不得写入错误指纹 |
| 新库首次提交前已有预置键 | 不得发生；预置在首次提交后启动 |
| 两进程同时提交 | `RollbackState` 互斥；缓存不匹配则重新校验；不得双 current |
| 状态写失败 | 旧状态/旧键保持有效；预置键可复用或清理 |
| 崩溃在删键前 | 启动清理旧键；清理失败 fail-closed |
| TPM 被清除 | 当前键缺失 → 既有恢复流程；不得自动放行 |
| 关闭时后台建键 | join/超时；孤儿键下次清理；不得卸载后回调 |

## 6. 评审结论

**有条件通过原型**，前置条件：

1. F1 旧键删除失败/撤销/fail-closed 路径设计完成并有故障注入测试。
2. F2 新库首次提交前不预置。
3. F3 预置键使用前验证；F4 缓存字段完整比较。
4. F5/F6 槽位与崩溃清理不变量实现。
5. F8 shutdown 生命周期与线程 join 设计落地。
6. 性能测试证明两槽 + 批量提交可行；若不可行，再评估第三槽或提交合并。

未满足上述条件前，不得进入 Phase 1 生产实现。

## 7. 残余风险

| 风险 | 处置 |
|---|---|
| TPM 删除/撤销双失败 | `ANCHOR_DIRTY` + fail-closed + 恢复流程；需产品确认提示与恢复成本 |
| 后台建键争用导致提交延迟 | 批量提交 + 有界等待 + 同步回退；性能报告量化 |
| 两槽在极端连续提交下饥饿 | 导入合并提交；必要时第三槽（需 TPM 容量验证） |
| 本地管理员/进程内存攻击 | 超出威胁模型；不作为本设计承诺 |
| TPM 固件异常/清除 | 既有 fail-closed 与恢复流程 |
