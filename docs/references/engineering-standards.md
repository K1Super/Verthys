# 工程规范

## 第一章 总则

### 1.1 目的与适用范围

本规范适用于所有软件开发任务，包括但不限于需求分析、架构设计、编码实现、测试、部署与维护。旨在建立统一、明确、可执行的工程约束，确保交付物安全、正确、可维护、可扩展。

### 1.2 约束层级

约束分为两级：

- **刚性底线**：无条件执行，任何情况下不得违背、降级或省略。
- **弹性标准**：默认执行，但满足特定条件时可降级；降级必须显式声明且说明理由。

### 1.3 冲突消解优先级

当不同约束发生冲突时，按以下顺序裁决：

> **安全合规 > 用户需求 > 功能正确性 > 代码可读性 > 性能优化**

### 1.4 术语定义

- **生产级标准**：默认交付基线。指标必须可测量，测量方式未定义的一律视为未达成。
  - 核心逻辑单元测试覆盖率 ≥ 80%。统计范围须排除 DTO、常量、生成代码与纯配置；以项目既有覆盖率工具的报告为准。
  - 关键接口常规负载 P95 延迟 ≤ 200ms。须同时记录测量环境、负载模型、采样窗口与样本量；按业务场景调整阈值时，四项一并显式定义。
  - 无 OWASP Top 10 高危漏洞。以依赖扫描与静态分析工具的报告为准，不以人工目测结论代替。
  - 并发场景无数据竞争与死锁。须给出验证手段：竞态检测器、压测或并发用例，任选其一并留存结果。
  - 关键路径具备结构化日志与异常追踪能力，日志可被检索与关联。
- **企业分层架构**：至少划分接口层、业务逻辑层、数据访问层。层间单向依赖，禁止跨层调用。不适用三层模型的形态（前端应用、数据管道、CLI、算法库、消息消费者）须划分等价边界，例如视图层与状态层、抽取层与转换层、命令层与领域层，同样执行单向依赖与禁止跨层，并在说明中写明映射关系。小型工具、脚本或临时验证任务可适度简化，但必须在说明中声明简化范围。
- **降级**：在特定条件下，对弹性标准的部分或全部要求进行降低或豁免。降级必须显式声明、有明确理由，且不得触及刚性底线。

## 第二章 刚性底线（无条件执行）

### 2.1 安全合规

- 敏感信息（密钥、密码、令牌、证书等）必须使用环境变量、配置中心或密钥托管服务管理，**禁止硬编码**在代码或配置文件中。
- 所有外部输入（用户输入、API 参数、文件内容、网络数据、模型输出等）必须进行校验、过滤和净化，防范注入、XSS、路径遍历、SSRF、CSRF、不安全反序列化等攻击。
- 涉及认证、授权、加密、审计的场景，必须遵循安全最佳实践，禁止使用已废弃或不安全的算法（如 MD5 作为密码哈希、SHA-1 签名、明文存储密码等）。
- 第三方依赖必须进行安全审查，禁止引入存在已知高危漏洞且无修复版本的组件。

### 2.2 需求忠实与坦诚

- **存疑必问**：需求存在歧义、缺失或不确定时，必须向需求方确认。判定标准是：能由代码、配置、测试、依赖自行查证，且影响可逆、成本极低的歧义，先行查证并记录假设；查证后仍不收敛，或涉及不可逆与高成本决策的，未经确认不得实现。
- **坦诚直言**：如果技术能力、资源、时间或技术栈无法满足需求，必须如实说明，不得敷衍、拼凑、曲改需求或降低交付标准来「完成」任务。

### 2.3 功能正确性底线

- 交付物必须满足已明确的需求功能，不得遗漏核心功能或故意改变行为。
- 关键业务流程（如支付、交易、认证、数据写入）必须具备完整的异常处理与回滚机制，确保数据一致性。
- 禁止为了通过测试或演示而伪造功能、硬编码返回值或绕过真实逻辑。

### 2.4 数据与隐私保护

- 涉及个人隐私数据（PII）必须遵循最小化采集、加密存储、脱敏展示原则。
- 禁止将测试数据、生产数据或用户数据硬编码在代码与注释中。日志不得记录凭据、完整证件号、完整联系方式等敏感明文；排障必需的标识（如用户 ID、订单号）须脱敏或哈希后记录，且仅保留定位所需的最小字段。
- 数据删除、导出、迁移等操作必须经过明确授权，并提供审计日志。

## 第三章 工程质量标准（弹性执行）

### 3.1 架构设计

- **默认采用企业分层架构**：接口层、业务逻辑层、数据访问层；不适用三层模型的形态按 1.4 的等价边界划分。层间单向依赖，禁止跨层调用。
- **遵循 SOLID 原则**，保持高内聚、低耦合。
- 适度设计：既要避免过度设计，也要保证可扩展、可迭代、向后兼容。
- 模块职责单一，边界清晰，避免「上帝类」或「万能模块」。

### 3.2 技术选型

- **默认使用稳定、主流、LTS 版本**的官方技术栈，禁止使用废弃、过时或实验性能力（除非用户明确要求且说明理由）。
- 引入新依赖前，评估其许可证、活跃度、维护状态、社区支持与安全记录。
- 技术栈选定后，保持版本一致性，避免混用不兼容版本。

### 3.3 代码质量

- 命名语义化，遵循主流语言社区约定（如 Java 驼峰、Python 蛇形等）。
- 单一职责：一个函数、类或模块只做一件事。
- 具有业务含义、需要统一变更或需要按环境切换的常量、文案、配置项，必须抽离到配置文件或常量表，**禁止硬编码**在业务逻辑中。语言与协议层面的既定值（如 HTTP 状态码、数组下标 0、单位换算系数）不强制抽离，抽离反而降低可读性。
- 优先保障可读性、可维护性与多人协作适配性，避免过度炫技。
- 代码风格统一（可引入格式化工具与静态检查）。

### 3.4 健壮性与接口规范

- **全链路入参校验**：覆盖空值、空集合、极值、非法格式、类型错误等边界条件。
- **区分业务异常与系统异常**：业务异常返回友好提示；系统异常记录详细日志并返回通用错误信息，不泄露内部细节。
- 对外接口的入参、出参、异常返回必须严格规范化，提供明确的文档或 Schema 定义；内部函数以类型声明与必要注释为准，不强制 Schema。
- 对外接口必须考虑幂等性、超时、重试策略与并发安全。

### 3.5 性能与并发

- 规避低效写法：冗余循环、重复计算、频繁 IO、无索引全表扫描、N+1 查询等。
- 合理使用缓存、批处理、异步等优化手段，但不过度提前优化。
- 并发场景必须保证线程安全、资源正确释放，避免数据竞争、死锁、连接泄漏。
- 对资源（文件、数据库连接、网络连接、句柄、锁）使用语言提供的确定性释放机制（如 try-with-resources、defer、using、with、context manager）确保关闭，异常路径亦然。

### 3.6 可测试性与可观测性

- 业务逻辑与外部依赖解耦，支持单元测试与 Mock。
- 关键路径（核心业务、复杂算法、数据转换）必须提供单元测试。
- 测试必须能在实现出错时失败：恒过的测试、无断言的测试、只验证不抛异常的测试视为未覆盖。断言针对行为与边界，不针对内部实现细节。
- 日志规范：关键节点、异常场景必须记录结构化日志，避免无效调试输出。
- 对外部依赖的调用（数据库、缓存、消息队列、第三方 API）应记录关键信息（如耗时、参数摘要、结果状态）。

### 3.7 注释与文档

- 复杂逻辑、核心算法、对外接口、非常规实现必须添加注释说明意图与设计。
- 注释应解释「为什么」，而非重复「做什么」；拒绝无脑逐行注释。
- 对外接口需提供文档：用途、参数、返回值、异常、示例。

### 3.8 文件与目录结构治理

本节把「文件职责过重」与「目录平铺失控」变成可测量、可复核的工程门禁。原则：按变更理由划界，不以行数作为拆分依据；先建立行为基线，再迁移代码；结构变更与行为变更分开验证。

#### 3.8.1 职责判定

- 两段代码满足任一条件即属于不同职责：修改原因不同；维护角色不同；失败后果不同；需要分别测试或分别发布。
- 文件头需要「并且」才能描述清楚，或目录名无法用一个领域词概括，按职责混杂处理。
- 职责数按「变更理由」计数，不按函数、类或导出数量计数；一个职责可以包含多个函数。

#### 3.8.2 结构体检指标

改动前对将修改的文件与所在目录记录以下指标，并写明测量方式（工具、命令或统计口径）：

| 指标 | 口径 | 说明 |
| --- | --- | --- |
| 有效代码行 | 排除空行、纯注释、生成代码 | 语言无统一工具时以去空行去纯注释的物理行为准 |
| 顶级职责数 | 按变更理由计 | 参考文件头职责清单与公开面 |
| 公开面规模 | 导出符号、公共方法、命令入口数量 | 纯桶文件只计实际契约，不计转发 |
| 同层目录规模 | 直接子文件数与领域数 | 不计生成目录、构建产物与第三方 |
| 函数规模 | 有效行数与最大嵌套层数 | 热点循环与状态表可注明豁免 |

单文件包含模板、样式、脚本的组件按一个维护单元统计；声明文件、生成代码、测试夹具、数据表单列，不参与行数阈值判定，但不得借此类文件藏业务逻辑。

#### 3.8.3 默认阈值与分类

| 信号 | 预警 | 超载 | 处置 |
| --- | --- | --- | --- |
| 有效代码行 | ≥ 800 | ≥ 1200 | 预警：仅同职责改动；超载：新增职责先拆分或书面豁免 |
| 顶级职责数 | — | ≥ 3 | 按变更理由拆分 |
| 公开面 | ≥ 40 个导出符号或单类 ≥ 30 个公开方法 | — | 评估门面与契约拆分，保持导出等价 |
| 同层目录 | — | ≥ 20 个源文件且跨 ≥ 3 个领域 | 按领域分组，根目录留入口、契约与薄桶 |
| 单函数 | ≥ 80 有效行或嵌套 ≥ 5 层 | — | 提取或提前返回；热点与状态表可注明豁免 |

项目既有约定阈值优先，但必须有仓库内可验证依据（配置、脚本或评审记录）；不得为规避门禁临时调高。阈值判定必须结合职责：行数超限但职责单一且高内聚的文件，只禁止新增职责，不强制机械拆分。

阈值是触发器，不是拆分配额：有效行低于 300 的小文件即使职责数超限，也优先合并同职责代码、删除无依据职责或明确边界，不强制拆分为多个碎片；任何拆分须证明收益大于导航与依赖成本。

#### 3.8.4 超载处置

1. **先拆后加（默认）**：按 3.8.5 拆分协议执行，再新增职责。
2. **仅同职责改动**：允许缺陷修复、等价重构、依赖升级；不得扩大职责集合。
3. **书面豁免**：无安全接缝、拆分风险高于收益或用户明确要求时，按 3.8.7 记录；豁免必须写入交付汇报，下次触达时优先复审。

结构治理不构成「顺手重构」：同职责缺陷修复不强制拆分；拆分只在新增职责、触达超载文件或用户要求治理时触发，并与行为变更分开验证。

#### 3.8.5 拆分协议

1. **行为基线**：现有测试或可复现对照；关键路径无测试时先补特征测试。安全、并发、数据写入路径须补不变量测试。
2. **接缝设计**：按变更理由划界；先定义契约（类型、接口、函数签名），再移动实现；共享状态、锁、事务、缓存一致性必须明确归属，不得复制两份。
3. **公开面审计**：迁移前记录导出清单，迁移后 MISSING 与 EXTRA 均为 0；确需增删导出的，逐个列出调用方迁移路径与弃用期。
4. **机械迁移**：先原样移动并修正导入，不混入逻辑改动；行为修复与结构调整分开提交或分开验证。
5. **依赖方向**：禁止新环与低层反向依赖高层；共享契约放叶子模块；禁止把多个子模块状态打包成 god-context 传递，也禁止用参数对象掩盖职责。
6. **验证**：构建、测试、关键路径；前端补组件/交互验证；C/Rust 补编译与测试；脚本补语法检查与可复现执行。
7. **汇报与回滚**：给出拆分前后指标、接缝理由、公开面与行为等价证据、剩余风险、回滚方式。

#### 3.8.6 目录治理

- 同层文件达到 20 个且跨 3 个领域时，按领域建立子目录；根目录只保留入口、公共契约与薄桶文件。
- 目录名必须表达领域，不得使用 `utils`、`common`、`misc`、`helpers` 作为跨领域垃圾桶；确需共享的放 `shared` 且只含稳定契约。
- 优先按变更理由分组，其次按技术角色分组；禁止同一领域在多个层级重复出现。
- 移动文件必须同步更新导入、构建清单、测试路径与文档路径；保持公开导入路径时用薄桶重导出，不得复制实现。
- 桶文件不得承载逻辑、状态或副作用；禁止循环桶与跨层再导出。

#### 3.8.7 豁免与记录

```
结构豁免
- 文件/目录：
- 命中指标：
- 本次新增职责：
- 不拆分理由：没有安全接缝 / 拆分风险高于收益 / 用户明确要求
- 风险与触发条件：
- 到期或复审条件：
- 决策人：
```

豁免不能用于掩盖可拆而未拆的职责混杂；同一文件累计两次豁免后，下一次触达必须给出拆分方案或终止新增职责。

#### 3.8.8 禁止事项

- 按行数均分、按函数数量平均切分。
- 只做转发壳或把原文件改名后原样保留。
- 拆出 `utils` / `common` / `misc` 垃圾桶或一次性抽象。
- 拆分后不更新调用方、不审计导出、不建立行为基线。
- 以「文件太长」作为唯一理由要求或执行拆分。
- 用新文件继续堆积同一混杂职责，制造「看起来拆了」的假象。

## 第四章 输出与交付规范

### 4.1 代码交付

- 代码必须结构化、可直接运行或集成，符合语言与框架标准；不得以占位实现、省略片段或「其余不变」冒充完整交付。

### 4.2 说明文档要求

- 精简话术：只保留有效技术说明，不输出冗余科普、客套铺垫。
- 文档结构清晰，逻辑分明，关键步骤不省略。
- 涉及安全、部署、配置的说明必须准确、完整，禁止含糊。

### 4.3 输出话术

- 回答问题时，先结论后解释。
- 不允许使用「可能」「大概」等模糊词汇描述已确定的事实。
- 当存在不确定时，明确说明不确定项，并给出判断依据或建议确认点。

## 第五章 执行与降级规则

### 5.1 刚性执行

- 刚性底线条款（第二章）在任何任务中**无条件执行**，禁止跳步、简化、合并流程、降级标准、选择性执行、变通替代。
- 即使任务复杂度极低或用户要求简化，刚性底线也不可豁免。

### 5.2 弹性降级条件

弹性标准（第三章）可在以下情况降级：

1. **用户明示简化**：用户明确提出降低工程要求（如「忽略单元测试」「不写注释」「仅实现核心功能」等）。
2. **临时验证任务**：用于原型验证、技术预研、一次性脚本等非生产用途。判定标准：不进入主干分支、不对外发布、不持久化生产数据，三者需同时成立。
3. **任务规模极小**：代码量极小或逻辑极简单，全面遵循会导致明显过度设计。判定标准：单一关注点、改动限于单文件或单函数、无对外契约变更，三者需同时成立。

降级必须满足以下前提：

- 不违反任何刚性底线；
- 不影响功能正确性与安全性；
- 降级范围和原因必须在交付说明中显式声明。

### 5.3 降级声明要求

降级声明应包含：

- 降级的具体条目（如「未编写单元测试」「未采用分层架构」）；
- 降级原因（用户要求 / 临时验证 / 规模过小）；
- 影响与风险（降级可能引入的缺陷与后续返工点）；
- 恢复建议（如需转生产，应补充哪些工作）。

### 5.4 一致性与联动

- 同一任务中，关联模块必须保持统一标准，不得出现部分模块高标准、部分模块低标准的不一致情况。
- 如果因降级导致与其他模块交互的接口契约不完整，必须明确标注风险。

## 第六章 附则
