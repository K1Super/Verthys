# 代码注释规范

## 1. 总则

1. **代码是唯一事实来源**。注释不得与代码行为冲突；冲突时以代码为准，但注释不一致视为缺陷。
2. **注释解释 Why，不解释 What**。禁止逐行翻译代码。
3. **注释必须可验证**。只写能从当前代码、类型、测试、配置、上下文合理确认的内容。
4. **不编造设计意图**。无法确认的内容不写，或写 `TODO(确认): ...`。
5. **最小必要**。公共契约必须注释；简单 getter/setter、显而易见赋值不注释。
6. **随代码更新**。修改代码时必须同步更新相关注释。
7. **注释不是需求追踪表**。不承担需求、工单、文档、版本、会议记录的索引职责。
8. **统一语言与术语**。默认中文；专有名词、代码符号、标准术语保持原文。
9. **注释不承载外部索引**。规范、条款、编号、工单、文档名一律不进入注释，具体边界见第 4 节。

---

## 2. 注释层级与要求

| 层级 | 位置 | 必须写 | 禁止写 |
| --- | --- | --- | --- |
| 文件头/模块 | 文件顶部 | 模块用途、职责边界、关键约束、线程/安全/兼容性说明 | 外部文档引用、工单号、章节号、无意义版权模板 |
| 类型/类/接口 | class/struct/interface/enum 上方 | 用途、生命周期、所有权、线程安全、契约、状态机 | 逐字段翻译、空话 |
| 公共函数/方法 | 声明或定义上方 | 用途、参数、返回值、异常、副作用、幂等、并发、事务、鉴权、性能约束 | 「这是一个方法」「用于返回结果」 |
| 字段/常量/枚举 | 字段/常量上方或行尾 | 单位、取值范围、默认值、生命周期、业务含义 | 重复字段名 |
| 复杂逻辑/分支 | 代码块上方 | 为什么这样分支、边界条件、兼容性、算法来源、规避的坑 | 逐行解释 if/else |
| TODO/FIXME | 对应位置 | 待办原因、触发条件、影响范围、确认人角色 | 外部工单号、日期、人名 |
| 变更/版本记录 | 文件头或 CHANGELOG | 当前有效版本、兼容性约束 | 外部文档名、章节号、方案编号 |

> 变更历史优先放对应变更记录文档，不要塞进代码注释。若 ABI 头文件必须保留版本记录，只写代码内实际存在的版本常量和兼容性约束。

**必须写注释的触发条件**（命中任一即必须写，其余按最小必要处理）：对外暴露的公共契约；非显然的分支与边界条件；绕过常规做法的实现；并发、事务、缓存相关逻辑；对上游缺陷的规避；容易被误用或误删的约束。

## 3. 注释内容标准

### 3.1 应当写

- 用途与职责边界
- 设计思路与关键取舍
- 约束、前置条件、后置条件
- 边界条件、异常路径、错误码语义
- 副作用：IO、网络、磁盘、全局状态、缓存、事务
- 并发：线程安全、可重入、锁、原子性
- 安全：鉴权、权限、敏感数据、加密、校验
- 性能：复杂度、超时、批量、内存占用
- 兼容性：ABI、协议、格式、版本迁移
- 单位、取值范围、默认值、生命周期、所有权
- 幂等性、重试语义、顺序要求

### 3.2 禁止写

- 逐行翻译代码：`将 x 赋值为 y`、`调用 f 方法`。
- 显而易见的内容：`这是一个类`、`返回结果`。
- 空话：`用于处理相关逻辑`、`提高代码质量`。
- 无法验证的猜测，除非有代码证据。
- 过期信息：已删除的字段、旧流程、旧版本行为。
- 外部文档引用和编号。
- 模糊溯源表述。
- 外部人员、会议、日期。
- 大段复制文档内容。

## 4. 外部引用禁用规则

### 4.1 禁止出现

注释中禁止出现任何外部文档引用和外部编号，包括但不限于：

- 文档名/路径
- 章节号/条款号
- 外部文档的版本号/版本别名（用于标识缺陷现象时按例外处理）
- 标准/协议编号，除非项目单独批准。
- 需求/设计/接口/缺陷/任务编号
- URL、链接、外部仓库、内部知识库
- 溯源表述：`见 xxx`、`参考 xxx`、`依据 xxx`、`详见 xxx`、`参见 xxx`、`来源于 xxx`、`对应 xxx`、`按 xxx 要求`。
- 模糊替代表述：`相关文档`、`某规范`、`接口约定`、`需求要求`。
- 外部人员、会议、日期。

**例外**：说明规避上游缺陷的非常规写法时，允许写「库名 + 版本 + 现象」这一最小可复现标识（例如某库在某版本下返回空集合而非空值），以便他人独立验证；仍禁止 URL、issue 编号与文档路径。

### 4.2 允许引用

- 当前代码库内可直接解析的代码符号，使用所在语言的文档引用语法：Java 用 `{@link ApiResponse}`、`{@link #health()}`、`{@code Map<String, String>}`；TypeScript 用 `{@link ApiResponse}`；Go 用 `[ApiResponse]`；无文档引用语法的语言直接写符号名。
- 当前代码可直接验证的行为、约束、边界、副作用、异常、线程安全、事务、幂等、缓存、鉴权要求。
- 项目统一要求的文档标签：`@param`、`@return`、`@throws`，但标签内同样禁止外部引用。
- 代码内实际存在的 ABI/协议版本常量：应引用符号，例如 `{@code VERTHYS_ABI_VERSION_0x0007}`，不写外部文档版本号。

### 4.3 原有注释处理

- 原注释已有外部引用或编号时，允许删除该引用片段，或改写为不依赖外部编号的自包含描述。
- 改写不得改变原注释的技术语义。
- 若删除后语义不完整，只能补充当前代码可验证的信息。
- 若整条注释几乎只有外部引用且无法确认含义，可删除，或改为 `TODO(确认): 待补充设计意图`。
- 除处理外部引用外，不得改动代码和原有注释的技术语义。

## 5. 格式规范

### 5.1 通用

- 默认中文；代码符号、专有名词、标准术语保持原文。
- 中英文之间建议加空格：`返回 HTTP 200`。
- 句末统一使用中文句号。
- 注释与代码同级缩进。
- 行内注释仅用于短说明，复杂说明放上方。
- 公共 API 使用项目指定的文档注释格式。

### 5.2 禁止

- 注释中写 `@see` 外部文档。
- 注释中写外部文档版本号；标识缺陷现象所需的最小版本标识除外。
- 注释中写绑定工单号的 TODO。
- 注释中写外部文档引用。
